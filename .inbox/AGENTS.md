# Inbox Agent Instructions

이 지침은 `.inbox/`와 그 하위 작업 아티팩트를 작성·수정·이동·정리하는 에이전트에 적용한다. 사람을 위한 디렉터리 안내는 [README.md](README.md)가 맡고, 문서의 공통 품질은 [Documentation Principles](../docs/documentation/principles.md)를 따른다. 인박스 아티팩트 자체는 정본 정책이나 실행 지침이 아니다.

## 작성 위치

1. 기존 아티팩트와 링크를 확인하고, 같은 작업의 근거를 갱신할 수 있으면 새 파일을 만들지 않는다.
2. 작업을 식별할 수 있는 가장 안정적인 묶음에 작성한다. GitHub Issue·PR은 `.inbox/github-<number>/`, 브랜치는 `.inbox/branch-<slug>/`, 별도 식별자가 없으면 `.inbox/YYYY-MM-DD/`를 사용한다.
3. 한 작업 묶음 안에서만 파일 번호를 관리한다. 독립적인 작업 묶음의 번호를 이어 쓰지 않는다. 단일 문서 또는 디렉터리 번들을 허용하되, 번들 안에는 추가 하위 디렉터리를 두지 않는다.

## 파일명

새 작업 문서는 **순서 번호와 slug가 필수**이고, 유형 접두사와 확장 접미사는 필요할 때만 붙인다. 아래 대괄호는 선택 항목을 나타내는 문법이며 **실제 파일명에는 포함하지 않는다.**

```text
<NN>[-<type>]-<slug>[-<extension>].md
```

- `NN`: 같은 디렉터리에서 독립 문서에 `00`부터 순차 부여한다. 기존 독립 문서의 최대 번호 다음을 사용하고 충돌을 확인한다. **확장 문서는 원본 문서의 번호를 유지한다.** 나중에 수정·삭제해도 기존 번호를 다시 매기지 않는다.
- `<type>`: 선택적인 유형 접두사다. `research`, `plan`, `review`, `report`, `handoff`, `draft` 등 문서 역할을 설명하는 소문자 값을 사용한다. 유형 목록은 고정 enum이 아니다.
- `<slug>`: 내용을 구별하는 짧고 안정적인 kebab-case 주제다. 이미 디렉터리가 식별하는 PR 번호나 브랜치명을 불필요하게 반복하지 않는다.
- `<extension>`: 선택적인 확장 접미사다. 원본 문서의 특정 내용을 별도 문서로 확장할 때 `sources`, `findings`, `evidence`처럼 그 내용을 표시한다. 원본의 번호·선택된 유형·slug를 유지하고 뒤에 붙인다. **날짜·작성자·검토 상태·버전 같은 메타데이터에는 사용하지 않는다.** 독립된 문서는 별도 번호와 slug로 작성한다.
- `README.md`와 `AGENTS.md`는 진입점 파일이므로 번호를 붙이지 않는다. 기존 번호 없는 작업 파일은 일괄 개명하지 않으며, 명시적인 이관 시 참조 링크·문서 내용·보존 정책을 함께 검토한다.

```text
.inbox/github-294/
├── 00-research-generated-sync.md
├── 00-research-generated-sync-sources.md
├── 01-review-generated-sync.md
├── 01-review-generated-sync-findings.md
└── 02-follow-up.md
```

위 예시는 **명명 형식만** 설명한다. `02-follow-up.md`는 유형 접두사를 생략한 예시다. PR #294의 실제 파일명이나 현 상태를 나타내지 않는다.

## 라이프사이클

1. 작업 중에는 기존 문서의 갱신을 우선한다. 필요한 경우 별도 확장·독립 아티팩트를 만들고, 이름이나 경로를 변경하면 관련 링크와 참조를 확인한다.
2. 검토·조사 결과가 장기적으로 유효한 결론으로 확정되면 해당 정본에 반영한다. 인박스 자료는 정본 정책·실행 지침을 대신하지 않으며, 정본 반영 자체가 작업 완료를 뜻하지 않는다.
3. 작업 종료는 남은 과제·차단·인계를 확인해 판단한다. PR의 merge·close 또는 문서 작성 완료만으로 종료하지 않는다. 미완료 과제가 있으면 작업 중인 자료로 유지한다.
4. 정리는 **작업이 종료되고**, **생성 또는 마지막 실질적 갱신 후 7일이 지난 경우에만** 검토한다. 단순 Git merge·이동으로 그 시점을 갱신하지 않는다.
5. 필요한 맥락을 정본·코드·PR·검증 기록·Git 이력에서 확인할 수 있으면 중복·초안 문서는 삭제를 우선한다. 현재 정본이 원문을 직접 인용하거나 재현·감사에 원문이 필요하고 Git 이력에서 복원하는 비용이 큰 경우에만 아카이브를 검토한다.
6. 종료 여부·보존 근거가 불확실하거나 아직 보호 기간이면 현 상태로 유지하고 다음 재평가 조건을 남긴다. 보존만을 위해 별도 상태 파일·레지스트리를 만들지 않는다.

사람이 읽는 흐름도와 보존 정책은 [README.md의 라이프사이클](README.md#라이프사이클)에서 확인한다.
