# Chatbot Development Workflow — 제안 및 후속 검증

> 작업 중인 제안 기록입니다. 재사용 패턴의 현재 본문은 [Chatbot-Driven Development](../../catalog/patterns/workflow/chatbot-driven-development.md)를 참고합니다.

## 배경과 선택

처음 문제는 챗봇에서 `검토 → 수정 → CI 확인 → 재검토`를 사용자가 매번 지시해야 하는 부담이었습니다. 논의 과정에서 더 본질적인 문제는 **목표·지시·완료 조건이 불완전할 때 사람과 구체화하거나 에이전트에 판단을 위임하고, 그 결과를 증거로 검증할 수 있는가**임을 확인했습니다.

처음에는 챗봇 전용 실행 레시피, Prompt, Rulesync Command, Skill을 검토했습니다. 그러나 이 단계에서 새로운 실행 자산을 결정하면 협업 방식 자체가 도구·호출 형식에 묶일 수 있습니다. 따라서 재사용 가능한 접근을 **workflow pattern**으로 먼저 기술하고, 개별 프로젝트의 적용과 자동화는 나중에 결정하는 방향을 택했습니다.

현재 패턴은 특정 오케스트레이터나 도구를 요구하지 않습니다. 기존 `mols-loops`와 GitHub CI는 활용 가능한 사례이며, 이 제안은 별도의 RPI 상태 기계나 CI 정책을 만들려는 것이 아닙니다.

## 실증할 질문

1. **목표 정렬:** 모호한 요청에서 사용자의 의도와 에이전트가 도출한 완료 기준이 실제로 맞는가?
2. **위임 품질:** 불필요한 질문을 줄이면서 중요한 선호·승인·범위 변경은 정확히 사람에게 돌려주는가?
3. **작업 수렴:** 같은 작업에서 사용자에게 반복 지시를 요구하지 않고 적절한 조사·구현·리뷰·검증을 이어 갈 수 있는가?
4. **증거와 재개:** 실제 테스트·CI·리뷰가 증명하지 않은 성공을 주장하지 않고, 중단 시 현재 revision과 남은 작업을 정확히 남기는가?

대표 사례로 명확한 PR, 모호한 PR의 협업형/위임형, 기존 스펙과 목표의 충돌, CI 실패, 도구 미지원, 다른 head revision으로 재개하는 경우를 고려할 수 있습니다.

수동 다단계 지시 방식과 비교한다면 가능한 한 같은 모델·도구·권한·초기 revision·평가 기준을 사용하고, 질문 수뿐 아니라 결과 품질과 잘못된 범위 확대도 함께 측정하는 편이 적절합니다.

## 아직 결정하지 않은 것

- 어떤 챗봇/하네스에서 패턴을 실제로 적용하고 어떻게 로드할지
- 실행 자산이 정말 필요한지, 필요하다면 최소 단위가 무엇인지
- 대표 사례의 독립적인 목표 정렬 기준과 실제 런타임 측정 방식

이 PR의 문서 리뷰와 CI 성공은 **문서 변경의 검증 근거**일 뿐, 협업 패턴을 적용한 챗봇의 행동 품질 검증은 아닙니다.
