## 결론과 사용자 의도

- **스킬은 개발환경 부트스트랩의 설계·리뷰·구현 인계를 담당한다.** 구현 자체는 에이전트의 일반 엔지니어링 작업과 대상 프로젝트의 명시적 요구가 소유한다. 스킬에 구현·설치 실행 절차를 추가하지 않는다. 기존의 '스킬도 구현까지 소유한다'는 잠정 제안은 철회한다.
- **설치 여부는 사용자에게 명시적으로 허가받는다.** 계획된 설치 작업의 도구·위치·버전·공유 영역 영향과 기존 도구 재사용 가능성을 먼저 알려주고, 허가 전에는 설치하지 않는다. 도구별로 반복 승인받기보다는 영향이 명확한 설치 묶음을 한 번에 승인받을 수 있다. 단순한 스킬 활성화나 코드 구현 요청은 설치 승인이 아니다.
- **일반 개발 도구(Ruff, Biome 등)는 최신 릴리스를 선호할 수 있다.** 그러나 어떤 도구를 어느 버전 범위로 업데이트할지는 기존 프로젝트 정책과 재현성 요구가 소유하며, `setup`은 최신 버전으로 암묵적 갱신을 하지 않는다.
- **안전의 기준은 도구 이름이 아니라 변경 위치·영향·권한 범위다.** 이미 사용자가 명시적으로 허가한 동일 설치 묶음은 반복 질의 없이 실행할 수 있지만, 새로운 설치 범위·위치·전역 영향으로 확대할 때는 다시 허가받는다.
- **`setup`과 `update`는 분리한다.** `setup`은 재현 가능한 확정 버전을 사용하며 반복 실행만으로 최신 버전으로 승격하지 않는다. `update`는 사용자가 명시적으로 요청한 때 정책상 허용된 최신 버전을 해석·기록·검증한다.
- **설계·구현 요청과 실제 사용자 컴퓨터 환경 변경은 다르다.** 스킬 활성화 또는 코드 구현 요청만으로 도구 설치·업데이트 권한이 생기지 않는다. 프로젝트에 정책이 선언돼 있어도 에이전트가 실제 설치를 실행할 때는 해당 범위에 대한 사용자 허가가 필요하다. 사용자가 직접 명령을 실행하는 경우는 [정본의 명시된 동작](../../docs/development/development-environment.md)을 따른다.
- **전역 도구의 재사용을 기본 우선순위로 두지 않는다.** 먼저 프로젝트의 도구 소유권·격리·잠금 계약을 확인한다. Git 같은 독립 도구는 적합하면 재사용하되, Python 인터프리터가 있다고 전역 site-packages나 Ruff를 프로젝트 의존성처럼 재사용하지 않는다. 별도 설치가 필요할 때만 승인 범위 안에서 진행한다.

위 항목은 대화에서 확인된 사용자 요구와 설계 방향이다. 구체적인 도구별 권한 목록, 버전 채널, 잠금 전략, 신규 실행 기능은 **아직 제안/검증 대상**이며 합의된 구현 완료로 간주하지 않는다.

## 왜 재검토하는가

1. 초기 토론에서는 스킬 자체가 설계와 구현을 모두 담당하도록 확장하자는 제안이 있었다. **최신 결정으로 이를 철회**했다. 스킬은 설계·리뷰·구현 인계에 집중하고, 일반 코딩 에이전트가 실제 구현을 맡는다.
1. 설치 승인 없이 도구 관리 영역이나 HOME을 바꾸면 안 된다. 그렇다고 일반 도구마다 매번 묻는 것도 비효율적이므로 **설치 범위를 먼저 설명하고 사용자가 묶음 단위로 허가**하도록 설계한다.
1. 현 PR의 [`mise.toml`](../../mise.toml)은 CLI를 전부 exact pin으로 선언하며, [`development_bootstrap.py`](../../scripts/development_bootstrap.py)는 `mise install <tool>@<version>`을 호출한다. 이는 **OS 전역 패키지 설치는 아니지만 사용자 공유 mise 데이터/캐시에 쓰기**를 할 수 있다. 현재 `update`는 Python 의존성의 bounded update만 구현하고 Ruff/Biome 등의 tool-range/latest update는 구현하지 않았다.
1. 기본 `setup`에서 Rulesync projection, HOME의 native Skill 설치, Git hook 변경을 분리한 것은 안전 경계로 유지할 가치가 있다. 특히 외부 설치 스크립트를 프로젝트 로컬 패키지 설치와 동일하게 취급하면 안 된다.
1. [Skill capability 평가](https://github.com/mols3131d/mols-agent-assets/blob/1f1efa63efaad63f4bda19fe4781920bb2c6c541/docs/skills/mols-dev-env-bootstrap-design/evaluation.md)에는 모델별 near-miss/behavior 실패가 남아 있다. 설계 요청에서 설치를 허용하지 않는지, 구현 요청의 경우 일반 엔지니어링 caller에게 적절히 인계하는지, 설치 허가를 명시하는지를 아직 충분히 검증하지 않았다.

## 결정된 책임 경계와 후속 설계 인계

### 사용자 요청별 실행 경계

| 요청 의도 | 스킬의 결과 | 실행·쓰기 경계 |
| --- | --- | --- |
| 부트스트랩 **설계·리뷰** | 현재 정책 분석, 비교, 설계/검토 결과 | 기본 읽기 전용. 설치·설정 수정 금지 |
| 부트스트랩 **구현·개선** | 설계 스킬은 구현 가능하도록 인계; 실제 코딩은 일반 개발 작업 | repository 파일 변경의 권한과 실행 책임은 caller·대상 프로젝트가 소유. 설치는 별도 사용자 허가 |
| 부트스트랩 **실행·복구** | 설계 스킬의 범위 밖인 운영 작업 | 실행 에이전트는 실제 설치 이전 사용자에게 영향 범위를 제시하고 허가받음 |
| **명시적 update** | 설계 스킬은 업데이트 경로 설계·리뷰만 수행 | 실제 업데이트 실행 전 사용자 허가 필요; 정책 범위 초과·자동 커밋 금지 |

**스킬은 설계 전용이다.** 구현 요청의 일반 개발 작업과 실제 설치·업데이트 실행은 대상 프로젝트·에이전트 호출자가 담당하며, 사용자 허가 없이 설치를 시작하지 않는다.

### 승인을 도구별이 아닌 변경 범위별로

- **한 번에 승인할 수 있는 영역:** 설치가 필요한 도구·의존성, 지정한 관리 영역(mise cache 및 프로젝트 `.venv` 등), 예상 네트워크·공유 캐시 쓰기를 에이전트가 먼저 제시하고 사용자에게 명시적으로 허가받는다. 프로젝트 정책 선언만으로 허가를 생략하지 않는다.
- **새 허가 또는 별도 실행 경로가 필요한 경계:** OS 패키지 관리자·`sudo`, 전역 npm/pip, Shell profile/PATH·Git 전역 설정, 사용자 파일 덮어쓰기, HOME의 native installer·symlink 교체/삭제, 외부 remote installer 실행 등. 사용자 허가 외에도 runtime·OS·정책 권한을 확인한다.
- **도구 관리자 ≠ 무조건 안전:** 사용자 공유 캐시, 사용자 지정 `MISE_DATA_DIR` 등으로 실제 쓰기 위치가 달라질 수 있고, 설치 중 제3자 코드가 실행될 수 있다. 설치 전에 변경 경계를 설명하고 사용자에게 허가받되 **매 도구마다 개별 확인을 요구하지 않는다.**
- 사전 허용 범위는 가능하면 기존 repository 정책·도구 설정에 선언한다. 별도의 범용 권한 프레임워크나 승인 파일을 새로 만드는 것은 요구하지 않는다.

### 프로젝트 격리 계약에 따른 재사용·설치 판단

**기존 전역 도구 우선이라는 잠정 제안은 철회한다.** 도구 종류마다 재사용할 수 있는 계층이 다르며, 사용자의 Python 반례에 따라 재사용보다 프로젝트의 **관리 주체·격리 계약**을 먼저 판단하기로 수정했다. 실제 운영 정본은 [개발환경 구축 정책](../../docs/development/development-environment.md)이다.

| 자산 | 판단 |
| --- | --- |
| Git·Shell 같은 독립 호스트 도구 | 프로젝트의 전제조건을 충족하면 기존 실행 파일 사용; 사용자 전역 버전 임의 변경 금지 |
| Python 인터프리터 | 프로젝트 버전·managed/system 선택 정책이 허용하는 기존 인터프리터를 **가상환경 기반**으로 활용할 수 있음 |
| Python 패키지·Ruff·pytest | `uv.lock`과 프로젝트 `.venv`를 따른다. 동일 버전의 전역 site-packages나 PATH Ruff도 대체물로 인정하지 않음 |
| mise-managed Node·Biome 등 | 해당 manager의 선언된 버전과 캐시를 사용. PATH의 다른 전역 명령으로 임의 대체 금지 |
| 사용자 HOME·외부 installer | 기존 사용자 상태를 보존하고, 실제 변경 시 별도 영향·허가 판단 |

Python 인터프리터를 재사용할 수 있다는 사실은 그 인터프리터의 전역 패키지·라이브러리를 재사용해도 된다는 뜻이 아니다. 기존 전역 패키지 환경을 대상으로 `uv sync`·`pip install`을 수행하지 않으며, `uv sync`의 프로젝트 가상환경 내 기존 패키지 제거 가능성도 사용자에게 안내한다. 이 저장소 runner는 외부 `UV_PROJECT_ENVIRONMENT`와 `.venv` 링크를 차단하고 `--locked`로 프로젝트 `.venv`를 동기화하므로 **현재 실행기의 실제 동작과 잘못된 재사용 일반화를 구분한다.**

이미 설치된 호환 자산과 manager 캐시는 활용하되, 사용 권한과 새로운 설치·업데이트 권한은 분리한다. 별도 설치가 필요한 경우도 프로젝트가 지정한 영역과 사전 사용자 허가를 따라야 하며, 모호하다고 자동으로 새 전역 설치를 시작하지 않는다. 별도 범용 도구 탐색 프레임워크를 만들지 않고 기존 도구 관리자의 native 기능을 우선한다.

### 최신 버전의 의미와 재현성

- **설정:** `setup`은 잠긴 선택 결과를 재사용하며 임의의 `latest` 탐색이나 lock 재작성을 하지 않는다.
- **업데이트:** `update`를 명시적으로 실행할 때만 각 도구의 **사전 허용 버전·채널·revision 정책** 안에서 최신 적합 버전을 선택한다. "최신 선호"는 모든 도구의 무제한 major 승격을 의미하지 않는다.
- **일반 도구:** Ruff, Biome처럼 최신 stable 선호가 타당한 경우 프로젝트 정책에 맞춰 허용 범위를 넓게 정할 수 있다. 포맷/린트 결과와 기존 프로젝트 호환성 변화는 검증해야 한다.
- **호환성 민감 도구:** Node.js, Rulesync 등은 프로젝트가 정한 major/minor 또는 exact 정책을 따른다. 이동하는 Git ref, 외부 Skill revision은 정책 없이 무조건 갱신하지 않는다.
- 정책은 해당 도구의 native 설정, lock/resolver가 소유한다. 스크립트에 또 다른 허용 버전 목록을 하드코딩하지 않는다. Tool range와 mise lock/sidecar를 채택하기 전에는 실제 설치 버전의 native 재현·갱신 기능과 플랫폼 호환성을 검증한다.

| 전역 도구의 출처·버전이 모호하거나 pin과 충돌하는가? | 전역 설치를 건드리지 않고 승인된 별도 경로 선택, 불가 시 보류·보고 | PATH 충돌/lock 재현성·side-effect 테스트 |

| OS 전역/HOME 변경을 임의 실행하는가? | 사용자 허가 및 runtime·정책 권한 없으면 중단·인계, 기존 사용자 상태 보존 | 격리된 runtime/side-effect 테스트 |
| `setup` 재실행에서 버전이 올라가는가? | locked 결과 보존 | deterministic lock/state 비교 |
| Ruff/Biome에 새 stable 버전이 나왔는가? | 명시적 `update`에서만 해당 버전 정책에 따라 선택 | native resolver/lock + 기능 검증 |
| 설치 중 일부만 실패했는가? | 독립 단계 계속, 의존 단계 skip, 실패·복구가 정확히 표시 | deterministic 실패 주입 |
| 설치 위치가 사용자 설정으로 변경되는가? | 실제 쓰기 범위 인지, 승인 바깥 변경은 차단 또는 보류 | 환경변수/설치 경로 fixture |

이 테스트는 **스킬이 과잉 행동을 제안·실행하지 않는지**와 **실제 설치기가 쓰기 범위를 지키는지**를 분리한다. 프롬프트 평가 통과를 OS 격리나 설치기 안전성 입증으로 주장하지 않는다.

## PR #256 작업 인계 및 미확정 항목

1. **스킬 책임 확정:** 설계·리뷰·구현 인계만 담당하도록 유지한다. 실제 구현·설치 실행은 일반 코딩 에이전트와 대상 프로젝트가 소유한다. portable core 및 native tool 우선 원칙을 보존한다.
1. **사용자 설치 허가 반영:** 에이전트가 manager-managed/project-local 변경을 실행하기 전에도 설치가 필요한지, 무엇이 어디에 설치되는지를 제시해 명시적으로 허가받는다. 하나의 명확한 설치 묶음에 대해서만 반복 승인을 생략한다. user/global·host scope 확대는 별도 판단한다.
   - **환경 정책 우선:** 독립 호스트 도구, Python 인터프리터, 프로젝트 격리 패키지 및 manager-managed CLI를 구분한다. 전역 Python 패키지/전역 Ruff는 프로젝트 `uv.lock`의 대안이 아니다. 기존 도구를 무조건 재설치하지 않되, 재사용 여부는 환경 소유권·격리 계약으로 판정한다.
1. **실제 구현 범위 재검토:** Ruff/Biome 등의 최신 정책을 도입할 도구와 정확한 버전 고정이 필요한 도구를 구분한다. mise lock/native resolver·sidecar·Windows/다중 OS 테스트가 준비되기 전까지 tool range 도입을 완료라고 표시하지 않는다.
1. **평가 확대:** Skill은 설계 범위와 설치 허가 설계를 평가하고, 실제 구현 품질과 설치 허가 준수는 일반 개발 workflow 및 deterministic/integration evidence로 따로 검증한다.
1. **기존 리뷰 결함과 분리:** [재리뷰](https://github.com/mols3131d/mols-agent-assets/pull/256#pullrequestreview-5639031596)에서 지적된 Git 환경변수 상속에 따른 dirty-lock 검사 우회는 이번 UX/권한 논의와 별개인 구현 결함으로 계속 추적한다.
1. **정본 반영:** 이 저장소의 구축·설치 허가·운영 정책은 [Development Environment](../../docs/development/development-environment.md)가 소유한다. 스킬 계약은 `SKILL.md`, 정확한 버전 선언은 `mise.toml`과 native config/lock, 실제 명령은 [mise 안내](../../docs/development/tooling/mise.md)가 소유한다. 이 inbox 문서는 논의 근거와 인계만 보존한다.

**확정된 결정:** 설계 전용 Skill, 개발환경 구축 문서의 운영 정본화, 에이전트 실행 전 사용자 설치 허가, 승인 범위별 묶음 승인. **남은 판단:** 어떤 개발 도구를 최신 stable 채널로 운영할지, 새로운 범위형 버전 정책을 이 PR에 포함할지/후속 작업으로 넘길지, 현재 CLI 실행기에 사용자 허가를 기계적으로 검증하는 기능이 필요한지. 사용자의 "일반 도구는 최신 버전이면 충분"이라는 선호를 모든 도구에 대한 무제한 업데이트 승인으로 해석하지 않는다.
