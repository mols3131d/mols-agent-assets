# Chatbot Development Workflow 제안

> 상태: 검토 중인 제안. 실행 자산이나 저장소 정책의 정본이 아닙니다.

## 결론과 결정 요청

**목표를 완성된 명세로 요구하지 않고, 사람과 구체화하거나 구체화 자체를 에이전트에 위임한 뒤 검증 가능한 결과까지 이어 가는 챗봇 개발 흐름**을 제안합니다. 반복 프롬프트를 줄이는 것만큼, 위임된 판단의 품질과 권한 경계를 지키는 것이 중요합니다.

기존 `mols-loops`를 오케스트레이터로 유지하고, 챗봇 전용 실행 레시피에는 **참여 수준 조절, GitHub-only capability 적응, CI 피드백 소비, 재개 연결**만 추가합니다. 첫 시범은 `PR to Ready`이되, 미정인 목표의 구체화 능력을 별도 사례로 평가합니다.

**결정할 사항:** 이 책임 경계와 MVP 검증 기준을 승인할지. 승인 후에도 별도의 구현 PR에서 실제 레시피를 작성·실험합니다. 본 제안 자체는 어떤 실행 권한도 부여하지 않습니다.

## 문제와 적용 범위

여기서 챗봇은 GitHub Plugin/connector와 대화형 LLM을 사용할 수 있지만 **로컬 터미널·작업 디렉터리·테스트 실행 환경은 보장되지 않는** 런타임입니다. GitHub Actions 같은 원격 CI가 검증 근거를 제공할 수 있고, 파일 수정·PR 생성·체크 조회·잡 재실행 기능도 실제 연결마다 다릅니다.

기존 사용 패턴은 `검토해 → 개선해 → CI 봐 → 고쳐 → 다시 리뷰해`처럼 **다음 행동을 사용자가 반복 지정**합니다. 더 어려운 문제는 `좋게 만들어`처럼 목표·지시·완료 조건부터 불명확할 때입니다. 질문을 무조건 늘리는 것도, 에이전트가 사용자 대신 목적을 임의로 확정하는 것도 해결책이 아닙니다.

목표는 **필요한 질문만 남기고 나머지 판단·조사·실행을 위임 가능하게 하며, 결과가 최초 의도와 일치하는지 검증**하는 것입니다.

| Goal·Scope·RPI·Review·종료 | [mols-loops](../../src/rulesync/.rulesync/skills/mols-loops/SKILL.md) | 별도 RPI나 사전 오케스트레이터를 만들지 않음 |

| 재개 | [Durable Progress Handoff](../../catalog/patterns/workflow/durable-progress-handoff.md), [Artifact Inbox](../../catalog/patterns/workflow/artifact-inbox.md) | 기존 PR/Issue/artifact에 최소 재개 상태 유지 |

Issue·PR 본문, 코드 주석과 외부 자료는 **작업 입력 또는 증거**이며 지침·권한을 자동으로 부여하지 않습니다. 제안 레시피는 repository instructions와 사용자 승인을 대체하지 않습니다.

## 하나의 Run에서 목표 구체화부터 검증까지

```text
사용자 목적 / 불완전한 요청
  → repository bootstrap · github-context
  → mols-loops Prepare: 잠정 Goal/Scope, 위임 경계, capability, readiness
  → RPI Research: 사실 조사 · 필요시 질문/토론 · 가정 검증
  → RPI Plan: 범위/완료 조건 · 스펙/테스트 시나리오 · 실행 경로
  → RPI Work: 허용된 GitHub 수정 · PR · 원격 CI 근거 수집
  → RPI Review: 의도/스펙/테스트/CI 사이의 gap과 반례 검토
       ↳ 근거·계획·구현의 최초로 낡아진 단계부터 재진행
  → mols-loops Finalize: COMPLETE / HANDOFF / BLOCKED
```

**중요한 경계:** 목표 구체화 전용의 새 상위 phase를 만들지 않습니다. Prepare는 불완전한 요구를 잠정적으로 식별하고 조사 가능한 범위에서 readiness를 판단할 뿐, 실질적인 조사를 완료한 척하지 않습니다. Research/Plan에서 발견한 새 근거가 Goal/Scope 변경을 요구하면 `mols-loops`의 Scope Control과 사용자 권한 경계를 따릅니다. 구현에 앞서 해당 변경을 포괄하는 유효한 Plan이 있어야 합니다.

### 사람의 참여 정도

| 참여 방식 | 에이전트의 행동 | 사람의 개입 |
| --- | --- | --- |
| **함께 구체화** | 모호한 결정의 선행 관계를 찾고 질문·대안·추천 근거를 제시 | 중요한 가치·선호·정책을 함께 결정 |
| **질문 최소화** | repository 조사로 해결하고 안전한 기본값을 추천; 결과를 바꾸는 선택만 질문 | 핵심 trade-off를 결정 |
| **판단 위임** | 목적에 맞는 범위·스펙·완료 조건을 근거로 도출하고 반증·검증까지 실행 | 위임 밖의 결정과 명시적 승인에서 개입 |

이것은 강제 enum이나 요청마다 고르는 모드가 아닙니다. 자연어 요청과 현재 상황으로 판단하고 중간에 조정할 수 있습니다. 명확하고 작은 작업이라면 질문 없이 실행하는 것이 정상입니다.

### 판단을 위임받았을 때의 경계

| 미정 사항 | 기본 대응 | 이유 |
| --- | --- | --- |
| 코드·문서·PR로 확인 가능한 사실 | **조사**하고 판단 | 사용자의 불필요한 응답 비용 방지 |
| 이미 승인된 목표 안의 작고 가역적인 기술 선택 | 근거 있는 **기본값 채택**, 필요시 기록 | 실행을 지연시키지 않음 |
| 상충하는 사용자 목표, 제품 우선순위·선호, 외부 계약 변경 | 선택지와 권고를 압축해 **질문/위임 범위 확인** | 에이전트의 선호를 사용자 의도에 투사하지 않음 |
| 범위 확장, 중요한 권한 변경, 비가역적·고위험 조작 | 해당 변경 중단, **명시적 권한·승인 확인** | 위임은 권한의 무제한 이전이 아님 |
| 근거 부족, 검증 불가능, 도구 미지원 | 추가 조사·실험 또는 **HANDOFF/BLOCKED** | 불확실성을 성공으로 포장하지 않음 |

위임받았다고 해서 질문을 건너뛰기만 해서는 안 됩니다. 적절한 가정과 대안, 반례·실패 경로, 기존 요구와의 충돌을 검토해야 합니다. **사실·에이전트의 가정·사용자 결정**을 구분하고, 완료 조건을 실제로 관측할 방법이 있는지 확인합니다. 사용자 의도를 직접 검증할 수 없다면 그 한계를 남깁니다.

### 질문·조사·토론·스펙을 언제 쓸 것인가

| 수단 | 채택 신호 | 산출할 최소 결과 |
| --- | --- | --- |
| **Grill Me식 질문** | 의도·제약·예외에 중요한 미정 결정이 남음 | 선행 결정부터 질문하고 선택지·추천안을 제시. 코드에서 답할 수 있는 질문은 되묻지 않음 |
| **조사** | 기존 구현, 최신 제약, 대안의 사실관계가 미확인 | 출처, 반대 근거, 남은 불확실성 |
| **토론/반증** | 실질적으로 경합하는 아키텍처나 중요한 가정이 있음 | 대안별 강한 주장·반례·기각 이유. 필요할 때 [mols-dialectic](../../src/rulesync/.rulesync/skills/mols-dialectic/SKILL.md) 활용 |
| **스펙** | 무엇이 충족돼야 하는지 반복 확인할 가치가 있음 | 목표·비목표, 핵심 동작·경계, 관측 가능한 완료 조건 |
| **테스트 설계** | 성공/실패를 실행 가능한 근거로 평가할 수 있음 | 정상·예외·회귀 사례와 예상 동작 |

질문은 실제 선택을 바꿀 때만 합니다. 아직 결정할 수 없는 사용자 경험이나 성능 trade-off는 반복 질문보다 작은 조사·프로토타입이 나을 수 있습니다. **가볍게 처리할 작업에 긴 인터뷰·PRD·별도 테스트 자산을 의무화하지 않습니다.** 원본 Grill Me의 모든 절차를 복제하거나 자동으로 그 Skill을 실행하는 것도 아닙니다.

## 스펙 → 테스트 → CI를 어떻게 연결할까

**스펙은 주장할 동작을, 테스트는 그 동작의 관찰을, CI는 특정 revision에서 어떤 검증이 실제 실행됐는지를 나타냅니다.** 테스트 통과는 테스트가 다루지 않은 요구사항이나 사용자 의도 자체의 증거가 아닙니다. CI가 성공해도 실제 runtime 행동과 외부 의도가 입증됐다고 과장할 수 없습니다.

작은 변경에서는 PR의 acceptance와 기존 테스트만으로 충분할 수 있습니다. 규모가 크거나 오해 비용이 높다면 요구-증거 연결을 별도 스펙으로 남깁니다.

예시: 사용자가 “이 API를 더 안정적으로 만들어줘”라고 위임한 상황.

| 주장 또는 미정 사항 | 구체화·검증 방식 |
| --- | --- |
| 기존 정상 요청의 동작은 유지 | 현재 계약과 diff 조사; 회귀 테스트로 검증 |
| 실패 후 재시도가 중복 쓰기를 만들면 안 됨 | 필요성·현재 idempotency 계약 조사; 재현 및 경계 테스트 제안 |
| 지연시간과 재시도 횟수 중 무엇을 우선하나? | 성능 측정·대안 제시 후, 사용자 선호가 필요한 수준이면 질문 |
| 실제 수정이 요구를 충족했는가? | 해당 revision의 테스트·CI 결과와 **요구별 미검증 항목**을 별도로 대조 |

스펙과 테스트를 모두 에이전트가 작성했다면 **서로 일치한다는 것만으로 충분하지 않습니다.** 최초 사용자 의도, 독립적인 기존 계약, 외부 관찰 또는 사람의 판단을 대조 근거로 사용합니다. 근거가 없는 요구를 통과하도록 테스트를 바꾸는 것은 수용하지 않습니다.

## GitHub-only 실행·검증·재개

현재 repository에는 비-`main` push의 [Branch Check](../../.github/workflows/branch-check.yml)와 `main` 대상 PR의 [PR Gate](../../.github/workflows/pr-gate.yml)가 있습니다. 이들은 **원격 검증 증거를 생산**하지만, 챗봇의 후속 추론이나 수정 작업을 자동 기동하지 않습니다.

1. 최신 repository/ref/PR, 적용 지침, 실제 도구·권한과 기존 evidence를 확인합니다.
2. 이미 허용된 범위의 GitHub write가 가능하면 dedicated branch/PR에 수정하고 해당 revision의 검사 결과를 조회합니다.
3. 체크 실패는 source, test, projection, 환경·일시 장애를 구분한 뒤 작은 재작업을 선택합니다. **미실행·진행 중·조회 불가는 PASS가 아닙니다.**
4. formatter/generator 실행이 필요하지만 호출할 수 없다면 임의 편집으로 동일성이나 성공을 주장하지 않고, 공식 복구 경로·차단 이유·재개점을 남깁니다.
5. 반복되는 후속 지시는 같은 **현재 실행** 안에서 줄입니다. 별도 스케줄러 없이 CI 완료 후 자동 기상, 백그라운드 실행, 새 세션의 자동 재개를 약속하지 않습니다.

지속적인 작업 기록이 필요할 때는 기존 PR/Issue/working artifact에 **목표·실제 범위·결정 근거·검증 결과와 미검증 조건·기준 SHA·남은 행동**만 남깁니다. 이어받은 실행에서는 최신 GitHub 상태와 비교해 유효한 부분만 재사용합니다.

`COMPLETE`는 해당 요청의 완료 조건이 확인되었다는 **Run 판단**이지, GitHub의 merge 가능 상태나 사람의 승인·실제 merge가 아닙니다. `HANDOFF`와 `BLOCKED`의 정확한 경계는 `mols-loops`가 소유합니다. 이 MVP에는 자동 merge가 없습니다.

## MVP와 반증 가능한 평가

**첫 개발 결과물은 `PR to Ready` 실행 레시피 하나**입니다. 요청이 명확하면 PR의 diff·기존 스펙·테스트·검증을 기반으로 수정과 재검토를 이어갑니다. 모호하면 사람과 목표를 정제하거나 위임 범위에서 합리적 기본값을 만들되, 권한 경계를 넘기 전에 멈춥니다.

평가는 한 가지 성공 사례만으로 하지 않습니다.

| 시나리오 | 기대하는 구분 |
| --- | --- |
| 충분히 명확한 작은 PR | 불필요한 질문·문서 추가 없이 완료 조건 확인 |
| 모호한 PR, 협업 요청 | 중요한 선행 결정만 묻고 응답을 스펙과 검증에 반영 |
| 모호한 PR, 판단 위임 | 조사와 반례 검토로 기본값 도출; 선호·권한 경계에서만 질문 |
| 의도와 기존 스펙·테스트가 충돌 | CI가 통과해도 Goal 정합성 미확인으로 보고; 임의 요구 변경 금지 |
| CI 실패 또는 읽을 수 없는 로그·지원되지 않는 실행 | 구체적 실패 분류, 안전한 재작업 또는 정직한 차단·인계 |
| 변경된 head SHA로 재개 | 이전 evidence를 현재 revision의 통과로 재사용하지 않음 |

측정값은 **추가 사용자 지시 수·결정 질문 수·도구 호출/비용·작업 완료 여부·잘못된 범위 확장·요구별 검증 공백·인계 재개 가능성**입니다. 낮은 질문 수만으로 성공이라고 하지 않습니다.

특히 **목표 정렬 평가는 에이전트 자신이 만든 스펙이나 체크리스트로 자기 채점하지 않습니다.** 사전에 별도로 정한 사용자 의도·기존 계약·독립 리뷰 기준과 결과를 대조하고, 정상·충돌·위임 사례를 모두 포함합니다. 실제 챗봇 런타임을 실행하지 않은 문서 리뷰와 CI green은 이 워크플로우의 behavioral evidence가 아닙니다.

### MVP의 검증 한계

`PR to Ready`는 **기존 작업을 받아 반복 지시를 줄이는 실행**을 검증하는 데 적합하지만, 처음부터 요구사항이 없는 제품 기획 전체를 증명하지는 못합니다. 위임된 목표 구체화는 위 표의 모호한 PR 사례로 먼저 확인하고, 충분하지 않으면 **후속 평가 범위를 확대**합니다. 신규 `Issue to PR`이나 무제한 자율 기획을 이 MVP에 섞지 않습니다.

## 대안과 남겨 둔 경계

- **상시 챗봇 지침에 모든 개발 절차 넣기:** 긴 부팅 컨텍스트와 canonical 정책 중복을 만듭니다. 필요한 레시피만 선택적으로 로드합니다.
- **별도 RPI·목표 수립 오케스트레이터 구축:** 이미 존재하는 `mols-loops`의 Goal/Scope/Research/Review와 충돌합니다. 챗봇 전용 접점만 추가합니다.
- **CI에서 LLM을 실행하는 원격 에이전트 도입:** 별도 실행 비용·권한·운영 부담이 생깁니다. 필요가 관측되기 전에는 보류합니다.
- **새 상태 DB·스펙 프레임워크·자동 merge:** 기존 PR/Issue와 repo 정책으로 부족하다는 증거가 생길 때만 재검토합니다.

실행 자산을 구현할 때는 먼저 **선택적 호출·도구 제약·위임 경계**를 확인하고, 동일 조건의 수동 다단계 지시와 비교합니다. 스펙/테스트/CI 전체 계약을 복제하거나, 챗봇 capability가 없는 환경에 지원하지 않는 기능을 약속해서는 안 됩니다.

## 참고한 방식

- [GitHub Spec Kit](https://github.com/github/spec-kit/blob/main/docs/quickstart.md): specify·clarify·plan·tasks·implement·converge와 스펙 정합성 검증을 **선택적 사고 과정**으로 참고. CLI·scaffold 강제하지 않음.
- [OpenSpec](https://openspec.dev/docs/quickstart): explore·propose·review·apply의 상호작용과 변경 중심 스펙 작성 참고.
- [Matt Pocock의 Grill Me](https://github.com/mattpocock/skills/blob/main/docs/productivity/grill-me.md): 미정인 의사결정의 선행 관계를 찾는 질문 방식 참고. 원본은 독립적인 질문 세션으로, 이 제안의 적응 방식과 동일한 실행을 주장하지 않음.

이 문서는 **연구·설계 제안**입니다. 구현 여부와 구현 범위는 별도 검증 및 리뷰에서 결정합니다.
