# Chatbot Development Workflow 제안

> 상태: 제안 / 검토 대상 — 구현 또는 정책 확정이 아닙니다.

## 제안 요약

**불완전한 요청을 사람과 함께 구체화하거나, 그 구체화 작업 자체를 에이전트에 위임할 수 있는 목표 지향적 개발 흐름을 제안합니다.** 초기 아이디어에서 목표·지시·완료 조건을 다듬은 뒤 기존 `mols-loops`와 GitHub 도구·CI로 실행 및 검증을 이어갑니다. 첫 검증 대상은 `PR to Ready`입니다.

새 레시피는 **참여·위임 방식 선택, 실행 가능성 확인, GitHub 피드백 연계, 재개 경계**만 연결합니다. 요구사항 조사·토론·스펙·테스트·RPI의 내부 방법론, 저장소 정책, CI 판정과 권한은 기존 정본이나 적합한 외부 방법론이 소유합니다.

**결정 요청:** 아래의 MVP 범위와 성공 기준에 합의한 후 작은 챗봇 전용 실행 자산으로 시범 구현합니다. 이 문서만으로 실행 지침을 활성화하거나 자동 병합을 허가하지 않습니다.

## 해결할 문제와 전제

로컬 에이전트와 달리 이 제안의 챗봇은 작업 디렉터리, 터미널, 로컬 테스트 실행을 **전제할 수 없습니다**. GitHub Plugin/connector 수준에서 저장소를 읽고 원격 변경을 제안하며, 실행 가능한 검증은 주로 GitHub Actions가 제공합니다. 제품마다 도구의 종류와 쓰기 권한은 다릅니다.

현재 사용 경험의 문제는 단계별 지시를 반복한다는 점입니다.

```text
"PR 검토해" → "개선해" → "CI 확인해" → "실패 고쳐" → "다시 리뷰해"
```

문제는 실행 단계에만 있지 않습니다. “좋게 개선해”, “완성해”처럼 **목표·지시·완료 조건이 아직 불명확한 상태**에서도 사용자가 모든 판단을 대신 내려 주거나, 반대로 챗봇이 근거 없이 요구를 확정하는 일이 발생합니다. 목표는 무조건 질문하거나 장문 프롬프트로 절차를 고정하는 것이 아니라 **필요할 때만 질문·조사·토론하고, 위임받은 판단은 높은 품질로 스스로 수행한 뒤 증거를 기준으로 다음 행동을 선택**하는 것입니다.

## 목표와 완료 조건 구체화

사용자의 최초 요청은 **이미 충분히 명확할 수도 있고, 함께 구체화해야 할 출발점일 수도 있습니다.** 명시적인 목표·제약·완료 조건을 우선 보존하며, 미정인 부분만 구체화합니다. 사람의 가치 판단과 repository에서 확인할 수 있는 사실을 같은 질문으로 취급하지 않습니다.

### 참여와 위임의 연속선

| 방식 | 사람의 역할 | 에이전트의 책임 |
| --- | --- | --- |
| **협업형** | 중요한 선택을 함께 결정하고 질문·토론에 응답 | 결정의 분기와 의존관계를 찾고, 근거·대안·권고를 제시하며 대화로 명확화 |
| **간소화형** | 소수의 결과를 바꾸는 선택만 결정 | 코드·문서·기존 스펙을 먼저 조사하고 저위험·가역적인 세부사항은 추천안으로 압축 |
| **위임형** | 목적, 명시한 금지 조건, 부여한 권한을 정하고 필요한 경계에서만 개입 | 목적에 맞는 스펙·검증 기준·대안을 스스로 구체화하고 근거와 한계를 기록하며 실행 |

이는 별도 필수 `mode` 파라미터가 아니라 요청의 의도에서 판단하는 **참여 수준**입니다. 사용자는 진행 중 언제든 “질문하며 정하자”, “권장안으로 정리해”, “이 범위는 네가 판단해”라고 조정할 수 있습니다. 이미 충분한 요청에는 구체화 절차를 강제하지 않습니다.

**위임은 판단 노동의 위임이지 목표·권한·승인의 무제한 이전이 아닙니다.** 명시된 제약과 사용자 결정은 임의로 재정의하지 않습니다. 결과를 바꾸는 사업적 선호, 충돌하는 요구, 비가역적·고위험 선택, 범위 확대 또는 승인이 필요한 조작은 질문하거나 작업을 멈춥니다. 반면 저장소에서 조사할 수 있는 사실이나 안전하고 가역적인 세부사항은 사용자에게 되묻지 않습니다.

### 구체화의 품질 기준

중요한 미정 사항에만 다음 방법을 선택적으로 조합합니다. 각 방법은 **이름을 채우기 위한 단계가 아니라 실제 결정을 개선하는 수단**입니다.

| 방법 | 쓰는 경우 | 구체화에 기여하는 증거 |
| --- | --- | --- |
| **Grill Me식 질문** | 의도·우선순위·전제·예외가 모호함 | 결정 트리의 아직 열린 분기를 질문하고, 질문마다 추천안 및 이유를 제시; 코드에서 답할 수 있으면 조사 우선 |
| **조사** | 현재 동작, 제약, 관례, 대안의 사실관계가 불명확 | repository/PR/문서/외부 근거로 사실·추론·미확인을 구분 |
| **토론·반증** | 설계 선택이 경합하거나 중요한 가정이 취약함 | 경쟁 대안의 장단점·반례·기각 이유; 합의를 꾸미지 않고 미해결을 보존 |
| **스펙** | 구현 전에 기대 동작과 범위를 고정할 가치가 있음 | why/what, 명시적 비목표, 정상·실패·경계 조건, 관측 가능한 완료 기준 |
| **테스트 설계** | 완료 조건을 실행 가능한 동작 증거로 연결 가능 | 요구별 성공·실패 사례 및 예상 결과; 테스트로 입증할 수 없는 조건도 명시 |

질문의 목적은 사용자를 심문하는 것이 아니라 **결정 품질을 높이는 것**입니다. 선택의 선행 조건이 정해지지 않았다면 후속 질문을 서두르지 않습니다. 사용자가 모르겠다고 답하면 근거 조사, 실험, 작은 프로토타입이나 명시적 보류로 처리합니다. 질문 횟수·문서 수를 목표로 삼지 않습니다.

### 위임받았을 때의 판단 계약

위임형 실행에서는 에이전트가 질문을 단순히 생략해서는 안 됩니다. 내부적으로 필요한 만큼 조사·대안 비교·반증을 수행한 뒤 다음을 충족해야 합니다.

1. **목표 정렬:** 사용자의 의도를 가장 잘 설명하는 목표와 out-of-scope를 도출합니다. 사용자 확정 사항과 에이전트의 가정을 구분합니다.
2. **실행 가능한 정의:** 중요한 동작에 대해 관측 가능한 완료 조건을 만들고, 기존 스펙/테스트가 있는 경우 그것과의 변경점을 확인합니다.
3. **독립적인 반증 시도:** 선택한 방향이 실패할 반례, 회귀, 더 단순한 대안을 검토합니다. 같은 모델의 역할 분리 검토를 독립된 검증이라고 주장하지 않습니다.
4. **근거에 비례한 결정:** 조사로 해결할 수 있는 질문은 해결하고, 합리적 기본값은 제한된 범위에서 채택하되 불확실성·영향을 기록합니다.
5. **중요한 경계에서만 사람 호출:** 목적이 충돌하거나 사용자 선호 없이는 결정할 수 없는 선택, 승인이 필요한 조작, 무허가 범위 확장은 임의로 결정하지 않습니다.

결과적으로 필요한 것은 정형화된 긴 PRD가 아니라, 다음 실행이 **무엇을 왜 만들며 무엇이 충족되면 끝나는지** 판단할 수 있는 가장 작은 산출물입니다. 간단한 변경은 PR 또는 Issue의 짧은 acceptance로 충분하고, 복잡한 변경만 별도 스펙·계획을 둡니다.

### 스펙·테스트·CI를 연결하는 방법

```text
목표·제약·완료 조건 구체화 (협업 / 간소화 / 위임)
        ↓
필요한 만큼의 스펙·계획·테스트 시나리오
        ↓
mols-loops: Research → Plan → Work → Review
        ↓
변경된 코드/문서 ↔ 스펙 ↔ 예상 동작/테스트
        ↓
GitHub CI 관측 → 실패 원인·검증 공백·요구 변경 구분
        ↳ 가정이나 스펙이 틀렸으면 적절한 선행 단계부터 재검토
        ↓
완료 근거 / 필요한 질문 / 인계
```

**스펙은 무엇을 만족해야 하는지**, **테스트는 해당 동작이 성립하는지**, **CI는 특정 ref의 검증이 실제 수행됐는지**를 각각 보여줍니다. 이 셋은 대체 관계가 아닙니다. 에이전트가 직접 만든 스펙과 테스트가 서로 일치한다는 사실만으로 원래 사용자 목표까지 올바르게 해석했다는 증거가 되지는 않습니다. 검증 가능한 결과·반례·실제 변경 diff에 다시 연결해야 합니다.

기존 `mols-loops`의 Prepare에서는 초기 목적, 권한, 유의미한 미정 사항과 진행 가능성을 확인합니다. **실질적인 도메인 조사·토론·스펙 정제는 RPI의 Research/Plan 및 Review가 맡으며**, 그 결과 Goal/Scope/acceptance 변경이 필요하면 기존 Scope Control을 따릅니다. 새로운 선행 오케스트레이터나 필수 단계 게이트는 만들지 않습니다.

### 참고한 방법론과 채택 범위

- [GitHub Spec Kit](https://github.com/github/spec-kit/blob/main/docs/quickstart.md): `specify → clarify → plan → tasks → implement → converge`의 요구 명확화·산출물 정합성·완료 수렴 사고를 참고합니다. CLI와 전체 scaffold가 필수는 아닙니다.
- [OpenSpec](https://openspec.dev/docs/quickstart): `explore → propose → review → apply`와 변경 단위 스펙, 재개 가능한 artifact 연결을 참고합니다. OpenSpec을 모든 저장소에 강제하지 않습니다.
- [Matt Pocock의 Grill Me](https://github.com/mattpocock/skills/blob/main/docs/productivity/grill-me.md): 아직 정해지지 않은 결정 분기를 탐색하고 선행 결정의 의존성을 해결하는 질문 방식을 참고합니다. 긴 인터뷰를 기본 요구로 만들지 않습니다.
- 기존 [mols-dialectic](../../src/rulesync/.rulesync/skills/mols-dialectic/SKILL.md): 사용자가 구조화된 정반합 토론을 원하거나 실제 경합하는 중대한 선택에 필요할 때만 사용합니다. 리뷰나 일반 질문에 무조건 호출하지 않습니다.
- 기존 [Testing](../../docs/development/testing.md), [Evaluation](../../docs/development/evaluation.md), [CI](../../docs/development/ci.md): 증거 유형과 검증의 한계를 그대로 따릅니다.

이 방법론들은 **선택 가능한 도구와 사고 방식**이지 이 제안서가 새로 소유할 vendor-independent 강제 스키마가 아닙니다.

## 기존 기반과 책임

| 영역 | 재사용할 정본 | 이번 제안의 경계 |
| --- | --- | --- |
| 챗봇 진입·라우팅 | [CHATBOT.md](../../CHATBOT.md), [repository route](../../.agents/route/ROUTE.md) | 새로운 정책 진입점이나 전체 자산 복제는 만들지 않음 |
| 실행 반복 | [mols-loops](../../src/rulesync/.rulesync/skills/mols-loops/SKILL.md) | Prepare/RPI/Review/Finalize, Scope와 종료 상태는 그대로 활용 |
| GitHub 대상 탐색 | [github-context](../../src/rulesync/.rulesync/skills/github-context/SKILL.md) | 최신 ref, 적용 지침, 권한과 도구 범위를 실행 전에 확인 |
| 브랜치·PR·승인 | [VCS](../../docs/development/vcs-git.md), [GitHub](../../docs/development/github.md) | 브랜치/PR/merge 정책을 재정의하지 않음 |
| 원격 검증 | [CI](../../docs/development/ci.md), [Branch Check](../../.github/workflows/branch-check.yml), [PR Gate](../../.github/workflows/pr-gate.yml) | CI 결과를 소비하며 테스트 실행이나 성공을 추측하지 않음 |
| 중단·재개 | [Durable Progress Handoff](../../catalog/patterns/workflow/durable-progress-handoff.md), [Artifact Inbox](../../catalog/patterns/workflow/artifact-inbox.md) | 이미 있는 PR/Issue/artifact를 우선 사용 |
| 챗봇 전용 차이 | [Chatbot Asset Surface](../../catalog/patterns/context-engineering/chatbot-asset-directory.md) | 필요한 delta만 향후 실행 자산으로 분리 |

이 저장소의 현재 `Branch Check`는 `main` 이외의 push에, `PR Gate`는 `main` 대상 PR 이벤트에 연결되어 있습니다. 이 두 workflow는 **검증 근거를 생산**하며 자동으로 원본을 수정하거나 LLM 개발 작업을 이어 실행하지 않습니다.

## 제안하는 실행 모델

```text
사용자의 목적·지시 (명확하거나 미정)
  → bootstrap / github-context
  → 필요시 질문·조사·토론 / 위임 판단으로 목표·완료 조건 구체화
  → 현재 작업과 사용 가능한 capability 확인
  → 기존 mols-loops의 Run
      → 필요한 GitHub read/write
      → branch/PR 이벤트에 따른 서버 측 CI
      → check·diff·review evidence 확인
      → 검증된 결함만 수정, 필요한 단계부터 반복
  → COMPLETE / HANDOFF / BLOCKED
```

### 1. 목표 지향적 호출

완료 조건이 미정이면 위의 참여·위임 방식에 따라 먼저 구체화하며, 사용자가 작업 결과를 명확히 요청하면 해당 결과까지 수행하는 것을 기본으로 합니다. 예를 들어 “PR #N을 머지 가능하게 개선해”는 리뷰 한 번이나 수정 한 번으로 끝내지 않고, 목표 범위에서 필요한 수정과 검증까지 포함합니다.

이는 **반복 지시를 생략**하는 의미이지, 명시되지 않은 범위 확장이나 위험한 side effect를 승인하는 의미가 아닙니다. 새로운 연구·구현·리뷰 방법론을 추가하지 않고 `mols-loops`와 task-specific 자산을 조합합니다.

### 2. Capability와 Authority를 분리

시작할 때 대상 저장소/PR/ref와 **현재 실제 사용 가능한** GitHub read, file write, branch/PR mutation, check/log read, rerun 기능을 확인합니다. 지원 여부가 확인되지 않은 조작은 가능하다고 가정하지 않습니다.

- 도구가 허용하고 승인된 조작만 실행합니다.
- tool 성공, commit 생성, 테스트 성공, PR 승인과 merge 가능 상태를 구분합니다.
- 플랫폼이 강제하는 승인, 권한과 Ruleset을 프롬프트로 우회하지 않습니다.
- 자동 merge는 이 MVP의 범위가 아닙니다.

### 3. GitHub를 실행·검증 접점으로 활용

챗봇은 파일 편집이나 PR 갱신과 같은 GitHub 변경을 수행할 수 있지만 로컬 커맨드 실행을 전제하지 않습니다. GitHub Actions가 체크를 제공하면 **해당 commit/ref 및 PR merge candidate에 대응하는 결과**를 읽고 실패를 분류합니다.

- source/edit 문제: 수정할 수 있으면 좁은 범위로 고치고 다시 검증합니다.
- 일시적인 CI 문제: 근거가 있을 때만 적절한 재실행을 검토합니다.
- generator·formatter처럼 실행 환경이 필요한 문제: 저장소의 공식 복구 경로를 확인합니다. 해당 경로를 호출할 capability가 없으면 임의 수작업으로 동일성을 주장하지 않고 `BLOCKED` 또는 `HANDOFF`로 남깁니다.
- 체크가 미실행/진행 중/조회 불가: `PASS`로 보고하지 않습니다.

현재 대화에서 도구 호출을 계속할 수 있을 때만 확인·개선 루프를 진행합니다. **별도 스케줄러 없이 백그라운드 실행, 세션 종료 후 자동 재개, CI 완료 시 자동 기상을 약속하지 않습니다.**

### 4. 최소 상태로 재개

중단 시 새로운 상태 파일을 무조건 만들지 않습니다. 기존 PR/Issue, 작업 문서 또는 인계 surface가 있다면 그곳에 **다음 실행을 위해 다시 계산하기 비싼 정보만** 남깁니다.

- 목표, Active Scope, 완료·남은 작업과 최신 branch/commit/PR 기준점
- 확인한 검증 근거와 아직 확인하지 못한 조건
- 반복하면 안 되는 실패 시도, blocker, 다음 전환점

재개 때에는 기록된 기준점과 GitHub의 **현재** 상태를 비교한 뒤 유효한 판단만 재사용합니다. 전체 대화, tool 로그, canonical 정책을 복제하지 않습니다.

## MVP: PR to Ready

**입력 예:** “PR #N을 머지 가능한 수준으로 개선해. 필요한 판단은 네가 해.” 또는 “완료 조건부터 함께 정하자.”

**목표:** 현재 PR을 검토 가능한 품질과 검증 근거까지 끌어올리고, 리뷰어가 남은 승인 판단을 할 수 있게 합니다. GitHub의 실제 mergeability 및 required approval까지 챗봇이 보증한다는 의미는 아닙니다.

실행 흐름:

1. 대상 PR의 base/head SHA, diff, 적용되는 저장소 지침, 기존 스펙·테스트·리뷰·checks를 확인합니다.
2. 참여 수준에 맞춰 “무엇이 완료인가”를 구체화합니다. 사람에게 물어야 할 결정과 조사·위임 판단으로 해결할 부분을 구분합니다.
3. 요구 대비 스펙·테스트·구현·검증의 gap을 파악하고, 중요한 가정과 결정은 반례로 확인합니다.
4. 수정이 필요하고 가능한 경우 승인된 PR head 범위 안에서만 변경합니다. 해당 revision의 CI·리뷰 근거를 확인하고 필요한 선행 단계부터 재작업합니다.
5. 목표 충족 시 완료 기준별 근거와 잔여 위험을 요약하고 종료합니다. 확인 불가능한 조건이나 사용자 결정이 남으면 구체적인 질문과 재개점을 남깁니다.

`COMPLETE`는 **이 Run에 요청된 준비 작업의 완료**만 뜻합니다. 플랫폼의 merge authorization이나 사람의 최종 승인이 아닙니다. `HANDOFF`는 실행/시간/반복 경계에 이르렀지만 이어갈 수 있는 작업이 남은 경우, `BLOCKED`는 필요한 권한·도구·승인·검증 근거 없이는 신뢰할 수 있는 다음 행동이 불가능한 경우를 구분합니다. 종료 semantics 자체는 `mols-loops`가 소유합니다.

## 검증할 가설과 성공 기준

첫 시범에서는 자동화 범위를 넓히기 전에 **동일 과업을 기존의 여러 사용자 지시 방식과 비교**합니다. 정량값은 지금 추측하지 않고 시험에서 기록합니다.

| 가설 | 확인 방법 |
| --- | --- |
| 반복 프롬프트 감소 | 완료 또는 정직한 인계까지 추가로 필요한 사용자 작업 지시 횟수 |
| 목표 정렬 | 최초 의도와 도출된 스펙·완료 조건의 정합성, 누락·임의 확정 여부 검토 |
| 위임 품질 | 대안·반례·가정·남은 결정의 근거, 필요 없는 질문 회피와 꼭 필요한 escalation 여부 |
| 작업 품질 유지 | 완료 조건별 스펙·테스트·diff·CI·리뷰의 근거 수준과 실제 수정 결과 대조 |
| 실행 가능성 | 로컬 터미널 없이 지원되는 GitHub 도구만으로 완료 가능한 단계 기록 |
| 재개 비용 감소 | 새 세션에서 기준점 검증 후 다음 행동을 식별하는 도구 호출/컨텍스트 비용 |
| 통제 경계 준수 | 미승인 merge·scope 확대·수행하지 않은 검증의 PASS 주장 없음 |

필수 시나리오는 **명확한 요청(불필요한 질문 없음)**, **모호한 요청(협업 질문)**, **모호하지만 위임된 요청(자율 정제와 검증)**, **서로 충돌하는 목표(사람의 결정 필요)**, **정상 PR**, **수정 후 CI 실패**, **지원하지 않는 생성 작업**, **세션 중단 후 다른 revision으로 재개**를 포함합니다. CI가 늦거나 도구에서 조회되지 않는 경우도 `HANDOFF/BLOCKED`와 잘못된 성공 주장 여부를 검사합니다. 관측된 결과와 모델의 설명을 분리하고, 가능하면 같은 조건에서 반복해 비교합니다.

## 대안과 채택 이유

| 대안 | 판단 |
| --- | --- |
| 상시 프로젝트 지침에 모든 개발 절차 추가 | 부팅 컨텍스트 비용과 정책 중복 증가. 좁은 routing + 선택적 레시피 우선 |
| 새 RPI 또는 별도의 챗봇 오케스트레이터 작성 | `mols-loops`와 역할 중복. 실행 접점만 보완 |
| GitHub Actions 내부에서 LLM 에이전트 상시 실행 | 별도 모델 실행 비용·권한·운영 부담 발생. 필요해질 때 별도 선택 |
| GitHub CI를 챗봇 전용으로 복제 | 검증 계약 drift 유발. 기존 branch/PR gate 재사용 |

## 구현 순서와 보류 범위

1. **목표 구체화와 실행 레시피 시범 구현:** 챗봇 전용 자산 위치에서 참여/간소화/위임에 따른 명확화와 `PR to Ready` 연결만 작게 시작합니다. 활성화 방식은 현재 runtime의 실제 discovery 지원을 확인해 정합니다.
2. **실제 PR로 검증:** 동일 목표를 사람이 구체화한 경우와 에이전트에 위임한 경우, 기존 다단계 지시와 비교하고 목표 정합성·결과·추가 개입·미검증 조건을 기록합니다.
3. **반복 사례가 확인될 때만 확장:** Issue to PR, CI Recovery, Review Loop, Resume 등의 별도 호출 단위가 정말 필요한지 결정합니다. 기존 자산과 겹치는 Skill을 무조건 늘리지 않습니다.

보류 사항: 독립 LLM runner, 원격 비동기 agent, vendor 공통 API 추상화 계층, 새로운 상태 데이터베이스, 자동 merge, 새 CI gate. 이런 요소가 없어서 실패하는 실제 사례가 확인되기 전에는 추가하지 않습니다.

## 주요 위험과 완화

- **프롬프트만으로 지속 실행을 기대하는 오류:** 실행 중 도구 호출과 미래 이벤트를 분리하고, 이후 재개는 최신 상태 확인으로 시작합니다.
- **근거 없이 “머지 가능”을 주장하는 오류:** CI evidence, review, GitHub mergeability, 최종 merge 승인을 구분합니다.
- **도구별 capability 차이:** 제품명이 아니라 현재 도구 결과와 권한으로 실행 분기합니다.
- **장황한 질문과 절차의 토큰·도구 비용:** 중요 결정을 바꾸는 질문·조사·토론만 선택하고, 최소 스펙/인계 상태와 의미 있는 gap에만 반복 실행합니다.
- **위임이 임의 요구 변경이 되는 오류:** 명시된 목표·제약과 추론한 기본값을 구분하고, 목표 충돌·범위 확대·고위험 결정은 사람에게 되돌립니다.
- **CI를 통제 표면 변경의 독립 검토로 오인:** 기존 GitHub 정책에 따라 사람의 승인과 독립된 근거를 유지합니다.

## 이후 결정

이 제안서의 범위를 확정한 다음, **별도의 구현 PR**에서 `PR to Ready` 실행 자산 한 개와 대표 검증 사례를 만듭니다. 이 PR 자체는 연구·설계 제안이며, 동작하는 자동화나 에이전트 런타임을 제공한다고 주장하지 않습니다.
