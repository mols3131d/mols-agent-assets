# Chatbot Harness — Execution Adaptation Guidance Design

> PR #267 작업용 설계·구현 인계 / 2026-11-02. 대상 `CHATBOT.md` 사례를 **범용 규칙으로 복제하지 않고**, 상황별 authoring 판단으로 추상화한다.

## 문제와 목표

로컬 agent harness가 요구하는 실행 책임이 챗봇의 실제 런타임에서 제공되지 않을 수 있다. 기존 `CHATBOT.md`에는 예를 들어 **제한된 코드 실행 환경에서 스크립트를 재현 가능한 범위로 실행하는 방법**, **독립 Subagent 호출이 없을 때 역할별 작업을 순차적으로 수행하는 방법**이 명시되어 있다. 이는 유효한 **대상별 호환성 사례**지만, 모든 chatbot·repository에 일률적으로 추가할 지침은 아니다.

목표는 `mols-chatbot-bootstrap`을 **하네스 작성·관리자**로 사용해 다음 결정을 내리게 하는 것이다.

1. 원본 하네스의 어떤 행동 계약(필수 도구·위임·독립성·입출력·부작용·권한·증거)이 실제 작업에 필요한가?
2. 현 런타임의 native API/tool, 파일·코드 실행, 연결 앱과 승인 범위에서 그 계약을 수행할 수 있는가?
3. 불가능할 때 **의미를 보존하는 대체**, **부분 수행**, **허용된 선택 단계 생략**, **사용자에게 필요한 정확한 인계** 중 무엇이 타당한가?
4. 사용자가 실제로 소비하는 chatbot 지침의 어느 권한 있는 surface에 최소 조건부 지침을 작성하거나 수정해야 하는가?

## 대체 실행 지침이 필요한 때

- 원본 계약이 명시한 실행 책임이 있고, 현재 타깃의 native 경로가 **실제로 부족**하고, 대체가 사용자에게 가치가 있을 때.
- 동일한 판단을 이후 작업에서도 반복할 가치가 있어 타깃의 영속 지침으로 남길 이유가 있을 때. 일회성이라면 현재 작업에서만 임시 지침/인계로 충분할 수 있다.
- 단순한 경로/라우팅 누락이라면 fallback execution이 아니라 first-hop/selection 복구가 책임이다.
- 도구가 제한됐다는 추측, 특정 제품명, 단순 편의, 실행 실패 하나만으로 범용 adapter를 설치하지 않는다.

## 행동 선택과 허용 조건

| 선택 | 허용 조건 | 사용자에게 노출해야 할 것 |
| --- | --- | --- |
| Native | 실제 경로로 원본 필수 계약을 만족 | 사용한 경로와 확인 수준 |
| 동등/충실 대체 | 입력·출력·권한·부작용·필수 독립성 등 의미 보존 가능 | 대체 메커니즘 및 남은 차이 |
| 부분 수행 | 독립적인 안전한 하위 결과가 유효하며 미수행 부분을 명확히 식별 가능 | 완료한 부분, 남은 부분, 검증 한계 |
| 생략 | 원본/사용자 목표상 **선택적 단계**이고 생략해도 필수 계약 훼손 없음 | 결과에 의미 있는 영향이 있으면 무엇을 생략했는지 |
| 인계/차단 | 필수 권한·도구·독립성·원본 접근을 재현할 수 없음 | 불가능한 이유, 남은 책임, 사용자에게 필요한 구체적 조치 |

사용자가 모르게 필수 작업을 생략하거나 성공처럼 표기하지 않는다. 대체에 사용 가능한 도구와 **해당 작업의 실행 승인**은 구분한다. 타 계정·명의 전환, 승인 없는 외부 기록, 보호된 런타임 기능 우회를 금지한다.

## 새 레퍼런스 설계

경로: `src/rulesync/.rulesync/skills/mols-chatbot-bootstrap/references/execution-adaptation.md`.

- **진입 조건:** 대상 agent harness에서 실제 필요한 실행 책임이 있으나 native runtime에서 일부가 부족할 때만 로드. 기본 부트스트랩에서는 선로딩하지 않음.
- **입력 사실:** 대상/버전, 원본 행동 정본과 필수 불변조건, 실행 환경 도구/권한, 사용자의 허용 범위.
- **핵심 단계:** 책임 식별 → capability/authority gap 판정 → 안전한 가장 작은 대안 비교 → 호환 지침 구성/배치 → 적용 및 근거 확인.
- **작성 내용:** `trigger`(언제), `source`(원본/범위), `fallback`(도구·경로·입출력), `guardrail`(권한·부작용·독립성), `failure`(부분/생략/인계), `disclosure`(보고할 한계). 이는 설명용 작성 구성 요소이며 새로운 config schema가 아니다.
- **배치:** 기능과 적용 범위를 실제로 소유하는 타깃의 보장된 instruction entrypoint/조건부 참조에 둔다. repository policy나 Skill body를 다른 문서에 복제하지 않는다. 매번 필요한 것이 아니라면 불필요한 토큰을 상주시키지 않는다.

## 사례의 올바른 일반화

**코드/CLI:** Shell/CLI가 없는 세션이어도 실제 코드 실행기가 있고 원본 script와 dependency를 확보할 수 있다면 원래 명령과 필수 의미·side effect를 확인한 뒤 최소 대체 실행을 허용할 수 있다. 불가능한 조건은 미검증/인계한다. 임의로 비슷한 Python 코드를 새로 작성해 원본 검증 성공으로 주장하지 않는다.

**Subagent:** Native 위임을 우선한다. 실행기 부재 시 원본 계약이 역할별 순차 분해를 허용하면 단일 수행자가 순차적으로 수행할 수 있다. 독립성·병렬성·격리·별도 권한이 필수면 동등하다고 주장하지 않고 해당 부분을 차단/인계한다.

**명령/외부 서비스:** 도구가 있지만 API capability/permission이 부족하면 임의 인터페이스를 발명하지 않는다. 실제 동작 가능한 범위의 읽기/초안만 수행하고, 이후 외부 조치를 누구에게 어떤 승인/도구로 맡길지 알린다.

**예약·장시간 작업:** 현재 환경이 지속 실행을 제공하지 않으면 완료 시점을 속이거나 background 수행을 약속하지 않는다. 승인된 native scheduling capability가 있다면 사용자 요구에 맞춰 사용하고, 아니면 실행 가능한 다음 단계나 handoff만 제공한다.

## 유지보수·평가 경계

- 이 레퍼런스는 **다른 챗봇 자산을 설계할 때 참고하는 작성 지침**이지 런타임에서 모든 대체를 실행하라는 명령이 아니다.
- 개별 구현 계약은 해당 로컬 하네스/asset이 소유하며, 범용 스킬이 vendor-specific 실행 규격을 소유하지 않는다.
- 설계 검토에서는 native 충분함 / 안전한 대체 가능 / 필수 독립성 불가 / 읽기만 가능 / 승인 불가 / optional step 사례를 대조한다.
- 의미 보존의 실측은 별도 runtime evidence가 필요하며 source-only 리뷰와 혼동하지 않는다.
- 정본 변경은 Skill 및 이 reference에, 유지보수 이유는 maintainer README에, 일시적인 논의는 이 inbox에만 둔다.
