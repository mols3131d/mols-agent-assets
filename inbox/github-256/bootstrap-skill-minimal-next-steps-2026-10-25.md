> 2026-10-25 · 대상: [PR #256](https://github.com/mols3131d/mols-agent-assets/pull/256) · 현재 기준 HEAD `45f6dfef3493c0e6538aa9c1bf3502f58c648e41` (계획 작성 시점).
> 이 문서는 후속 작업 범위를 제한하는 **인박스 계획**이며, 이미 수정·평가를 완료했다는 기록이 아니다.

## 결론

**새 기능을 늘리지 말고, 설계 Skill이 사용자 요청보다 많은 작업과 설정을 제안하지 않도록 최소 수정한다.** 특히 환경변수, CLI 플래그, 설정 파일, 사전 점검 항목, 테스트 조합을 선제적으로 늘리는 것을 금지한다. 필요한 안전성은 유지하되, 설계의 크기와 조사 깊이는 요청된 작업·실제 위험에 비례해야 한다.

[기존 과잉 작업 검토](bootstrap-skill-workload-review-2026-10-25.md)의 W1–W7이 근거다. 이는 현재 지침의 **과잉 작업 유도 가능성**을 정적으로 검토한 것이며, 실제 모델이 환경변수를 과다 생성했다는 측정 결과는 아니다.

## 지금 할 일 — 세 가지로 제한

1. **Skill 본문 최소 수정 (필수).** [정본 SKILL.md](../../src/rulesync/.rulesync/skills/mols-dev-env-bootstrap-design/SKILL.md)의 기존 Procedure/Handoff만 좁게 정리한다.
   - 사용자의 정확한 요청과 변경 대상부터 식별한다. 관련 없는 도구, OS, lifecycle 단계는 조사·설계하지 않는다.
   - `every managed item`을 영향받는 항목과 직접 선행조건으로 한정한다.
   - setup만 요청되면 setup만, update만 요청되면 update만 상세히 다룬다. 다른 경로는 호환성을 깨지 않을 최소 경계만 확인한다.
   - Decision Checks는 관련된 대표 실패 경로를 선택해 검토한다. 모든 항목을 의무적인 전수 테스트 목록으로 취급하지 않는다.
   - 리뷰는 findings/근거/최소 조치로 끝내고, 별도 요청 없는 구현 인계서·전체 설계서를 만들지 않는다.
2. **대표 평가만 보강 (필수).** 기존 11-case Promptfoo fixture에서 behavior 사례 **1개를 교체 또는 조정**해 '좁은 리뷰가 전체 bootstrap 설계로 번지지 않는가'를 검증한다. 해당 rubric에 **불필요한 환경변수·플래그·설정 추가 제안이 없는가**를 포함한다. 별도 evaluator, 새 runner, 대량 fixture는 만들지 않는다.
3. **검증 및 종료 (필수).** 변경된 Skill/fixture만 정적으로 점검하고 기존 평가 경로를 가능한 범위에서 재실행한다. 실행 결과와 미검증 사항을 구분한다. 기존 PR Gate/Branch Check 결과는 이전 HEAD 기준이므로 수정 후 최신 HEAD로 다시 확인한다. 통과 또는 남은 제한 사항을 요약하고 최종 리뷰한다.

## 환경변수·옵션 증식 방지 기준

**기본값은 새 환경변수·CLI 옵션·설정 키를 만들지 않는 것**이다. 환경 차이가 있다는 이유만으로 모든 도구와 플랫폼의 동작을 변수로 노출하지 않는다.

- 먼저 대상 프로젝트의 **기존 정본 설정, lock, native manager의 설정·명령·기본 동작**으로 해결 가능한지 확인한다. 외부 관리자의 옵션을 별도 bootstrap 변수로 다시 포장하지 않는다.
- 새 제어 수단은 **현재 요청을 해결하는 데 꼭 필요한 실제 차이**가 있을 때만 제안한다. 필요성은 간단히 밝힌다: 누가 소비하는가, 어떤 기본 동작이 부족한가, 기존 수단으로 왜 해결할 수 없는가, 값이 잘못되면 어떤 영향이 있는가.
- 필요한 경우에도 **가장 좁은 기존 소유자의 수단 하나**를 선택한다. 같은 설정을 환경변수·CLI 플래그·프로젝트 파일 세 곳에 동시에 노출하거나 우선순위 체계를 새로 설계하지 않는다.
- 임시 셸 변수, 프로젝트 파일, 사용자 프로필, 시스템 전역 환경, CI 비밀값은 **서로 다른 영향 범위**다. 일회성 실행 문제를 해결하려고 사용자 전역 `PATH`, 셸 프로필, 언어 런타임/프로젝트 환경 변수를 영구 변경하도록 권고하지 않는다.
- 비밀정보나 CI처럼 환경변수가 실제로 적합한 예외는 허용한다. 이때도 해당 도구의 공식 사용법과 소유 정책을 따르고 값을 출력·기록하지 않는다.
- **환경변수가 반드시 0개여야 한다는 뜻은 아니다.** 이미 필요한 native 변수까지 제거하거나 금지하지 않는다. 추가 제어 수단이 실제로 필요한 경우만 근거 있게 선택한다.

예: 'Python 프로젝트의 기존 lock 기반 setup만 검토' 요청에 Node/OS별 변수, custom bootstrap mode, 다중 config fallback, 새 `BOOTSTRAP_*` 스위치, 범용 override table을 만들어 제안하면 **실패**다. 현재 프로젝트의 Python 환경/lock/승인 경계만 검토하고 멈추면 **성공**이다.

## 이번 PR에서 하지 않을 일

- Skill 선택만으로 설치 실행, 사용자 허가 요청, 전역 환경·HOME·셸 프로필 수정.
- 새 설정 프레임워크, permission engine, OS별 환경변수 매트릭스, 래퍼 CLI, 하위 Skill/참조 문서, 독립 테스트 러너 추가.
- 지원한다고 확정하지 않은 OS·언어·도구 전수 조사 또는 모든 실패모드의 테스트 확대.
- 테스트 통과율을 높이기 위한 기존 안전 조건 삭제·rubric 약화.
- 프로젝트 전용 실행기나 `mise.toml`의 실제 환경변수·옵션 수정. 이는 [PR #258](https://github.com/mols3131d/mols-agent-assets/pull/258)의 별도 책임이다.

## 안전 조건과 종료 기준

**간소화해도 유지할 것:** 프로젝트 런타임/패키지 격리, 사전 선언 버전·lock 소유권, setup과 명시적 update의 분리, 설치 전 영향 범위 설명과 사용자 승인, 기존 상태 보존, 부분 실패의 사실 그대로의 보고. 다만 모든 요청에서 모든 세부 검사를 실행하라는 뜻은 아니다.

**완료 조건:** (1) 범위 축소 지침이 기존 Skill에 최소 변경으로 반영됨, (2) 좁은 리뷰 평가가 불필요한 설정·업무 확장을 포착함, (3) 변경 후 검증 결과와 한계가 기록됨. 근거가 충분하고 추가 작업이 판단을 바꾸지 않으면 종료한다. 새 문제는 별도 증거가 있을 때만 범위를 다시 정한다.

**PR #258에 전달할 별도 관점:** 실제 부트스트랩 코드에서 환경변수·CLI 옵션·설정 소스가 중복되거나 영구적인 사용자 전역 상태 변경이 발생하는지 구현 리뷰 때 확인한다. 이 계획을 이유로 #256에서 #258의 코드를 수정하지 않는다.
