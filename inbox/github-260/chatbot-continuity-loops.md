## Loop 1 — Research → Plan → Work → Review

### Research / 실제 결함

1. **조건부 reference 불일치**: 본문은 이벤트 중복 처리에 참조를 허용했지만 참조 첫 문장은 '같은 목표를 이어받는 경우'로 좁게 써서 독립 이벤트의 중복 쓰기 판단을 배제할 수 있었다.
2. **경합·멱등성 표현 부족**: 작업 ID 조회는 두 실행의 동시 쓰기를 막지 못한다. 직렬화/조건부 갱신 지원 여부를 확인해야 한다.
3. **중지의 두 의미 혼동**: 개별 실행에서 새 일을 하지 않는 것과 호스트의 반복 예약을 실제로 중지하는 것은 다르다.
4. **실행 모드 간 기능 차이**: 일반 대화에서 연결 앱·상태 접근이 된다는 이유만으로 예약 실행에서 접근 가능하다고 보장할 수 없다.

### Plan / 범위

기존 파일 2개를 고치고 새 스케줄러·상태 저장소·서비스별 reference를 만들지 않는다. 지침 owner는 `SKILL.md`, 조건부 실행 간 상태 판단은 `references/resumable-work.md`로 유지한다. 모델 시뮬레이션/평가 fixture는 추가하지 않는다.

### Work / 적용 내용

- 본문에서 예약 **실행 모드**의 입력·상태·쓰기 권한을 실제 확인하도록 하고, 운영 기한 이후 자동화 비활성화 또는 사용자 인계를 구분한다.
- 참조의 진입 조건을 이벤트 중복/재시도/동시 쓰기에까지 일치시켰다.
- 재조회와 멱등성·경합 방지의 차이, 결과 미확인 시 쓰기 재시도 금지, 접근 불가 상태와 외부 입력의 신뢰 경계를 명시했다.

### Review / 관점별 정적 판단

- **품질/안전**: 동시 실행을 조회만으로 통제한다고 오인할 가능성과 예약 미종료 위험을 직접 제한했다.
- **라우팅/로딩**: 단순한 독립 정기 보고에 조건부 참조를 읽게 하지 않는다.
- **효율**: 변경은 기존 두 원본에만 하고 상태 프레임워크를 신설하지 않았다.
- **증거**: 문구·경계에 대한 정적 검토이며 실제 챗봇 동작을 입증하지 않는다.

**다음 전환**: Loop 2에서 설명 중복·불필요한 세부 단계를 줄이고, 다시 구조 정합성을 확인한다.
