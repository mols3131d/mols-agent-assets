# Test Design — Goal and Guidance

이 문서는 Skill의 **유지보수 판단 근거**를 보존한다. Goal·Principles는 지향점과 선택 기준이고, Patterns·Contracts는 이를 구체화하는 방식과 적용 경계다. GPPC의 논리적 책임을 구분하되 네 개의 파일이나 고정 실행 순서를 요구하지 않는다.

실제 Agent가 따르는 동작은 `src/rulesync/.rulesync/skills/mols-test-design/SKILL.md` 및 조건부 `references/`가 소유한다. 이 문서는 그 내용을 복제하거나 새로운 런타임 권한을 부여하지 않는다.

## Goal — 목적

**중요한 사용자·시스템 계약과 실패 위험을, 신뢰할 수 있고 유지 가능한 최소 충분한 테스트 근거로 보호한다.**

성공은 테스트의 양이나 커버리지 수치가 아니라 **올바른 동작에 대한 신뢰, 중요한 결함의 발견 가능성, 요구한 산출물의 수용 여부, 독립적인 변경·검증 가능성**으로 판단한다.

## Principles — 판단 기준

- **계약 우선:** 현재 구현이나 테스트가 우연히 통과하는 방식보다 요구사항·공개 인터페이스·소비자가 관찰할 결과를 우선한다. 기준 동작이 불분명하면 기대값을 임의로 확정하지 않는다.
- **오라클과 판별력을 분리:** 정상 동작을 부당하게 거부하지 않는 것과 중요한 잘못된 동작을 검출하는 것은 서로 다른 품질 조건이다. 실행 성공, 커버리지, Mutation 점수 하나로 둘을 대체하지 않는다.
- **독립성과 통합 신뢰를 함께 보호:** 각 작업자가 다른 소유자의 비공개 구현을 몰라도 관련 테스트를 유지·실행하도록 돕되, 실제 컴포넌트 간 계약·상태·트랜잭션의 실패를 감추는 고립은 피한다.
- **위험 대비 검증 가치:** 중요한 미검증 실패를 우선하며 새 테스트와 강한 검증 기법의 **추가 판별력·수용 근거**가 실행·맥락·유지보수 비용을 정당화하는지 살핀다. 충분한 기존 검증이 있으면 새 테스트가 필요하지 않을 수 있다.
- **증거의 정직성:** 제품 결함, 잘못된 테스트 기대값, Fixture·실행 환경 문제를 구별한다. 검토·가정·미실행과 실제 관찰을 혼동하지 않는다.

이 기준은 특정 언어, 프레임워크, 테스트 수준의 고정 비율, TDD 순서 또는 여러 에이전트 사용을 보편적 정답으로 만들지 않는다.

## Patterns — 선택적인 구현 방향

다음은 반복되는 문제에 대한 **설계 선택의 근거**다. 항상 거치는 단계나 문서 출력 양식이 아니다.

| 상황 | 선택할 만한 접근 | 유지해야 할 판단 |
| --- | --- | --- |
| 테스트가 무엇을 보호해야 할지 불분명함 | 중요한 계약·수용 경로에서 출발해 오라클과 대표 반례를 도출 | 현재 코드나 기존 assertion을 요구사항 자체로 승격하지 않음 |
| 다른 컴포넌트의 내부 변경에 테스트가 자주 깨짐 | 소유 범위 내 검증과 안정된 소비자 계약 검증을 구분 | 실제 호환성·트랜잭션 검증까지 제거하지 않음 |
| 테스트 결과·기대값이 충돌하거나 실패 의미가 모호함 | 근거를 분류하고 필요한 경우에만 Oracle validation 상세 가이드를 사용 | 정상·결함 사례의 양방향 검증과 수정 책임을 구별 |
| 검증 비용이 늘지만 위험이 크게 줄지 않음 | 기존 근거 재사용, 더 작은 테스트 경계 또는 추가하지 않음 | 테스트 개수·강한 도구 사용 자체를 성과로 보지 않음 |

오라클의 심화 판단은 **특정 조건에서만 필요한 내용**이므로 별도 reference에 뒀다. 독립적 테스트 가능성은 현재 공통 원칙과 검증 사례만으로 설명할 수 있어 별도 reference로 분리하지 않았다. 파일 수보다 실제로 줄어드는 문맥 비용과 새로운 판단 가치를 기준으로 이 결정을 재검토한다.

## Contracts — 책임과 근거의 경계

- **실행 정본:** Agent에게 주입되는 판단과 선택적 loading 조건은 Skill 원본이 소유한다. 유지보수 문서는 런타임 지침의 두 번째 정본이 아니다.
- **작업 소유권:** 이 Skill은 테스트의 선정·기대값·품질·충분성 판단을 돕는다. 일반 제품 코드 구현, 모듈 아키텍처 개편, CI 병합 정책, Agent 자체의 행동 평가 체계를 대신하지 않는다.
- **이식성:** 다른 Skill·도구·저장소 설정을 암묵적인 전제 조건으로 만들지 않는다. 적용 프로젝트의 명시적인 계약은 존중하되 특정 프로젝트의 방법을 범용 규칙으로 고정하지 않는다.
- **검증 주장:** 정적 구조 검사는 실제 모델 선택·행동 개선을 증명하지 않는다. 테스트나 Eval을 실행하지 않았다면 통과했다고 기록하지 않는다. 구체적인 평가 조건과 근거는 [Evaluation](evaluation.md)에서 다룬다.

## 변경 시 판단

Goal이나 Principles가 바뀌면 Skill의 **존재 이유 또는 선택 기준**이 달라지는지 먼저 검토한다. Patterns와 Contracts를 조정할 때는 상위 목적·기준과의 정합성 및 현재 런타임 정본과의 차이를 확인한다.

새 reference·기법·문서가 정말 별도 적용 조건이나 유지보수 가치를 가지는지 확인하고, 단순한 대칭성·섹션 수·커버리지 수치를 위해 내용을 증설하지 않는다.
