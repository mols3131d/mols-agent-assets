# Test Design Goal

이 문서는 `mols-test-design`의 지속적인 목표와 유지보수 경계를 기록한다. Agent가 실제로 따르는 지침의 정본은 `src/rulesync/.rulesync/skills/mols-test-design/SKILL.md`가 소유한다.

## Goal

**중요한 observable behavior와 실패 위험을 최소한의 지속 비용으로 검증할 수 있는 테스트를 설계하거나 기존 테스트 설계를 개선한다.** 테스트 수·커버리지 수치·기법의 다양성이 아니라, 테스트가 보호하는 계약과 실패 시 제공하는 유용한 근거가 중심이다.

## Responsibility

- 변경 목표와 기존 테스트·실패 근거를 바탕으로 중요한 검증 대상, 불변식과 경계·실패 사례를 식별한다.
- Unit, integration, contract, end-to-end 등 테스트 수준은 그 이름보다 보호할 계약·관찰 가능성·비용으로 선택한다.
- 소유자가 다른 컴포넌트의 비공개 구현에 테스트가 불필요하게 결합하지 않도록, 각 작업자의 독립 변경·검증 가능성과 소비자 계약의 안정성을 함께 고려한다.
- 테스트 오라클, fixture, 격리와 mocking을 검토해 허위 성공, flaky failure, 구현 세부 결합을 줄인다.
- 기존 테스트의 중복, 검증 누락, 진단 가능성과 유지보수 부담을 판단하고 가장 작은 유효한 개선을 제안한다.
- 중요한 테스트를 실행하지 못했다면 설계 근거와 실행 근거를 구분한다.

## Boundaries

- 일반 코드의 구현·수정과 실제 테스트 실행은 작업 주체와 프로젝트 도구가 소유한다. 이 Skill은 테스트 **설계 판단**을 보조하며 코드를 자동으로 작성하거나 통과를 보증하지 않는다.
- CI trigger, 실행 위치, 병합 차단 조건, 영향 기반 CI orchestration은 CI 설계 책임이다.
- Agent Asset의 routing·behavior 성능 평가는 해당 평가 책임에 속한다. 일반 소프트웨어 테스트와 model/runtime eval을 혼동하지 않는다.
- 특정 언어, 프레임워크, 테스트 피라미드, coverage 수치, TDD 순서나 저장소 구조를 보편적인 요구로 강제하지 않는다. 물리적 분리나 모든 의존성의 mock이 실제 통합 결함을 가리지 않도록 한다.
- 다른 Skill이나 이 저장소의 파일을 런타임 의존성으로 전제하지 않는다. 프로젝트 계약이 있으면 그 범위 안에서 적용한다.

## Maintenance Criteria

완성 후 변경을 검토할 때 다음을 확인한다.

1. 독립적으로 호출해도 무엇을 어떻게 검증할지 결정할 수 있는가?
2. 테스트를 불필요하게 추가하거나 하나의 테스트 수준·도구를 강제하지 않는가?
3. 관찰 가능한 결과와 실패 원인, 테스트의 신뢰성을 우선하는가?
4. 검증 미실행, 불충분한 evidence, 외부 의존성의 한계를 분명히 드러내는가?
5. CI, 일반 코드 구현, Agent Asset 평가의 기존 소유권을 침범하지 않는가?
6. 작업자는 타인의 비공개 구현에 의존하지 않고 자기 변경을 검증할 수 있으며, 그 과정에서 실제 경계 호환성 증거를 잃지 않는가?
