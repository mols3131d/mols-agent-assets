# Software Spec Framework — Maintainer Guide

> 상태: 설계 준비. 아직 Skill 작성 원본, 스크립트, 템플릿, 설치·실행 검증이 없다. 이 문서는 실행 지침이나 확정된 파일 스키마가 아니다.

## Goal and Scope

소프트웨어 변경의 명세와 구현·검증 산출물을 추적하고, 리뷰 피드백에 따라 필요한 개발 단계로 되돌아갈 수 있는 **외부 프로젝트용 단일 Agent Skill 프레임워크**를 구상한다. CLI가 없는 ChatGPT Chat에서도 지원 가능한 작업을 수행하되, 스크립트나 독립 실행 환경의 존재를 전제하지 않는다.

- **Artifact definitions**는 산출물의 종류, 의미, 형식, 유효성 기준을 소유한다. 산출물에 생성 순서를 내장하지 않는다.
- **Workflow definitions**는 단계, 순서, 진입·종료 조건, 리뷰 결과에 따른 복귀·재실행을 소유한다. 기본 워크플로는 제공하되 소비 프로젝트의 개발 방법론 전체를 대체하지 않는다.
- **Skill runtime**은 실제 프로젝트 지침, 현재 도구·권한·상태를 확인하고 워크플로를 수행한다.
- **Bundled scripts**는 실행 가능할 때 초기화, 구조 검사, 상태 계산 등 결정적인 작업을 지원한다. 의미적 판단과 구현·리뷰 자체를 대체하지 않는다.

프레임워크는 소프트웨어 개발에 한정한다. 일반 문서 업무·연구 에이전트의 보편적 작업 엔진, 별도 CLI 서비스, 자체 계정·권한 시스템은 초기 책임이 아니다.

## Artifact and Step Ownership

| Artifact ID (working) | 대상 | 책임 |
| --- | --- | --- |
| `proposal` | 문서 | 변경 문제, 목표, 범위와 기대 결과 |
| `research` | 문서 | 사실·근거·대안·제약 및 남은 불확실성 |
| `plan` | 문서 | 접근 방식, 영향 범위, 실행·검증 계획 |
| `specification` | 문서 | 요구사항, 기대 동작, 수락 조건 |
| `test-design` | 문서 | 테스트 시나리오, 경계 조건, 추적 가능성 |
| `test-implementation` | 테스트 코드 | 검증 가능한 자동화 테스트의 구현 |
| `code-implementation` | 제품 코드 | 명세에 부합하는 실제 코드 변경 |

이 목록은 **설계상 구분**이지 파일명·디렉터리 구조·JSON/YAML 스키마가 확정되었다는 뜻은 아니다. 코드 산출물을 억지로 Markdown 문서로 복제하지 않는다. 한 단계가 여러 산출물을 읽거나 갱신할 수 있고, 하나의 산출물이 여러 단계에 재사용될 수 있다.

`review`는 기본 워크플로의 마지막 **단계**이다. 리뷰 finding과 검증 근거를 남겨야 하지만, 별도의 영구 문서 타입 또는 매번 생성되는 새 파일을 강제할지는 아직 결정하지 않았다.

## Default Workflow

기본 순서는 다음과 같다.

```text
Proposal → Research → Plan → Specification
         → Test Design → Test Implementation
         → Code Implementation → Review
```

테스트 구현이 제품 코드 구현보다 먼저 오는 **test-first 기본값**이다. 제품 코드가 아직 없는 시점의 기대된 테스트 실패를 구현 결함이나 전체 작업 실패로 오인하지 않는다. 기존 산출물을 사용할 수 있는 경우 무조건 재생성하지 않으며, 별도 워크플로에서는 순서와 선택적 단계를 변경할 수 있어야 한다.

리뷰는 실제 산출물과 검증 근거에 기초해 문제를 식별하고 원인·영향 범위를 제안한다. **전환 권한은 Workflow**에 남긴다. 올바른 복귀 지점을 선택하고, 영향받은 산출물만 수정·재검증하며, 다시 Review에 도달해야 한다. 단순히 1단계부터 반복하거나 이후 산출물 전체를 폐기하지 않는다. 해결할 수 없는 도구·권한·근거 부족은 완료로 위장하지 않고 차단·인계한다.

## Single-Skill Packaging

하나의 `SKILL.md`가 진입점이고, 필요할 때만 `references/`의 산출물·워크플로 정의 및 `assets/`의 템플릿·스키마를 로드한다. `scripts/`는 그 계약을 결정적으로 확인하거나 조작하는 내부 도구로 둔다. 별도 설치형 CLI나 여러 개의 Skill을 초기 필수 구성으로 만들지 않는다.

작성 원본의 실제 위치와 대상별 배포 방식은 구현 때 선택한다. 단일 작성 원본 원칙을 지키며 Rulesync·ChatGPT native 배포물을 중복된 정본으로 관리하지 않는다. ChatGPT Chat의 코드 실행기·GitHub 연결·Skill 리소스는 같은 파일시스템이나 인증 컨텍스트에 있다고 가정하지 않는다. 원본 스크립트를 실행하지 못했다면 해당 검사를 성공으로 보고하지 않는다.

## Maintenance and Validation

- Artifact 정의를 바꾸면 참조하는 워크플로와 템플릿·검증기의 영향 범위를 검토한다. Workflow의 순서 변경만으로 Artifact 의미를 다시 정의하지 않는다.
- Review 복귀 시 **가장 이른 영향받은 선행 조건**을 확인하고, 보존 가능한 산출물과 재검증이 필요한 산출물을 구분한다. 완료 조건을 미검증 상태에서 통과시키지 않는다.
- 프레임워크의 상태와 소비 프로젝트의 실제 코드·테스트·CI 결과를 구분한다. 정적 스키마 검사, 모델 리뷰, 테스트 실행, 실제 런타임 동작은 서로 다른 근거다.
- 외부 프로젝트의 지침·도구·권한을 우선하며, 사용자의 승인이나 연결 계정을 임의로 대체하지 않는다. 보안이나 데이터 손실 위험을 초래하는 자동 복구는 초기 기본 동작에 넣지 않는다.
- 대표 검증 사례에는 새 기능, 기존 구현 역추적, 스펙 결함으로의 복귀, 테스트 결함으로의 복귀, 테스트가 선행된 정상적 red 상태, 스크립트 부재, 읽기 전용 GitHub 연결, 새 Chat 세션에서 재개가 포함되어야 한다.

## Unresolved Design Decisions

구체적인 Artifact 파일 포맷·식별자·저장 위치, 변경 단위와 스펙의 장기 정본 관계, 리뷰 결과·무효화 상태의 기계 판독 형식, 반복 종료·인계 정책, ChatGPT 리소스 배포·실행 지원 범위는 구현 전에 검증·결정한다. 확정되지 않은 선택지를 이 문서에서 실행 계약으로 고정하지 않는다.
