# Code Pretest Optimize — Specification

## Goal

테스트·eval·벤치마크·프로파일링의 피드백을 **아직 사용할 수 없다고 가정**한 상태에서도 에이전트가 처음부터 합리적으로 효율적이고 유지보수 가능한 코드를 작성하도록 한다. 기존 코드에 대해서도 계약을 보존하는 범위에서 근거 있는 국소 개선을 선택할 수 있어야 한다.

**무검증 상태는 작업을 설계하기 위한 가정이지 후속 검증을 생략할 권한이 아니다.** 이 Skill이 끝난 뒤 수행할 테스트·eval·승인·배포는 호출자와 프로젝트 절차가 소유한다.

실제 실행 지침의 정본은 [SKILL.md](../../../src/rulesync/.rulesync/skills/mols-code-pretest-optimize/SKILL.md)이다. 이 문서는 의도·설계 결정·수용 기준을 유지보수하기 위한 명세이며 실행 프롬프트를 복제하지 않는다.

## Scope

**대상**

- **신규 구현:** 첫 구현을 시작하기 전 요구사항, 입력 규모, 데이터 흐름과 예상 비용을 고려해 합리적인 알고리즘·자료구조·디자인 패턴·I/O 형태를 선택한다. 디자인 패턴은 필요할 때만 적용한다.
- **기존 구현:** 관련 호출자·외부 계약·상태·부작용을 확인한 뒤 구조적으로 불필요한 비용을 줄이거나 현행 구현을 유지한다.
- **실행 피드백 부재:** 정적 코드·요구사항·알려진 제약을 근거로 선택한다. 실제 측정 결과가 없는 판단은 추론이나 가정으로 남긴다.

**비대상**

- 테스트·eval·벤치마크의 작성, 실행, 판정, 우회 또는 면제
- 측정 결과에 기반한 병목 진단과 성능 튜닝
- 버그 수정, 기능 변경, 아키텍처 재설계, 보안 검증
- 성능·자원 비용과 무관한 순수 가독성 또는 문체 정리
- 코드 변경이 없는데도 최적화를 의례적으로 수행하는 것

## Design Invariants

| ID | 반드시 유지할 성질 | 이유 |
| --- | --- | --- |
| I1 | 정합성, 안전성, 호환성과 사용자 계약이 성능 추정보다 우선한다. | 빠르지만 잘못된 구현을 막는다. |
| I2 | 명시된 규모·부하·제약 또는 코드 구조로부터 설명 가능한 비용만 최적화 대상으로 삼는다. | 존재하지 않는 병목과 과도한 미래 대비를 피한다. |
| I3 | 시간·공간·I/O 비용과 인지·유지보수 비용을 함께 비교한다. | 국소 수치나 Big-O 개선이 전체 퇴행이 될 수 있다. |
| I4 | 동작을 바꿀 위험이 있는 캐싱, 병렬화, 배치화, 공유 상태 변경은 계약을 정적으로 설명할 수 있을 때만 선택한다. | 실행 피드백 없는 상태의 회귀 위험을 제한한다. |
| I5 | 가장 작은 일관된 변경을 선택하며 이득이 불확실하면 단순한 기존 접근을 유지할 수 있다. | 불필요한 추상화·변경 확산을 방지한다. |
| I6 | 정적 검토는 테스트 통과, 성능 측정, 동작 동등성 증명으로 표시하지 않는다. | 증거의 강도와 결론을 일치시킨다. |
| I7 | 호출자·프로젝트의 후속 테스트, eval, 승인과 통합 게이트를 대체하거나 약화하지 않는다. | 구현 준비와 검증 의무를 분리한다. |
| I8 | 디자인 패턴은 도입 자체가 목표가 아니다. 도입·미적용·제거 모두 현재의 책임과 변경 비용, 계약 보존 가능성으로 판단한다. | 불필요한 간접 계층과 관성적 패턴 사용을 막는다. |

## Decision Model

첫 구현은 요구된 기능을 만족하는 가장 단순한 방법부터 검토한다. 실제 사용 규모에서 반복 탐색, 자료구조, 중간 객체, 외부 I/O 같은 비용이 의미를 가질 때 더 효율적인 후보와 비교한다. 자료구조를 바꿀 때는 조회 비용뿐 아니라 순서·중복·메모리 의미도 판단한다. 디자인 패턴은 반복되는 책임·변동점이 실제로 있을 때만 후보로 삼으며 직접 구현과 도입·유지·제거의 비용을 비교한다. 선택에는 예상 이득뿐 아니라 추가 상태, 오류 경로, 비용 전가, 구현 및 유지보수 부담도 포함한다.

기존 코드에 적용할 때는 '최적화가 된다'는 직관보다 **변경이 닿는 관찰 가능한 계약**을 우선 파악한다. 반환값·순서·예외·상태·부작용·직렬화·동적 참조 등 영향 가능성이 있는 경계를 한정해 비교한다. 필요한 근거가 부족하면 변경을 축소하거나 보류한다.

정적 역검토에서는 정상 경로뿐 아니라 빈 입력, 경계 조건, 오류·취소·재시도 가능성과 숨은 호출 관계 중 해당 변경에 영향을 받는 것을 검토한다. 결함을 발견했다면 최적화 명목으로 요구되지 않은 기능 수정을 섞지 않는다.

## Acceptance Scenarios

| 상황 | 기대 동작 |
| --- | --- |
| A1. 신규 기능 구현 전에 데이터 규모와 비용 제약이 주어짐 | 구현 전에 접근 방식과 구조적 비용을 비교하고, 합리적인 선택을 초기 코드에 반영한다. |
| A2. 처음부터 최적화해 달라는 요청에 입력 규모가 불명확함 | 규모를 지어내지 않고 단순한 접근을 기본으로 선택하며 중요한 가정을 드러낸다. |
| A3. 동일 결과를 반복 계산하는 기존 순수 계산 경로가 있음 | 평가 순서와 관찰 가능한 의미를 확인하고, 근거 있는 국소 변경만 제안·수행한다. |
| A4. 반복 I/O를 병렬화하면 빨라 보이지만 순서·실패 의미가 불명확함 | 개선 효과를 확정하지 않고 안전한 대안으로 축소하거나 보류한다. |
| A5. 코드 줄 수를 줄이면 복잡도와 간접 참조가 증가함 | 줄 수를 성과로 간주하지 않고 순이득이 없으면 변경하지 않는다. |
| A6. 실제 측정 수치를 요청받았지만 벤치마크를 실행하지 않음 | 수치를 만들어내지 않고 정적 추론과 미측정 상태를 구분한다. |
| A7. 테스트·eval이 이후 필수인 프로젝트에서 Skill을 사용함 | 사전 최적화만 수행하고 검증 의무·완료 판정은 기존 책임자에게 남긴다. |
| A8. 순수 디버깅·테스트 생성·측정 기반 튜닝만 요청됨 | 이 Skill의 적용 범위 밖임을 구분하고 해당 작업을 가로채지 않는다. |
| A9. 실제로 반복되는 책임과 변경 지점이 디자인 패턴으로 단순해짐 | 기존 패턴의 이름보다 책임·변경 비용을 근거로 필요한 패턴을 선택한다. |
| A10. 단일 구현에 패턴을 적용하면 클래스와 간접 계층만 증가함 | 패턴을 도입하지 않고 직접 구현을 유지한다. |
| A11. 기존 패턴의 간접 계층이 더 이상 실익이 없음 | 호출자·등록·동작 계약을 확인할 수 있을 때만 단순화하거나 제거한다. |
| A12. 조회 효율을 이유로 리스트를 집합으로 바꾸려 함 | 중복·순서·메모리 계약을 비교하고 의미가 달라지면 변경하지 않는다. |

## Completion and Evidence

작업 결과는 실행하지 않은 검증을 통과로 표기하지 않고 다음을 구분할 수 있으면 충분하다.

- **변경 또는 유지 결정:** 무엇을 최적화했고 어떤 대안을 버렸는가.
- **근거:** 계약·구조·명시된 규모에서 어떤 비용과 교환을 정적으로 판단했는가.
- **남은 불확실성:** 측정하지 않은 이득, 실행하지 않은 검증, 위험한 계약 경계 중 결과 판단을 바꿀 수 있는 것은 무엇인가.

고정 보고서나 스코어, 반복 횟수는 요구하지 않는다. 유효한 추가 개선이 없거나 위험 대비 이득이 불명확하면 변경하지 않고 종료하는 것도 정상적인 결과다.

## Maintenance Boundaries

- Skill 본문은 에이전트에게 주입할 최소 판단·실행 지침만 소유한다. 이 문서의 불변 조건과 시나리오는 변경 시 의미적 회귀를 검토하는 기준이며 런타임 참조 파일이 아니다.
- 특정 언어, 프레임워크, IDE, 서브에이전트, 다른 Skill 또는 테스트 도구에 의존하지 않는다. 실제 프로젝트 계약은 적용 시점에 확인한다.
- 이후 평가를 도입한다면 A1–A12를 후보 시나리오로 사용할 수 있지만, 이 문서에 기재한 것만으로 테스트나 eval을 수행했다고 간주하지 않는다.
