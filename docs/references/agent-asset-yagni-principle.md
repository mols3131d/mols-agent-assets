# Agent Asset YAGNI Principle

에이전트 자산에서 YAGNI의 목적은 **현재의 실제 요구보다 미래 가능성을 위해 만들어진 복잡성**을 막는 것이다.

> 관찰된 요구와 실패를 해결하는 것만 추가한다. 예상만으로 확장하지 않는다.

## Core Rules

1. **현재 요구를 근거로 추가한다.** 실제 사용자 요구, 반복되는 실패, 명확한 호환성 조건이 없는 기능은 보류한다.
2. **미래의 variant를 미리 모델링하지 않는다.** 아직 존재하지 않는 provider, workflow, output type을 위한 branch와 flag를 만들지 않는다.
3. **확장점보다 변경 용이성을 우선한다.** 필요해졌을 때 쉽게 수정할 수 있으면 지금 abstraction을 추가할 이유가 약하다.
4. **예외는 관찰된 뒤 일반화한다.** 한 번도 발생하지 않은 edge case를 위해 핵심 workflow를 복잡하게 만들지 않는다.
5. **삭제 가능한 설계를 선호한다.** 현재 요구가 사라졌을 때 쉽게 제거할 수 있는 작은 구조가 좋다.

## Evidence Test

새 규칙, 옵션, 자산, abstraction을 추가하기 전에 묻는다.

> **지금 이것을 필요로 하는 구체적인 요구나 실패 사례가 있는가?**

- 있다 → 현재 요구를 해결하는 최소 형태로 추가한다.
- 없다 → 추가하지 않는다.
- 곧 필요할 가능성만 있다 → 필요해졌을 때 추가할 수 있는지 확인하고 보류한다.

## What YAGNI Is Not

- 미래를 전혀 고려하지 말라는 뜻이 아니다.
- 안전성, 호환성, 데이터 손실 방지 같은 필수 guardrail을 미루라는 뜻이 아니다.
- 이미 확정된 요구의 다음 단계를 무시하라는 뜻이 아니다.
- 변경하기 어려운 비가역적 결정을 무계획하게 내리라는 뜻이 아니다.

핵심은 **미래를 예측해서 기능을 만드는 것**과 **미래의 변경을 막지 않는 단순한 설계**를 구분하는 것이다.

## Anti-patterns

- 지원하지 않는 도구를 위한 placeholder routing을 만든다.
- 언젠가 재사용될 수 있다는 이유로 base Skill이나 generic framework를 만든다.
- 한 종류뿐인 output에 strategy abstraction을 추가한다.
- 관찰되지 않은 edge case를 위해 다수의 예외 규칙을 추가한다.
- 실제 소비자가 없는 metadata field를 미리 정의한다.
- 현재 동작에 필요하지 않은 configuration option을 노출한다.

## Review Question

> **이 요소는 현재의 구체적인 문제를 해결하는가, 아니면 미래의 가상 문제를 대비하는가?**

후자라면 제거하거나 보류한다. 필요해진 뒤 추가하는 비용이 매우 큰 경우에만 예외를 정당화한다.
