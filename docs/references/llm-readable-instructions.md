# LLM-Readable Instructions

LLM-readable instruction의 목적은 문장을 자연스럽게 보이게 하는 것이 아니라 **의도, 조건, 우선순위, 행동을 오해 없이 복원할 수 있게 하는 것**이다.

> 한 개념은 한 용어로, 한 조건은 한 행동으로, 중요한 결정은 명시적으로 표현한다.

## Core Rules

1. **행동을 직접 쓴다.** 설명보다 `무엇을 한다 / 하지 않는다`를 명확히 적는다.
2. **같은 개념에는 같은 용어를 쓴다.** 문체 변화를 위해 유의어를 바꾸지 않는다.
3. **조건과 행동을 붙여 쓴다.** 언제 적용되는지와 무엇을 해야 하는지를 멀리 떨어뜨리지 않는다.
4. **기본값과 예외를 구분한다.** 정상 경로를 먼저 정의하고 실제로 필요한 예외만 추가한다.
5. **우선순위를 암시하지 않는다.** 충돌 가능한 지침은 어떤 규칙이 우선하는지 명시한다.
6. **모호한 대명사와 판단어를 줄인다.** `적절히`, `필요하면`, `관련된`, `이것` 대신 판단 가능한 조건을 쓴다.
7. **예시는 경계를 설명할 때만 사용한다.** 이미 명확한 규칙을 반복 설명하는 예시는 제거한다.

## Instruction Shape

가능하면 다음 형태를 사용한다.

```text
Condition → Action → Constraint or Validation
```

예:

```text
사용자가 destructive change를 요청하면 먼저 대상과 영향을 확인한다.
확인되지 않은 대상에는 변경을 적용하지 않는다.
```

다음처럼 해석을 위임하는 표현은 피한다.

```text
필요하면 적절한 안전 절차를 수행한다.
```

## Stable Vocabulary

같은 개념을 여러 표현으로 부르면 모델이 서로 다른 개념인지 판단해야 한다.

```text
권장: Rule → Rule → Rule
비권장: Rule → Policy → Guideline → Instruction
```

용어를 바꿔야 한다면 차이가 실제 의미 차이인지 먼저 확인한다.

## Ordering

지침은 일반적으로 다음 순서가 이해하기 쉽다.

1. 목적과 책임
2. 적용 조건
3. 정상 workflow 또는 핵심 행동
4. 중요한 constraint
5. 예외와 failure handling
6. validation 또는 종료 조건

모든 자산이 이 형식을 강제로 따라야 하는 것은 아니다. 순서는 **에이전트가 다음 행동을 결정하는 데 필요한 정보가 먼저 보이도록** 선택한다.

## Positive and Negative Instructions

가능하면 원하는 행동을 먼저 정의한다.

```text
변경 전에 현재 파일을 읽는다.
```

금지 자체가 중요한 guardrail이면 부정형을 명확히 유지한다.

```text
확인되지 않은 실행 결과를 성공했다고 표현하지 않는다.
```

부정형을 무조건 긍정형으로 바꾸거나 그 반대로 바꾸는 것이 목표가 아니다. **행동 경계가 가장 명확한 표현**을 사용한다.

## What LLM-Readable Is Not

- 모든 문장을 짧게 자르는 것이 아니다.
- 자연어를 schema나 pseudo-code로 전부 바꾸는 것이 아니다.
- 반복해서 강조하면 더 잘 따른다고 가정하는 것이 아니다.
- 사람에게 읽기 어려운 압축 문장을 만드는 것이 아니다.

좋은 instruction은 사람도 빠르게 읽을 수 있고 모델도 적은 추론으로 행동을 선택할 수 있어야 한다.

## Anti-patterns

- 같은 의무를 MUST, 반드시, 필수, 요구됨으로 반복한다.
- 예외가 정상 경로보다 먼저 등장한다.
- 서로 충돌하는 지침의 우선순위를 두지 않는다.
- heading과 본문이 서로 다른 용어 체계를 사용한다.
- 긴 배경 설명 속에 실제 행동 지침을 숨긴다.
- `상황에 맞게 처리한다`처럼 성공 조건을 모델에게 위임한다.

## Review Question

> **에이전트가 이 지침에서 다음 행동을 결정하기 위해 불필요한 해석이나 선택을 해야 하는가?**

그렇다면 용어, 조건, 우선순위 또는 구조를 더 명확하게 만든다.
