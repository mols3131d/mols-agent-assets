# Agent Asset DRY Principle

에이전트 자산에서 DRY의 목적은 **문장의 반복을 없애는 것**이 아니라, 같은 의미의 규칙과 지식이 여러 곳에서 독립적으로 진화하는 것을 막는 것이다.

> 하나의 의미에는 가능한 한 하나의 canonical owner를 둔다.

## Core Rules

1. **문장이 아니라 의미의 중복을 찾는다.** 표현이 달라도 같은 정책을 정의하면 중복이다.
2. **공통 지식에는 owner를 둔다.** 여러 자산이 공유하는 원칙은 가장 자연스러운 한 곳에서 정의한다.
3. **소비자는 필요한 만큼만 투영한다.** 원본 전체를 복제하지 말고 현재 자산의 행동에 필요한 최소 내용만 포함한다.
4. **동기화가 필요한 복제를 경계한다.** 한 곳을 바꾸면 다른 곳도 반드시 수정해야 한다면 canonical ownership이 잘못되었을 가능성이 높다.
5. **중복 제거를 위해 결합도를 높이지 않는다.** 작은 반복보다 숨은 dependency와 과도한 abstraction이 더 비쌀 수 있다.

## Semantic Duplication

다음은 DRY 위반 가능성이 높다.

```text
Rule A: destructive action 전에 사용자 확인이 필요하다.
Skill B: 삭제 작업 전에 반드시 확인한다.
Agent C: 파괴적 변경은 승인 후 수행한다.
```

세 문장이 같은 정책을 독립적으로 정의하고 있다면 변경 시 drift가 발생할 수 있다.

반대로 서로 독립적으로 이해되어야 하는 자산에 짧은 핵심 제약을 반복하는 것은 허용될 수 있다. 특히 runtime context가 분리되어 있다면 **self-contained behavior**가 추상적 DRY보다 우선한다.

## Ownership Test

중복이 보이면 다음 순서로 판단한다.

1. 이 내용은 하나의 정책이나 지식을 나타내는가?
2. 이를 가장 자연스럽게 소유할 자산은 무엇인가?
3. 다른 자산은 그 원본을 참조하거나 최소한으로 투영할 수 있는가?
4. 통합하면 오히려 routing, dependency, context cost가 증가하지 않는가?

마지막 질문이 `Yes`라면 중복을 일부 허용하는 편이 더 단순할 수 있다.

## What DRY Is Not

- 같은 단어가 두 번 등장하면 위반이라는 뜻이 아니다.
- 모든 공통 문장을 shared file로 이동하라는 뜻이 아니다.
- 자산의 독립성을 깨면서까지 중앙화하라는 뜻이 아니다.
- 한 번만 나타난 개념을 미래 재사용을 예상해 추상화하라는 뜻이 아니다.

## Anti-patterns

- 동일한 policy table을 여러 Rule과 Skill에 복사한다.
- 공통 문장 몇 줄을 줄이려고 새로운 router나 base asset을 만든다.
- canonical source가 무엇인지 알 수 없는 양방향 참조를 만든다.
- project-specific 규칙을 범용 Skill 내부에 복제한다.
- 서로 다른 책임을 단지 문장이 비슷하다는 이유로 합친다.

## Review Question

> **이 지식이 바뀔 때 어디를 수정해야 하는지가 하나로 명확한가?**

명확하지 않다면 ownership을 정리한다. 다만 그 해결책이 자산의 독립성과 단순성을 훼손한다면 최소한의 의도적 중복을 허용한다.
