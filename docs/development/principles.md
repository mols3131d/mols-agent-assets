# Development Principles

이 문서는 여러 구현이 요구사항과 구체 정책을 모두 만족할 때 **무엇을 우선할지** 정하는 공통 개발 원칙입니다. 더 좁은 정책이 이미 결정을 정하고 있다면 그 정책을 따릅니다.

## Decision Order

정확성, 안전, 명시적 요구사항, 호환성, 적용되는 표준과 저장소 정책은 먼저 만족해야 할 제약입니다. 이를 위반하는 선택지는 비교 대상에서 제외합니다.

남은 선택지 사이에서는 다음 순서를 기본 판단축으로 사용합니다.

**효과성 → 운영 편의성 → 단순성 → 기술적 아름다움**

기술적 아름다움을 배제하는 것은 아닙니다. 운영·유지보수 비용을 늘리지 않거나 얻는 이익이 그 비용을 분명히 상쇄할 때 선택합니다.

## Core Principles

| 원칙 | 판단 기준 |
| --- | --- |
| **정확성을 전제로 효과를 우선합니다.** | 요구사항을 올바르게 충족한 뒤 실제 효과가 큰 선택을 우선합니다. |
| **운영 편의성을 우선합니다.** | 기술적 정교함보다 배포·실행·관찰·진단·복구·변경이 쉬운 쪽을 우선합니다. |
| **최소한의 충분한 복잡성을 선택합니다.** | KISS + YAGNI. 복잡성이 필요성을 증명해야 합니다. |
| **안정된 개념만 추상화합니다.** | DRY. 반복만으로 공통화를 만들지 않습니다. |
| **책임은 변경 이유에 따라 나눕니다.** | SRP. 크기만으로 함수·파일·모듈을 분리하지 않습니다. |
| **가장 작은 coherent change를 만듭니다.** | 줄 수가 아니라 개념적 변경 범위를 최소화합니다. |
| **기존 시스템에 맞춥니다.** | 동등하게 좋은 선택이면 새로운 패턴보다 이미 정착한 좋은 방식을 우선합니다. |
| **근거에 비례해 검증합니다.** | 추측보다 관찰 가능한 계약, 실제 실패와 근거를 우선합니다. |

## Application

### Operational Convenience and Technical Elegance

필요한 동작과 제약을 모두 만족한다면 특별한 반대 근거가 없는 한 배포·실행·관찰·진단·복구·변경이 쉬운 쪽을 선택합니다. 결합도, 중복 지식, 숨은 동작과 이해·수정·검증에 드는 노력도 실제 비용으로 봅니다.

패턴의 수, 추상화 정도나 기술적 순수함 자체를 품질의 대리 지표로 사용하지 않습니다. 더 정교한 설계는 운영과 유지보수를 어렵게 만들지 않거나 그 이익이 추가 비용을 충분히 상쇄할 때 선택합니다.

### KISS and YAGNI

추상화, 설정, 확장 지점, 의존성, 자동화, 캐시, 동시성, 인프라 같은 복잡성을 미리 추가하지 않습니다. 현재 요구사항, 실제 변동성, 관찰된 문제나 명확한 계약이 필요성을 증명할 때 도입합니다.

복잡성을 추가하는 쪽이 항상 나쁜 것은 아닙니다. 반복되는 더 큰 비용을 없애거나 실제 계약을 더 안정적으로 지키는 등 얻는 효과가 추가 비용보다 클 때는 정당화됩니다.

### DRY and SRP

DRY는 단순한 반복 제거가 아니라 **함께 변경되어야 하는 안정된 지식이나 규칙의 정본을 하나로 두는 것**에 적용합니다. 공통 개념과 책임 경계가 아직 안정되지 않았다면 작은 로컬 중복이 성급한 추상화보다 낫습니다.

SRP는 함수·파일·모듈을 작게 만드는 규칙이 아닙니다. 책임, 소유 경계, 수명 주기나 변경 이유가 실제로 다를 때 분리합니다. 표면적인 중복 제거보다 책임 경계를 명확히 하는 것을 우선합니다.

### Change Scope and System Fit

가장 작은 coherent change는 줄 수가 아니라 **하나의 목적을 완결하는 최소한의 개념적 변경**을 뜻합니다. 요청 밖의 동작은 정확성, 안전, 호환성 또는 명확한 단순화를 위해 필요하지 않다면 보존하고, 관련 없는 정리나 추측에 기반한 미래 대비를 함께 넣지 않습니다.

기존 경계, 호출자, 데이터 흐름, 실패 동작, 테스트와 로컬 관례를 먼저 확인합니다. 동등하게 좋은 선택이면 이미 정착한 방식을 사용하되, 기존 방식 자체가 실제 비용이나 제약의 원인이라면 관성적으로 유지하지 않습니다.

### Verification

요구사항과 스타일 선호, 관찰된 실패와 가정한 위험, 현재 요구와 미래 가능성을 구분합니다. 변경된 관찰 가능한 계약과 중요한 실패 경로를 가장 저렴하면서 충분한 수준에서 검증합니다.

검증하지 않은 동작을 검증했다고 주장하지 않습니다.
