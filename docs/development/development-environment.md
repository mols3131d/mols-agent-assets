# Development Environment

이 문서는 **이 저장소의 개발환경 구축과 유지보수 운영 정책의 정본**입니다. 최초 setup, 반복 복구, 명시적 update 및 설치 승인 여부를 판단할 때 먼저 확인합니다. 현재 도구별 명령과 운영 방법은 [mise 안내](../references/tooling/mise.md), 도구·버전 선언은 [`mise.toml`](../../mise.toml) 및 각 native manifest/lock, 실제 동작은 [부트스트랩 스크립트](../../scripts/development_bootstrap.py)가 소유합니다.

재사용 가능한 부트스트랩 **설계 판단**은 [`mols-dev-env-bootstrap-design`](../../src/rulesync/.rulesync/skills/mols-dev-env-bootstrap-design/SKILL.md)이 다룹니다. 이 Skill은 설치 실행기나 이 저장소의 권한 정책 정본이 아닙니다. [PR #256 작업 문서](../../inbox/github-256/development-environment-bootstrap-spec.md)는 조사·논의 근거일 뿐 운영 지침을 대체하지 않습니다.

## 실행 의도와 설치 허가

- **진단·설계·코드 구현과 실제 설치는 별개입니다.** 스킬을 사용하거나 부트스트랩 코드를 구현하라는 요청만으로 사용자 컴퓨터의 도구 설치·업데이트를 실행하지 않습니다.
- **에이전트가 설치를 실행하기 전에는 사용자의 명시적 허가를 받습니다.** 어떤 도구·의존성을 왜 설치/갱신하는지, 기존 도구를 재사용할 수 있는지, 예상 설치 위치(프로젝트/사용자 공유 mise cache/호스트), lockfile 변경과 외부 설치기·설정 부작용을 필요한 수준으로 요약합니다. 허가 전에는 읽기 전용 확인과 계획 작성까지만 수행합니다.
- **도구마다 반복해서 묻지는 않습니다.** 사용자가 대상과 영향 범위를 이해하고 승인한 **하나의 설치 작업 묶음**은 그 범위 안에서 진행할 수 있습니다. 대상 도구·설치 위치·전역 영향·업데이트 범위가 실질적으로 달라지면 다시 허가받습니다. 응답이 없거나 거절하면 설치를 건너뛰고 필요한 조치만 안내합니다.
- **직접 명령을 실행하는 사용자**는 명령과 이 문서에 명시된 영향 범위를 스스로 선택한 것입니다. 현재 스크립트에는 별도의 대화형 승인 프롬프트가 없으며, **에이전트가 명령을 대신 실행할 때의 승인 확인은 호출자가 책임집니다.** 문서의 승인 지침만으로 자동 실행기에 기계적 승인 게이트가 구현되었다고 주장하지 않습니다.
- 사용자 허가는 실행 권한의 유일한 조건이 아닙니다. runtime·OS 권한과 저장소 정책도 적용되며, 사용자 승인만으로 관리자 권한 상승이나 알려지지 않은 외부 스크립트의 무제한 실행이 정당화되지는 않습니다.

## 이미 있는 도구 재사용

**기존 설치의 재사용 가능성 확인 → 선언된 계약 충족 여부 확인 → 필요한 설치 제안** 순서로 판단합니다.

- 도구가 이미 있고 프로젝트가 요구하는 **버전·실행 경로·관리 주체·잠금/재현성** 계약을 충족하면 재사용을 우선합니다. 전역에 존재한다는 이유만으로 재설치하거나 업그레이드하지 않습니다.
- 도구 관리자(mise/uv 등)가 자체적으로 관리형 설치와 캐시를 재사용한다면 그 기능을 우선 사용합니다. PATH에 같은 이름의 전역 실행 파일이 존재한다는 이유만으로 프로젝트가 선언한 관리형 pin/lock을 우회하지 않습니다.
- 기존 전역 도구의 출처·버전·호환성이 불분명하거나 프로젝트 pin과 충돌하면 **기존 설치를 변경하지 않고** 승인된 별도 관리 경로를 제안합니다. 별도 관리형 경로 역시 사용자 공유 공간일 수 있으므로 설치 전에 영향을 명시하고 허가받습니다.
- 재사용/설치를 판정한다는 이유로 범용 탐지·설치 프레임워크를 새로 만들지 않습니다. native manager의 기존 검증·설치 기능을 우선합니다.

## Setup, update 및 변경 경계

| 작업 | 버전·상태 계약 | 허가 및 변경 범위 |
| --- | --- | --- |
| 상태 점검·계획 | 기존 도구와 정책 확인; version/lock 변경 없음 | 설치 허가 없이 읽기 전용 진단 가능. 도구 자체의 사전 실행 부작용은 별도 확인 |
| `setup` / 반복 복구 | 확정된 exact pin과 잠금 결과로 맞춤; 암묵적 latest 갱신 없음 | 에이전트 실행 시 **사전 설치 허가** 필요. 승인된 mise 관리 영역과 프로젝트 `.venv`에 한정 |
| `update` | 프로젝트가 선언한 허용 범위의 최신 버전을 native resolver로 선택하고 lock diff를 검토 | 에이전트 실행 시 **업데이트·설치 허가** 필요. 버전 정책 확대·전역 변경·자동 commit 불허 |
| HOME Skill·Rulesync projection·Git hooks·호스트 도구 | core bootstrap에서 제외한 개별 integration | 별도 영향 설명과 허가 후 해당 native 경로로 실행. 기본 setup의 허가가 자동 확장되지 않음 |

현재 구현은 모든 mise CLI가 **exact pin**이고 `update`는 Python dependency의 `uv.lock`만 갱신합니다. Ruff/Biome 등 CLI의 최신 stable 갱신은 아직 구현되지 않았으며, 일반적인 최신 버전 선호와 현재 저장소의 자동 갱신 기능을 혼동하지 않습니다. 구체적인 명령·예외·검증 범위는 [mise 안내](../references/tooling/mise.md)를 따릅니다.

## 확인 및 종료 조건

- 에이전트는 설치 전에 계획과 승인 범위를 제시하고, 허가 여부를 확인한 뒤에만 설치 명령을 호출합니다. 미승인 작업은 성공으로 표시하지 않습니다.
- 설치 대상/실행 버전/위치의 재사용 여부를 확인하되 시스템 전역 도구를 조용히 교체하거나 사용자 HOME·Hook·Shell 설정을 덮어쓰지 않습니다.
- setup 반복 실행은 확정된 잠금과 정책을 유지합니다. update는 허용 범위 밖 버전으로 올리지 않으며 lock 변경을 검토 가능하게 남깁니다.
- 선행 도구가 없거나 단계가 실패하면 독립 작업은 가능한 범위에서 계속하되 필수 준비가 끝나지 않았다면 전체 `READY`로 주장하지 않습니다.
- 실제 부트스트랩 코드에는 **대화형 승인 및 기존 unmanaged 전역 바이너리 자동 선택 기능이 없습니다.** 이 정책의 에이전트 실행 승인 여부와 시스템·플랫폼별 설치 부작용 검증은 별도로 확인해야 합니다. 문서 업데이트만으로 기존 runner의 안전성 문제가 수정되지는 않습니다.

## 실행 참고

최초 요구 도구 준비, `mise run setup`/`update`, `--dry-run`, 선택적 Rulesync·Skill·hook 연동 및 OS별 미검증 사항은 [mise 설치·운영 안내](../references/tooling/mise.md)에서 확인합니다. `--dry-run`은 부트스트랩 단계의 설치를 수행하지 않는 계획 모드이지만, mise/uv 진입점의 평가·탐색까지 포함한 완전한 시스템 무변경 보증은 아닙니다.
