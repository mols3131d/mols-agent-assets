# Repository Layout

파일 구조는 **책임과 탐색 경로를 드러내는 보조 수단**입니다. 이름과 위치만 보아도 무엇이 어디에 있고 다음에 어디를 살펴볼지 대략 예측할 수 있어야 합니다.

파일 배치가 실제 책임 경계를 대신하지는 않습니다. 더 구체적인 framework·tool·generated 영역의 규칙이 있으면 그 규칙을 우선합니다.

## Placement

새 파일과 디렉터리는 가능한 한 가장 좁고 자연스러운 책임 경계에 둡니다.

- 이미 적절한 디렉터리가 있으면 재사용합니다.
- 파일과 디렉터리 이름은 그 역할이나 책임 범위를 짐작할 수 있게 합니다.
- 같은 위치에서 함께 찾는 파일은 이름 정렬에서도 자연스럽게 가까이 모이도록 공통된 이름 구조를 사용할 수 있습니다.
- 서로 관련 없는 파일이 한 디렉터리에 계속 쌓이지 않게 합니다.
- 반복되는 묶음을 분리했을 때 탐색이 실제로 쉬워지면 새 디렉터리를 만듭니다.
- `scripts/`에서 같은 도메인의 스크립트가 3개 이상이면 별도 `<domain>/` 디렉터리를 우선 고려합니다. 디렉터리 이름은 `generate`, `validate`, `sync` 같은 공통 동작보다 대상 도메인을 우선합니다.
- 둘 다 자연스러운 선택이라면 더 쉽게 찾고 이해할 수 있는 쪽을 선택합니다.

탐색성을 위해 불필요한 계층을 만들거나 대칭성만을 맞추려고 기존 구조를 일괄 재배치하지 않습니다. 변경하는 영역이나 실제 탐색 비용이 확인된 영역부터 정리합니다.

## Source and Test Alignment

source에 자연스러운 기준점이 있으면 관련 test의 위치도 예측할 수 있게 대응시킵니다.

```text
scripts/<domain>/<name>.py
               ↓
tests/scripts/<domain>/test_<name>.py
```

source 경로를 그대로 복제하는 것 자체가 목적은 아닙니다. 더 안정적인 기능·동작·test 경계가 있으면 그 경계를 우선합니다. framework의 test discovery와 import convention이 다르면 framework convention을 따릅니다.
