# Mols Autopilot Maintenance

`mols-autopilot`은 사용자가 직접 선택하는 **범용 최상위 Agent**다. 개별 작업 지시 없이도 프로젝트의 실제 목표와 마일스톤에 따라 다음 작업을 판단하고, 허용된 범위에서 실행·게시·통합까지 조정한다. 이 문서는 운영 시 필요한 설계 이유와 변경·검토 기준을 보존한다. **실행 계약의 정본은 [Agent 정의](../../../src/rulesync/.rulesync/subagents/mols-autopilot.md)**이며, 이 문서가 별도의 권한 정책이나 실행 지침을 정의하지는 않는다.

## Design decisions

| 결정 | 유지보수 이유 |
| --- | --- |
| Agent 정의와 실행 계층을 분리 | Rulesync의 `subagents/`는 자산 유형의 작성 위치다. 실제 최상위·위임 실행 가능 여부는 런타임이 소유하며, 메인 전용 자산을 위임 전용으로 해석하지 않는다. |
| 사용자 직접 선택만 활성화 | 일반 작업자가 다른 Agent를 호출하는 방식으로 광범위한 자율 실행 권한을 얻지 않게 한다. 직접 선택 또는 위임 금지를 네이티브로 강제할 수 없는 환경에서는 지침 수준의 제한임을 명시한다. |
| 하네스에 종속되되 프로젝트에는 독립 | 자산 자체에는 특정 저장소의 경로·승인 체계·워크플로를 넣지 않는다. 실행 때 대상 프로젝트의 실제 정본·Rule·Skill·검증·승인 조건을 찾아 적용한다. |
| 자율성은 작업 선택과 실행 조정 | 목적 없는 활동량을 늘리지 않는다. 가치가 부족한 일을 하지 않거나 위험·권한·의존성에 따라 범위를 좁히고 중단하는 것도 정상적인 결과다. |
| 기록은 기존 아티팩트에 남김 | 이슈·PR·작업 기록 등 프로젝트가 승인한 기록면을 갱신한다. 보조 로그나 별도 정본을 추가하면 상태 불일치·공개 위험·유지보수 비용이 증가한다. |
| 게시와 머지는 서로 다른 결정 | 구현·검증·PR 게시에 대한 위임이 필수 리뷰·보호 규칙·명시적 승인까지 대체하지 않는다. 최종 통합 가능 여부는 현재 프로젝트와 플랫폼의 실제 조건이 결정한다. |

## Boundaries to preserve

- **Authority:** 사용자 선택은 새 계정·명의·도구 권한이나 무기한 실행을 만들지 않는다. 거부된 작업은 계정·도구 전환으로 우회하지 않는다.
- **Harness ownership:** 프로젝트 지침과 전문 Skill의 절차를 메인 Agent가 재구현하지 않는다. 목표 탐색 자료와 정책 정본을 구분한다.
- **Risk and disposition:** 작업 임팩트, 되돌리기 가능성, 파급 범위와 기회비용을 고려한다. 필수 검증·승인을 `Skip`으로 처리하지 않고 `Stop`·`Handoff` 등으로 경계를 명확히 한다.
- **Progress and confidentiality:** 의미 있는 의사결정·검증·블로커·인계 상태만 기록한다. 비공개 대화, 인증 정보, 내부 지침이나 민감한 원본 로그를 공개 아티팩트에 복사하지 않는다.
- **Runtime honesty:** 정적 메타데이터·생성 성공을 사용자 선택, 비위임 제한, 권한 강제, 무인 실행 또는 실제 자동 머지의 성공으로 해석하지 않는다.

## Change and verification

1. 변경하려는 책임이 **범용 실행 계약**, 특정 프로젝트 정책, 특정 런타임 기능 중 어디에 속하는지 먼저 구분한다. 프로젝트 또는 런타임 소유 계약은 이 자산으로 복사하지 않는다.
2. [Agent 정의](../../../src/rulesync/.rulesync/subagents/mols-autopilot.md)와 해당 Rulesync/벤더의 **현재** Agent 메타데이터·호출·권한 모델을 확인한다. 새 타깃은 사용자 직접 선택형 메인 실행을 의미 있게 지원할 때만 추가한다.
3. 동작을 수정해야 하면 Agent 원본 하나를 변경한다. 설명이나 `targets` 변경은 저장소가 제공하는 정식 generator로 탐색 라우트를 재생성한다. 생성물을 독립된 정본으로 관리하지 않는다.
4. 프로젝트 하네스 준수, 권한·명의 안전, 작업 선정, 블로커 처리, 아티팩트 기록과 승인 경계의 의미를 리뷰한다. 더 적은 지침으로 동일한 실패를 막을 수 있다면 중복 절차를 제거한다.
5. 원본 frontmatter·Markdown·라우트 정합성 및 사용 가능한 Rulesync/CI 검증을 실행한다. 호출·위임 차단·실제 실행·머지의 성공 여부는 대상 런타임의 별도 행동 평가로 확인하고, 실행하지 않은 검증은 미검증으로 남긴다.

### Regression scenarios

- **목표만 있는 세션:** 구체적 요청 없이도 채택된 마일스톤에서 가치 있는 일을 선택할 수 있어야 하며, 근거가 없으면 임의의 이슈를 생성하지 않는다.
- **다른 Agent의 호출:** 위임 실행을 직접 선택으로 혼동하거나 새로운 권한을 부여하지 않는다. 네이티브 차단이 없는 런타임의 한계를 숨기지 않는다.
- **고위험 작업 또는 막힌 머지:** 필수 리뷰·승인이 없으면 해당 단계를 중단하고 유효한 작업 상태와 다음 승인 주체를 인계한다. 독립된 안전 작업만 계속할 수 있다.
- **장기 작업의 재개:** 기존 아티팩트의 revision·진행 상태·검증·블로커가 재개에 충분해야 하지만, 이전 기록을 현재 권한이나 승인으로 간주하지 않는다.
- **런타임/프로젝트 변경:** 다른 하네스·다른 계정·메인 실행을 지원하지 않는 도구로 바뀌었을 때 기존 가정을 묵시적으로 유지하지 않는다.

## Maintenance boundary

행동·활성화의 정본은 Agent 파일, 메타데이터 projection과 실제 호출 제약은 Rulesync 및 각 런타임, 프로젝트별 정책·통합 승인은 대상 프로젝트가 소유한다. 이 문서는 포터빌리티와 변경 이유만 보존한다. 자산을 다른 저장소로 옮길 때에도 이 책임 구분을 유지한다.
