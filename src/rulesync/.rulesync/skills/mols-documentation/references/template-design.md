# Template Design

재사용할 **문서 템플릿 자체**를 설계·생성·개선·검토할 때 적용한다. 이 파일은 설계 지침이지 문서 작성에 복사하는 템플릿이 아니다. 독자·목적·정보 구조·신뢰성은 상위 `SKILL.md`가 소유하며, Markdown 표현은 `markdown.md`를 따른다.

## When to Design

- 기존 프로젝트·도메인 템플릿과 적용되는 작성 계약을 먼저 확인한다. 적절한 원본이 있으면 새 템플릿보다 재사용·개선을 우선한다.
- 문서 목적과 반복되는 정보 구조가 안정적이고, 여러 문서를 같은 방식으로 작성할 가치가 있을 때만 템플릿을 만든다. 일회성 문서라면 직접 작성한다.
- 플랫폼이나 도메인이 제공하는 고유 양식, reserved field, schema와 작성 정책을 일반 템플릿 설계로 덮어쓰지 않는다.

## Design the Contract

1. 반복되는 사용 상황, 작성자와 독자, 문서가 지원할 판단·행동을 정의한다. 실제 사용 사례에서 공통으로 필요한 내용과 상황에 따라 달라지는 내용을 구분한다.
1. 유지할 구조와 채울 영역을 구분한다. 고정 구조는 필요한 heading·순서·불변 문구로 좁히고, 개별 문서의 사실·판정·수치·근거는 가변 영역에 둔다.
1. 가변 영역마다 의미, 필수 여부, 반복 가능 여부와 값이 없을 때의 처리 방식을 정한다. 선택 항목은 비어 있는 heading이나 안내 문구를 최종 문서에 남기지 않고 생략할 수 있게 한다.
1. placeholder는 문장 조각마다 쪼개지 말고 의미 있는 단위로 둔다. 대상 도구의 기존 구문과 reserved placeholder를 유지하며, 특정 템플릿 엔진을 기본 전제로 삼지 않는다.
1. 독자가 결과물을 사용하는 순서로 정보를 배치한다. 중요하지 않은 공통 섹션, 사실처럼 보이는 예시 문장, 중복 요약과 과도한 작성 지침을 제거한다.

구조를 정의하는 기존 template·schema·metadata가 있으면 해당 structural owner의 필드 의미·선택 조건·검증 계약을 따른다. 별도 spec이나 schema 파일은 템플릿 가까이에서 설명할 수 없는 계약이 실제로 있을 때만 만든다. 생성 방식과 렌더링 도구는 소비 환경의 정본이 결정한다.

## Probe and Improve

- 최소한의 정보만 있는 사용 사례와 반복·선택 항목이 많은 사례를 대상으로 템플릿을 채워 본다. 단순 템플릿이라면 더 작은 확인으로 충분하다.
- 결과 문서에서 필수 정보 누락, 근거 없는 기본 주장, 미치환 placeholder, 빈 section, 어색한 순서, 불필요한 중복을 확인한다. 실제 renderer나 generator가 있다면 그 계약에 맞는 결과도 확인한다.
- 기존 템플릿을 개선한다면 필드 이름, 고정 구조, 작성자 및 생성 도구의 소비 계약을 보존할지 먼저 판단한다. 호환되지 않는 변경은 단순 문장 개선으로 취급하지 않는다.
- 작성자가 템플릿을 이해하기 위해 장황한 별도 설명을 읽어야 하거나, 선택 조합이 지나치게 많다면 필드와 구조를 줄이거나 템플릿 분리가 실제로 필요한지 재검토한다.

## Boundary

- 이 Reference는 **템플릿 설계 방법**을 소유한다. 실제 템플릿 원본과 도메인별 필드 의미·승인·검토 절차는 해당 소유자가 정한다.
- 기존 템플릿을 채워 한 문서를 완성하는 일은 문서 작성이다. 템플릿 설계와 혼동해 원본 구조를 임의 변경하지 않는다.
- Markdown 문법과 표현 판단은 `markdown.md`, formatting·lint·frontmatter·index 같은 결정론적 유효성 검증은 `mols-markdown-maintenance`가 담당한다. 이 지침은 템플릿 렌더링 엔진이나 검증 도구를 새로 요구하지 않는다.
