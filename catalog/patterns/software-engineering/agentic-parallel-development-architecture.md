# Agentic Parallel Development Architecture

**여러 agent가 동시에 일할 수 있도록 폴더를 늘리는 대신, 한 변경을 다른 영역의 내부 구현을 거의 몰라도 이해·수정·검증할 수 있게 구조를 설계합니다.** 병렬 작업의 수보다 각 작업의 독립성과 마지막 통합 비용이 중요합니다.

이 문서는 [GPPC Guidance Stack](../context-engineering/gppc-guidance-stack.md)의 Goal·Principles·Patterns(GPP)를 따릅니다. 프로젝트의 필수 아키텍처 계약이나 agent 실행 절차를 정의하지 않고, **어떤 경계를 선택하면 더 적은 맥락과 조정으로 개발할 수 있는지**를 판단하는 재사용 패턴입니다.

## Goal

반복되는 기능 개발·수정·검토를 **응집된 변경 단위**에서 수행하고, 다른 작업이나 agent와는 필요한 접점만 공유하는 구조를 지향합니다.

좋은 결과는 병렬 agent를 많이 실행하는 것이 아니라, 작업마다 무관한 코드를 다시 읽는 비용, 공유 파일의 변경 충돌, 결과를 합친 뒤의 재작업을 줄이면서 정확성과 유지보수성을 유지하는 것입니다.

## Principles

- **변경 단위부터 생각합니다.** 디렉터리명이나 기술 계층보다 실제로 함께 바뀌는 동작·데이터·불변식을 먼저 봅니다. 독립 변경과 강한 일관성이 필요한 변경을 억지로 같은 방식으로 나누지 않습니다.
- **경계 안의 맥락은 충분히, 경계 밖의 지식은 최소화합니다.** 담당 기능을 찾고 이해하는 경로는 짧게, 다른 영역에 대한 의존은 가능한 한 공개된 접점으로 제한합니다.
- **완결된 변경과 국소 피드백을 선호합니다.** 기능을 만들고 관련 테스트로 확인할 수 있는 단위가 유리합니다. 전체 통합 검증이 필요한 문제까지 국소 테스트만으로 끝낼 수 있다는 뜻은 아닙니다.
- **총비용을 비교합니다.** 새 모듈·인터페이스·문서·검증 규칙을 유지하는 비용이 병렬성과 탐색성의 이득보다 크면 기존의 단순한 구조를 선택합니다.
- **기존 생태계의 경계를 활용합니다.** 언어·프레임워크의 module/package·test 규약이 이미 필요한 독립성을 제공하면 agent 전용 구조를 덧씌우지 않습니다.

## Patterns

### 1. 변경 시나리오로 경계 발견하기

현재 구조가 아니라 **실제로 맡길 수 있는 작업**에서 시작합니다. 예를 들어 '요금 정책 수정', '배송사 연동 변경', '주문 상태 규칙 변경'을 각각 수행한다고 가정합니다.

1. 각 작업이 읽고 수정할 동작·데이터·테스트·외부 효과를 추적합니다.
2. **같은 이유로 함께 바뀌는 것**을 모으고, 무관한 변경의 내부 구현을 얼마나 함께 알아야 하는지 확인합니다.
3. 다른 영역의 구현 대신 호출·이벤트·스키마 등 **작고 안정적인 접점**으로 연결할 수 있는지 봅니다.
4. 두 작업을 동시에 한다고 가정해 공유 파일·DB schema·설정·생성물의 충돌을 찾습니다.
5. 그 경계에서 기능을 구현하고 의미 있는 피드백을 얻을 수 있는지 확인한 뒤, 변경 비용이 줄어드는 가장 단순한 구성을 택합니다.

이때 '서로 다른 작업이 같은 파일을 자주 건드린다'는 현상은 **조사 신호**이지 자동 분리 규칙이 아닙니다. 함께 수정해야 할 하나의 불변식 때문일 수도 있고, 변경 이력의 작업 묶음 방식 때문일 수도 있습니다.

### 2. 큰 구조는 기능·도메인 경계를 우선 비교하기

반복적인 개발 작업이 기능이나 비즈니스 역량 단위라면, **큰 경계를 feature/domain으로 나누고 필요한 내부 계층만 두는 방식**을 우선 비교할 만합니다. 모든 프로젝트에 적용되는 유일한 기본 구조는 아닙니다.

| 구조 후보 | 선택하기 좋은 상황 | 주의할 비용 |
| --- | --- | --- |
| **Domain / capability** | 책임지는 규칙·데이터·변경 사유가 구분됨 | 도메인 간 무분별한 데이터 접근, 중복된 불변식 |
| **Feature / vertical slice** | 사용자 기능 하나를 끝까지 변경·확인함 | 기능마다 동일한 정책·모델이 분산됨 |
| **Layer / technical concern** | 시스템이 작거나 프레임워크가 이 구조를 자연스럽게 요구함 | 기능마다 여러 계층을 가로질러 공동 수정 |
| **Component / package** | 안정된 재사용 경계나 독립적인 배포·운영 요구가 있음 | 과도한 인터페이스와 패키지 관리 |

예를 들어 요청별로 API·서비스·저장소 계층을 모두 수정해야 한다면, 계층을 없애는 대신 **기능 경계 안에 그 계층을 배치**하는 선택을 비교합니다. 필요한 독립성은 하나의 프로세스에서도 확보할 수 있으므로 microservice 분리는 별도의 운영 판단입니다.

### 3. 작업에 가까운 코드·검증·맥락 묶기

아래는 도메인별 변경 지점을 찾기 쉬운 한 가지 예입니다. `src/`와 `tests/`는 자산 유형, `billing/`과 `shipping/`은 책임 경계를 표현합니다.

```text
src/
  billing/             # 가격 규칙과 공개 접점
  shipping/            # 배송 정책과 공개 접점
tests/
  billing/             # 요금 변경 피드백
  shipping/            # 배송 변경 피드백
  integration/          # 경계를 가로지르는 동작
```

이 구조에서 한 agent는 `billing`의 계산과 테스트를, 다른 agent는 `shipping`의 연동과 테스트를 주로 다룰 수 있습니다. **같은 주문 상태 schema를 둘 다 바꿔야 한다면 두 폴더가 독립적이라는 이유로 병렬 변경을 강행하지 않습니다.** 그 schema의 소유 경계와 전환 방법을 먼저 확인합니다.

테스트를 source 옆에 두는 언어도 있고, `tests/`에 분리하는 환경도 있습니다. 접근 가능한 공개 API·타입·동작 예시·관련 테스트가 있다면 별도 설명 문서를 추가하지 않아도 될 수 있습니다. 실제 파일 배치와 탐색성은 [Filesystem-Legible Structure](filesystem-legible-structure.md), 테스트 배치는 [Source-Mirrored Test Structure](source-mirrored-test-structure.md)를 참고합니다.

### 4. 병렬화 가능한 경계와 조정할 경계를 구별하기

| 변경 관계 | 구조적 대응 |
| --- | --- |
| **독립적인 기능·도메인 변경** | 각 작업이 자기 영역의 구현과 검증을 끝낼 수 있게 응집시킵니다. |
| **서로 다른 구현이 하나의 공개 계약을 사용** | 계약의 의미와 호환성부터 안정화하고, 소비자별 내부 구현은 독립적으로 변경할 수 있게 합니다. |
| **동일한 불변식·schema·공유 상태를 함께 변경** | 책임 주체를 한곳에 두거나 호환되는 전환 단계로 나눕니다. 인위적 분리보다 조정이 낫습니다. |

이 구분은 **작업 사이의 병렬 개발**과 **한 작업 안의 다중 agent 협업**에 모두 유용합니다. 한 기능 안에서도 API 계약이 안정되어 있다면 구현·테스트·리뷰가 서로 다른 관점에서 협력하기 쉽습니다. 반면 한 agent가 설계를 바꾸는 동안 다른 agent가 그 설계를 전제로 같은 코드를 쓰는 상황은 독립적이지 않습니다. 읽기 전용 분석·검토와 쓰기 작업의 차이도 고려합니다.

Agent의 실제 실행·위임·작업 공간 격리 절차는 별도 workflow가 결정합니다. 아키텍처의 역할은 **독립적인 작업이 가능한 접점을 제공하고, 독립적이지 않은 부분을 드러내는 것**까지입니다.

### 5. 대표 변경으로 구조를 되먹임하기

구조의 품질은 파일 개수나 추상적인 '독립성 점수'보다 **변경을 수행할 때의 비용**으로 살펴봅니다.

| 관찰 신호 | 다음 설계 질문 |
| --- | --- |
| 작은 기능 변경마다 무관한 내부 파일을 열거나 수정함 | 책임·데이터를 변경 단위에 더 가깝게 모을 수 있는가? |
| 여러 작업이 공통 `utils/`·설정·schema에서 충돌함 | 안정된 공통 계약인가, 불필요하게 공유한 구현인가? |
| 테스트를 위해 항상 전체 시스템을 띄워야 함 | 단위 동작을 가까이에서 확인하고 필요한 통합 검증으로 보완할 수 있는가? |
| 각 작업은 성공하지만 결합 후 재작업이 큼 | 경계의 계약·호환성·변경 순서가 불명확한가? |

먼저 **이름·배치·접점 정리처럼 비용이 작은 개선**을 검토하고, 반복된 문제가 확인될 때 모듈 경계나 검증을 강화합니다. 변경 전후에 같은 작업 시나리오를 적용해 실제로 맥락과 조정 비용이 줄었는지 비교합니다.

## Boundary

이 패턴은 **아키텍처 선택을 돕는 방법**이지 모든 프로젝트에 강제할 계약이 아닙니다. 필수 module 수, 디렉터리 깊이, agent 수, layer 구조, microservice, architecture linter를 요구하지 않습니다. 중요한 불변식의 책임과 공유 변경의 조정은 각 프로젝트가 실제 적용하는 설계·테스트·운영 계약에서 다룹니다.

독립 개발과 독립 배포는 다르고, 폴더 분리만으로 동시 쓰기의 안전성이나 권한 격리가 생기지 않습니다. 분리보다 한곳에서 순차적으로 처리하는 편이 더 정확하고 저렴한 변경도 허용합니다.

## Grounding

이 패턴은 에이전틱 개발의 보편적 최적 구조가 실증되었다는 주장이 아닙니다. 모듈화·느슨한 결합 원칙을 **agent의 맥락 비용과 병렬 작업의 통합 비용**에 적용한 설계 휴리스틱입니다.

- [Parnas, *On the Criteria to Be Used in Decomposing Systems into Modules*](https://doi.org/10.1145/361598.361623) — 모듈 수보다 분할 기준이 중요하다는 고전적 근거.
- [DORA, *Loosely Coupled Teams*](https://dora.dev/capabilities/loosely-coupled-teams/) — 독립적인 변경·검증과 낮은 조정 비용에 대한 인간 팀 중심 근거.
- [OpenAI, *Harness Engineering*](https://openai.com/index/harness-engineering/) — agent가 탐색 가능한 지식·구조·검증 수단의 사례. 특정 팀의 엄격한 layer 구조를 보편적인 답으로 채택하지 않습니다.
- [Anthropic, *How We Built Our Multi-Agent Research System*](https://www.anthropic.com/research/multi-agent-research-system) — 코딩 작업에는 독립적으로 병렬화할 수 있는 부분이 제한될 수 있음을 설명하는 사례.
- [*Is Code Co-Committal an Indicator of Evolutionary Coupling?*](https://doi.org/10.3390/software5010011) — 변경 이력을 분할의 단서로 쓰더라도 프로젝트의 작업 관행에 따라 해석이 달라질 수 있음을 보여주는 연구.
