# Agentic Parallel Development Architecture

이 패턴은 **서로 다른 작업이 다른 영역의 내부 구현을 거의 몰라도 변경·검증·통합할 수 있는 소프트웨어 구조**를 지향합니다. 병렬 작업뿐 아니라 한 작업 안에서 여러 agent가 협업할 때 발생하는 맥락 탐색, 공유 변경, 계약 조정 비용도 고려합니다.

[GPPC Guidance Stack](../context-engineering/gppc-guidance-stack.md)에 따라 **Goal·Principles는 지향점과 판단 기준**, **Patterns·Contracts는 선택 가능한 해결 방식과 적용 조건**을 다룹니다.

## Goal

기능 변경을 가능한 한 **응집된 책임 경계 안에서 이해하고 수행**하고, 다른 작업이나 agent와는 예측 가능한 계약으로 협업할 수 있는 상태를 목표로 합니다.

궁극적으로 줄이려는 비용은 디렉터리 탐색뿐 아니라 다음과 같습니다.

- 무관한 구현을 읽고 수정해야 하는 맥락 비용
- 공유 파일·데이터·설정을 함께 변경하며 생기는 충돌과 조정 비용
- 독립 작업의 결과를 통합할 때 발생하는 호환성 문제와 재작업

병렬 agent의 수, 모듈 수, 파일 수를 늘리는 것 자체는 목표가 아닙니다.

## Principles

- **책임과 변경 이유를 기준으로 나눕니다.** 함께 바뀌는 동작과 불변식은 응집시키고, 독립적으로 바뀌는 책임은 가능한 한 분리합니다. 파일 경계만으로 독립성이 보장되지는 않습니다.
- **경계 안에서는 깊이 이해하고, 경계 밖에는 계약으로 의존합니다.** 다른 영역의 내부 구현을 반복해서 추적하지 않고도 일반적인 변경을 판단할 수 있는 구조를 선호합니다.
- **국소적인 검증과 전체 정합성을 함께 봅니다.** 개별 모듈의 변경을 가까운 검증 수단으로 확인할 수 있되, 경계를 가로지르는 동작과 중요한 불변식은 통합 관점에서 확인할 수 있어야 합니다.
- **병렬 처리량보다 총변경 비용을 최적화합니다.** 분할 덕분에 절약한 시간보다 인터페이스·조정·통합·운영 비용이 더 크다면 단순한 구조가 낫습니다.
- **실제 시스템의 정확성과 관행을 우선합니다.** 언어·프레임워크·도구의 자연스러운 경계, 성능과 유지보수성을 희생하며 agent 전용 구조를 만들지 않습니다.

## Patterns

Patterns는 반복되는 상황에서 선택하거나 조합할 수 있는 해결 방식입니다. 정해진 단계나 디렉터리 템플릿은 아닙니다.

### 변경 경계에 맞는 분할 축 선택

| 분할 축 | 유리한 상황 | 재검토 신호 |
| --- | --- | --- |
| **도메인·역량 중심** (domain / capability) | 규칙·데이터·변경 이유가 다른 기능군 | 도메인 간 직접 데이터 변경, 공통 규칙의 무질서한 중복 |
| **기능 중심** (feature / vertical slice) | 사용자 가치 단위로 UI·업무 규칙·데이터 접근을 함께 수정 | 동일 불변식의 기능별 분산, 잦은 공동 수정 |
| **계층 중심** (layer / technical concern) | 작고 단순한 시스템, 프레임워크 관행, 독립적인 기술 관심사 | 기능 하나에 여러 계층의 공동 변경이 반복 |
| **컴포넌트·패키지 중심** (component / package) | 안정된 재사용 계약이나 독립 릴리스 경계가 존재 | 지나치게 작은 패키지와 버전·인터페이스 관리 부담 |

분할 축은 배타적이지 않습니다. 큰 경계를 도메인이나 기능으로 나눈 뒤 그 내부에 필요한 계층을 둘 수도 있습니다. **독립 개발을 위해 독립 배포까지 요구할 필요는 없으며**, 한 프로세스 내의 modular monolith도 유효한 선택입니다.

### 변경 시나리오로 경계 찾기

최근 또는 예상되는 서로 다른 변경을 몇 가지 골라, 각 변경에 필요한 코드·데이터·불변식·테스트를 추적합니다.

1. 같은 이유로 함께 바뀌는 동작과 데이터를 찾고, 하나의 책임으로 묶는 편이 나은지 봅니다.
2. 다른 변경 사유를 가진 영역은 공개 API·이벤트·데이터 계약 등 자연스러운 접점으로 분리할 수 있는지 비교합니다.
3. 서로 다른 작업을 동시에 진행한다고 가정하고 공통 schema·설정·생성물·helper에 변경이 집중되는지 확인합니다.
4. 한 경계의 변경을 이해하고 핵심 동작을 검증하는 데 다른 경계의 내부 지식이 얼마나 필요한지 살펴봅니다.
5. 분할로 줄어드는 조정·통합 비용과 추가되는 추상화·탐색·운영 비용을 비교합니다.

예를 들어 요금 계산과 배송 상태 변경이 대체로 독립적이라면 `billing`과 `shipping`을 나눌 근거가 생깁니다. 그러나 둘이 같은 주문 상태의 불변식을 함께 변경해야 한다면 계약 또는 책임의 소유자를 먼저 정해야 합니다. **디렉터리를 분리했다는 사실만으로 이 문제가 해결되지는 않습니다.**

### 두 수준의 협업을 수용하는 구조

**작업 사이의 병렬성**에서는 각 작업이 자신의 책임 영역을 변경하고 다른 영역에는 공개 계약을 통해 의존하는 형태가 유리합니다. 서로 다른 작업이 같은 schema나 설정을 바꿔야 한다면, 그 공유 자산을 별도의 조정 대상으로 봅니다.

**작업 안의 다중 agent 협업**에서는 역할 분리와 변경 소유권을 구분합니다. 분석·구현·테스트·검토 역할은 병렬로 진행할 수 있지만, 역할이 다르다는 이유만으로 같은 파일이나 공통 상태의 동시 쓰기가 안전해지지는 않습니다. 변경 대상이 겹치면 작업을 더 세분화하거나 한 주체가 통합하도록 조정할 수 있습니다.

협업자가 별도의 긴 문서 없이도 **기대 동작, 변경 경계, 공개 계약, 공유 자산의 소유권, 검증 방법**을 알아낼 수 있으면 충분합니다. 이미 코드·타입·테스트와 가까운 문서에 드러난 정보를 handoff 문서로 반복하지 않습니다. Agent orchestration이나 Git 작업 공간 격리 방식 자체는 이 아키텍처 패턴의 책임이 아닙니다.

### 파일 구조는 아키텍처의 표현으로 사용

`src/`, `tests/`, `docs/`, `scripts/`는 자산의 **종류**를, `billing/`, `shipping/` 같은 경계는 제품이나 도메인의 **책임**을 표현할 수 있습니다. 두 분할 축을 혼동하지 않습니다.

아래는 가능한 구조 중 하나입니다.

```text
src/
  billing/
    pricing.py
    public.py
  shipping/
    fulfillment.py
    public.py
tests/
  billing/
    test_pricing.py
  shipping/
    test_fulfillment.py
  contracts/
    test_billing_shipping.py
```

이 예시의 `public.py`는 공개 경계의 개념을 보여주는 자리표시자이지 필수 파일명이 아닙니다. 언어에 따라 package export, interface, service API 등 더 자연스러운 표현을 사용합니다. 테스트도 source와 같은 디렉터리에 두거나 기능·통합 경계에 따라 구성할 수 있습니다.

`common/`·`utils/`에 모든 재사용 코드를 모으기보다는 공통 불변식이나 안정된 재사용 계약이 실제로 있는지 살펴봅니다. 반대로 하나의 중요한 불변식을 기능마다 복제하는 것도 피합니다. 구체적인 탐색·배치 방식은 [Filesystem-Legible Structure](filesystem-legible-structure.md)와 [Source-Mirrored Test Structure](source-mirrored-test-structure.md)가 다룹니다.

### 관찰한 비용에 따라 구조 조정

실제 작업 기록이나 대표적인 변경 시나리오를 기준으로 다음 신호를 비교합니다.

| 신호 | 구조를 재검토할 질문 |
| --- | --- |
| 변경 범위 | 작은 기능 변경마다 무관한 모듈의 내부를 수정하는가? |
| 공유 자산 충돌 | 독립 작업들이 같은 schema·helper·설정·생성물에 반복해서 몰리는가? |
| 맥락·조정 비용 | 공개 계약만으로 충분하지 않아 다른 영역의 내부 구현을 계속 확인해야 하는가? |
| 검증 가능성 | 경계의 동작을 가까이에서 확인하고 필요한 통합 검증으로 보완할 수 있는가? |
| 통합 재작업 | 별도 작업은 성공해도 결합 시 계약 불일치나 순서 의존이 반복되는가? |

문제가 드러나면 **책임 재배치, 공개 계약 정리, 의존성 단순화, 검증 보강** 중 가장 비용이 작은 개선부터 비교합니다. 구조를 바꾼 뒤 같은 변경 시나리오로 효과를 다시 살펴봅니다. 관찰된 문제가 없으면 분할을 늘릴 이유도 약합니다.

## Contracts

다음은 **이 패턴을 특정 책임 경계에 적용하기로 했을 때** 유지해야 할 조건입니다. 모든 프로젝트에 별도 패키지·API 문서·검증 도구를 설치하라는 뜻은 아닙니다.

- **책임과 불변식의 소유가 모호하지 않아야 합니다.** 경계를 가로질러 변경되는 데이터·동작이 있다면 누가 계약과 정합성을 책임지는지 식별할 수 있어야 합니다.
- **경계 간 의존성과 호환성 영향이 파악 가능해야 합니다.** 소비자가 사용할 수 있는 표면과 변경 시 영향을 받는 곳을 구분할 수 있어야 하며, 내부 구현에 직접 의존하는 예외가 있다면 의도된 결합으로 취급해야 합니다.
- **같은 공유 상태에 대한 병렬 변경은 조정 없이 독립적이라고 간주하지 않습니다.** 공통 schema·migration·root 설정·lockfile·생성물 같은 대상에는 충돌 가능성을 고려해 변경 소유권과 통합 순서를 정합니다. 필요하면 호환 가능한 계약 제공 → 소비자 전환 → 구 계약 제거로 나눕니다.
- **검증 근거의 범위를 혼동하지 않습니다.** 국소 테스트 통과는 경계를 가로지르는 동작의 검증을 대체하지 않으며, 실행하지 않은 검증을 완료로 간주하지 않습니다. 검증 방식은 실제 언어·도구·시스템의 계약에 맞춥니다.

이 패턴만으로 **작업 공간의 격리, 권한, 보안, branch·PR 운영, agent 간 실행 순서**가 보장되는 것은 아닙니다. 이러한 규칙은 각 프로젝트와 실행 환경의 정본에 맡깁니다. 성능·정확성·운영 비용을 악화시키는 과도한 모듈화, 선제적인 microservice 전환, agent 수에 맞춘 영구 폴더 분할도 요구하지 않습니다.

## Grounding

이 패턴은 에이전틱 개발에서 보편적으로 최적인 레이아웃이 실증되었다는 주장이 아닙니다. 기존 모듈화와 느슨한 결합의 원칙을 agent의 맥락 비용·협업 충돌 문제에 적용한 설계 지침입니다.

- [Parnas, *On the Criteria to Be Used in Decomposing Systems into Modules*](https://doi.org/10.1145/361598.361623) — 변경 이유와 책임을 기준으로 모듈을 나누는 관점.
- [DORA, *Loosely Coupled Teams*](https://dora.dev/capabilities/loosely-coupled-teams/) — 인간 개발 조직의 조정 비용과 독립적인 전달을 다룬 근거. Agent 생산성의 직접 측정치는 아닙니다.
- [OpenAI, *Harness Engineering*](https://openai.com/index/harness-engineering/) — agent-first repository에서 읽기 쉬운 구조와 검증 가능한 불변식을 활용한 사례. 그 팀의 구체적 계층 구조는 보편적인 규칙이 아닙니다.
- [Anthropic, *Building Effective Agents*](https://www.anthropic.com/research/building-effective-agents) — 작업 분할과 병렬·조정 패턴의 조건. 특정 filesystem layout의 우월성을 입증하는 근거는 아닙니다.
