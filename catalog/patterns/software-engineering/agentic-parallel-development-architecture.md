# Agentic Parallel Development Architecture

**에이전트에 유리한 아키텍처는 모듈이나 agent 수가 많은 구조가 아니라, 하나의 변경을 정확히 찾아 이해하고 수정·검증한 뒤 다른 변경과 합치기 쉬운 구조입니다.** 사람을 위한 응집도와 낮은 결합도는 여전히 중요하지만, 이 패턴은 특히 에이전트가 매 작업마다 코드를 재탐색하고, 제한된 맥락에서 추론하며, 여러 독립 실행의 결과를 결합한다는 점을 설계 판단에 추가합니다.

[GPPC Guidance Stack](../context-engineering/gppc-guidance-stack.md)의 Goal·Principles·Patterns(GPP)로 구성합니다. 이것은 새 아키텍처 스타일이나 필수 폴더 템플릿이 아니라 **에이전트가 반복해서 수행할 변경 작업을 기준으로 구조 대안을 고르는 패턴**입니다.

## Goal

에이전트가 각 변경에서 **올바른 위치를 찾고 → 필요한 맥락만 읽고 → 의미를 보존해 수정하고 → 가까운 피드백으로 확인하고 → 다른 변경과 통합**할 때 발생하는 총비용을 줄입니다. 이때 일반적인 소프트웨어 품질, 데이터 정합성, 보안, 성능과 인간 개발자의 이해 가능성은 보존합니다.

다중 에이전트를 활용할 수 있다는 가능성보다 **독립적으로 완료 가능한 변경의 범위와 통합의 예측 가능성**이 중요합니다. 특정 모델이나 context window의 크기를 기준으로 구조를 고정하지 않습니다.

## Principles

- **개발 작업의 완결성을 설계 기준으로 삼습니다.** 파일 크기나 폴더 수가 아니라, 대표적인 변경 하나를 찾고 안전하게 끝내기까지의 경로를 비교합니다.
- **더 많이 읽게 하기보다 올바르게 찾게 합니다.** 기능의 실제 구현, 유사한 이름의 대안, 공개 접점과 검증 위치를 구분할 근거가 있어야 합니다. 탐색 도구만 개선하면 되는 문제를 구조 변경으로 해결하지 않습니다.
- **국소 수정과 관찰 가능한 피드백을 연결합니다.** 모듈의 의미 있는 동작을 인접한 단위에서 재현·검증할 수 있으면 매번 전체 시스템을 이해하고 실행할 필요가 줄어듭니다. 전체 정합성 검증은 여전히 필요합니다.
- **협업의 단위를 파일이 아닌 의미적 의존성으로 판단합니다.** 두 agent가 다른 파일을 써도 한쪽의 schema·정책 결정이 다른 쪽을 바꾸면 독립 작업이 아닙니다.
- **변경하지 않는 선택을 포함합니다.** 새 인터페이스, 계층, index, 문서, 테스트 장치의 유지비와 실제 절약되는 탐색·추론·검증·통합 비용을 함께 비교합니다.

## Patterns

### 1. 변경의 진입점이 드러나는 구조

**문제:** 비슷한 이름의 함수·유틸리티·구현체가 널려 있어 agent가 잘못된 위치를 수정하거나, 올바른 파일을 찾은 뒤에도 주변 전체를 다시 읽어야 합니다.

**해결 형태:** 실제 기능과 변경 책임을 찾는 데 도움이 되는 **명확한 진입점과 추적 가능한 관계**를 갖춥니다.

- 기능이 이미 module·package·route·type export 등으로 잘 드러나면 그 표현을 활용합니다. 코드 검색, symbol index, 호출 관계 탐색으로 바로 찾을 수 있다면 추가 파일이 필요 없습니다.
- 기능의 진입점에서 실제 정책과 데이터 소유자로 이어지는 경로가 불명확할 때는 공개 symbol, 명명, 위치 또는 가까운 안내를 개선합니다. 여러 유사 구현이 있다면 **어느 것이 언제 사용되는지** 구별 가능해야 합니다.
- 중요한 동작이 런타임 등록이나 생성 코드에 의해 연결된다면, 실제 owner와 생성·등록 관계를 추적할 수 있게 합니다. 외부 문서의 설명보다 현재 코드·설정·생성 원본을 우선합니다.

**구조를 바꿀 신호:** 여러 변경에서 코드 검색이 반복적으로 잘못된 구현에 도달하거나, 실제 실행 경로·책임을 알아내기 위해 무관한 영역을 계속 횡단합니다. 탐색 도구나 작은 entrypoint 설명만으로 해결된다면 대규모 모듈 재배치는 피합니다.

이것은 폴더를 더 설명적으로 만들자는 뜻과 다릅니다. 파일 이름·배치에 관한 판단은 [Filesystem-Legible Structure](filesystem-legible-structure.md)가 다룹니다. 여기서는 **검색 결과가 실제 변경·실행 경로와 연결되는가**가 핵심입니다.

### 2. 변경과 가까운 검증 경계

**문제:** agent가 작은 규칙 하나를 수정해도 전체 서비스를 띄우거나 외부 시스템과 얽힌 거대한 테스트를 돌려야 하므로, 수정·실패 분석·재시도의 맥락과 시간이 커집니다.

**해결 형태:** 수정이 잦은 정책·변환·계산처럼 관찰 가능한 동작에 대해, 적절한 **호출 경계와 빠른 피드백 경로**를 갖춥니다.

- 핵심 정책이 외부 I/O와 뒤섞여 검증하기 어렵다면 기존 함수·모듈 경계에서 순수한 계산이나 교체 가능한 입력을 분리하는 작은 seam을 비교합니다. 모든 함수를 interface 뒤에 숨길 필요는 없습니다.
- 테스트가 실제 공개 동작과 오류 의미를 설명할 수 있다면 다음 agent가 코드만 보고 추측해야 할 부분이 줄어듭니다. 계약 테스트·fixture·예제 입력은 필요할 때만 사용하고 framework의 자연스러운 배치를 따릅니다.
- 상태 변화·로그·에러가 외부에 보이지 않아 결함을 재현할 수 없다면, 해당 변경 경계의 관찰 가능성과 재현 가능한 입력을 개선할지 검토합니다. 실행 환경 격리·로그 수집 도구의 구현은 별도 책임입니다.

**예:** 주문 도메인의 계산 책임은 이미 잘 분리되어 있는데, 모든 테스트가 실DB를 켠 전체 checkout 경로에서만 실행된다면 **도메인을 재분할하기보다 계산 경계의 피드백부터 가깝게 하는 선택**이 더 에이전틱할 수 있습니다. 반대로 하나의 트랜잭션에서만 보장되는 불변식을 빠른 단위 테스트만으로 검증했다고 간주하지 않습니다.

### 3. 의미적 의존성에 맞춘 병렬 변경 경계

**문제:** agent별 폴더와 분리된 작업 공간이 있어도 생산자·소비자 계약이나 공유 데이터를 동시에 바꾸면 개별 작업은 성공하고 통합은 실패할 수 있습니다.

**해결 형태:** 아키텍처의 변경 경계를 다음처럼 구분하고, 병렬화할 수 없는 관계를 감추지 않습니다.

| 변경 관계 | 적합한 구조적 선택 |
| --- | --- |
| **독립 변경**: 각자의 책임·검증·불변식이 분리됨 | 각 영역의 구현과 가까운 검증을 하나의 변경 단위로 묶고 공개 접점만 공유 |
| **생산자–소비자 변경**: 한쪽의 API·schema·오류 의미가 다른 쪽의 입력 | 기존 계약을 유지하거나 호환 가능한 경계를 먼저 정한 뒤 소비자별 구현을 분리 |
| **공유 불변식 변경**: 동일한 정책·DB 상태·migration의 의미를 함께 바꿈 | 권위 있는 소유자에서 한 번 결정하고, 소비자는 이를 사용하도록 구성; 무리한 동시 분할보다 조정을 선택 |

예를 들어 한 agent가 정상화된 데이터 schema를 변경하면서 다른 agent가 새 입력원 adapter를 작성한다면, 서로 다른 파일을 수정해도 **schema의 의미가 결정되기 전에는 독립적이지 않습니다**. 반면 공개 schema가 안정되어 있다면 서로 다른 입력원 구현과 인접 테스트는 병렬로 작성하기 쉬워집니다.

이 구분은 *작업 사이의 병렬성*과 *한 작업 안의 다중 agent 협업* 모두에 적용할 수 있습니다. 다만 agent의 실행 순서, 실시간 상태 공유, branch·worktree 격리와 승인 정책 자체는 architecture가 아니라 orchestration/VCS의 책임입니다. 좋은 경계는 협업을 쉽게 할 뿐, 조정 없이 동시 쓰기를 안전하게 만들지는 않습니다.

### 4. 다음 실행에서 맥락을 복원할 수 있는 구조

**문제:** 이전 agent가 알고 있던 책임 경계와 중요한 예외가 채팅·임시 계획·추측에만 남으면, 다음 agent는 다시 탐색하거나 잘못된 관례를 복제합니다.

**해결 형태:** 이후 변경에 필요한 사실을 **변경 대상과 가까운 기존 정본**에서 재구성할 수 있도록 합니다.

- 공개 타입·스키마·테스트·선언적 설정이 실제 의미를 표현하면 그 자체를 근거로 사용합니다. 사라지기 쉬운 대화 내용을 별도 문서로 복제하지 않습니다.
- 구조적으로 드러나지 않는 중요한 의존성이나 소유 관계만 적절한 정본에 연결합니다. 큰 안내 문서 하나에 구현·결정·실행 방법을 모두 중복하지 않습니다.
- 생성물, 동적 등록, 외부 스키마처럼 진짜 원본과 소비자가 멀어지는 경우에는 **어느 쪽이 원본이고 어떤 경로로 파생되는지** 식별할 수 있게 합니다.

에이전트가 더 큰 컨텍스트를 주입받는 것을 목표로 하지 않습니다. **필요한 사실을 선택적으로 회수하고 최신 코드·검증과 대조할 수 있는가**가 설계 판단입니다. 문서 라우팅과 세션 인계의 구체적 형식은 이 패턴에서 정의하지 않습니다.

### 5. 에이전트의 리팩터링 발견 오류를 설계 비교에 반영하기

**문제:** 특정 변경 방법을 상세히 지정받은 agent는 구현할 수 있어도, '구조를 개선하라'는 요청만으로는 잘못된 리팩터링을 선택하거나 불필요한 분할을 할 수 있습니다.

**해결 형태:** 실제 수정 이전에 대표적인 변경 두세 가지로 **현재 구조 유지, 탐색·피드백만 보강, 작은 책임 추출, 더 큰 모듈 개편**을 비교합니다.

| 후보 | 적합한 신호 | 기각할 신호 |
| --- | --- | --- |
| **현 구조 유지** | 대표 변경이 이미 잘 찾아지고 검증·통합됨 | 반복된 잘못된 위치 수정·과도한 탐색·통합 재작업 |
| **탐색·피드백 개선** | 책임 경계는 적절하지만 진입점이나 빠른 테스트가 부족 | 원인이 실제 데이터/정책 소유권의 혼란 |
| **작은 책임 추출** | 특정 정책이 I/O·공유 helper에 가려지고 반복 변경됨 | wrapper를 더 만들 뿐 맥락과 결합이 줄지 않음 |
| **모듈 경계 재설계** | 변경과 불변식의 소유가 지속적으로 뒤섞임 | 새 패키지·서비스가 더 많은 계약·배포·조정 비용을 발생 |

비교 대상은 디렉터리의 아름다움이 아니라 **올바른 수정 지점까지의 탐색, 꼭 필요한 읽기 범위, 작은 변경의 검증, 다른 변경과 통합, 이후 유사한 수정의 난이도**입니다. 실제 측정이 없으면 휴리스틱 판단으로 남기고 token 수나 파일 수를 보편적인 성공 지표로 삼지 않습니다.

리팩터링에서 큰 재배치가 유력하더라도 한 번에 끝내기보다 변경 경계에서 작은 seam을 확보하고 호환 가능한 소비자 전환을 비교할 수 있습니다. 이는 기존의 점진적 리팩터링 방법을 **에이전트가 검증 가능한 작은 변경으로 실행하기 위해 재사용**하는 것이며, 별도 agent 전용 migration 절차를 요구하지 않습니다.

## Example: 같은 요구에 다른 구조를 선택하기

### 입력원 추가가 잦은 데이터 파이프라인

다음 구조가 있다고 가정합니다.

```text
src/
  fetch.py
  parse.py
  mapping.py
  validation.py
  utils.py
tests/
  test_pipeline.py
```

에이전트에게 `vendor_b` 수집을 추가하라고 하면 비슷한 파서·매핑 함수에서 정확한 수정 지점을 찾고, 공통 `validation.py`의 의미를 추론하고, 전체 파이프라인 테스트로 결과를 확인해야 할 수 있습니다.

기존 구조가 이 탐색을 잘 지원한다면 유지해도 됩니다. 그러나 새 입력원마다 같은 문제가 반복된다면 다음과 같은 **변경 경계의 표현**을 비교할 수 있습니다.

```text
src/
  sources/
    vendor_a.py
    vendor_b.py
  normalized_record.py   # 공유 데이터 의미의 소유자
  normalize.py           # 공유 정규화 규칙
  run.py                 # 입력원과 처리 조합
tests/
  sources/
    test_vendor_a.py
    test_vendor_b.py
  test_normalize.py
  test_pipeline.py
```

이후 agent가 `vendor_c`를 추가할 때는 **입력원 진입점 → 정규화된 레코드의 공개 의미 → 해당 테스트**를 중심으로 작업할 수 있습니다. 새로운 공급자별 파싱은 독립적으로 개발할 여지가 있지만, `normalized_record.py`의 의미를 바꾸는 작업은 모든 소비자와의 조정이 필요한 변경으로 남습니다.

여기서 단지 수직 슬라이스를 채택한 것이 차별점은 아닙니다. **새로운 agent가 다른 입력원 전체를 읽지 않고도 올바른 지점을 찾고, 빠른 테스트로 확인하고, 공유 schema 변경과 독립 작업을 구별할 수 있는지**가 선택의 이유입니다. 한편 schema가 자주 변하거나 입력원별 검증 규칙이 모두 다르면 이 구조 자체를 다시 비교해야 합니다.

### 이미 모듈화된 시스템에서의 다른 결론

`billing/`과 `shipping/`의 책임과 API가 충분히 명확하지만, 요금 정책 변경을 검증하려면 전체 앱·DB를 실행해야 한다고 가정합니다. 일반적인 모듈화 관점에서는 구조 문제가 작을 수 있습니다. **에이전트 변경 비용의 관점에서는**, 모듈을 더 쪼개기보다 요금 계산을 독립적으로 재현할 수 있는 경계·fixture·검증 경로가 더 가치 있는 선택일 수 있습니다. 실제 외부 효과와 트랜잭션 검증은 그와 별도로 유지합니다.

이처럼 에이전틱 최적화는 **새 폴더를 만드는 결론이 아니라 무엇을 개선하지 않을지 결정하는 기준**도 제공합니다.

## Boundary

이 패턴은 소프트웨어 **구조의 선택과 개선**을 다룹니다. Agent workflow, 컨텍스트 주입 방식, 장기 기억 시스템, Git 격리, CI gate, observability 도구의 상세 운영은 별도 책임입니다. 아키텍처가 그런 능력을 지원하는 접점을 가질 수는 있지만 해당 시스템까지 이 문서가 소유하지 않습니다.

책임 경계의 적합성, 보안, 성능, 거래 일관성, 유지보수성과 자연스러운 ecosystem convention을 희생하여 agent의 탐색만 최적화하지 않습니다. 고정 계층·도메인 구조·추가 documentation·index·test harness·linter·microservice는 필수가 아닙니다.

## Grounding

이 문서는 **특정 에이전트 전용 아키텍처가 보편적으로 우수하다는 실증 결과가 아니라**, 관찰된 에이전트 작업 특성에서 도출한 **구조 설계 가설과 선택 휴리스틱**입니다. 기존 소프트웨어 설계 원칙은 전제이며, 다음 근거는 그 위에 추가할 판단 기준을 뒷받침합니다.

- [OpenAI, *Harness Engineering*](https://openai.com/index/harness-engineering/) — agent가 실제 코드·실행 결과·설계 정보를 탐색하고 검증할 수 있을 때의 사례. 그 팀의 고정 layer·custom lint는 이 패턴의 필수 구조가 아닙니다.
- [CORE-Bench](https://aclanthology.org/2026.emnlp-main.1604/) / [RepoNav](https://aclanthology.org/2026.emnlp-main.1474/) — 요구에서 코드 위치와 주변 맥락을 찾아내는 어려움, 구조적 탐색 단서의 유용성. 특정 filesystem layout의 우수성을 직접 증명하지 않습니다.
- [ICLR 2026, *Improving Code Localization with Repository Memory*](https://proceedings.iclr.cc/paper_files/paper/2026/hash/b4c06f095368497f3ac19422efef8133-Abstract-Conference.html) — 변경 이력·기능 지식 재사용을 통한 localization 보강의 근거. 모든 저장소에 별도 memory 시스템을 요구하지 않습니다.
- [ICML 2026, *CodeTaste*](https://proceedings.mlr.press/v306/thillen26a.html) — 리팩터링 구현보다 적절한 후보의 발견이 어려울 수 있으며, 제안과 구현을 구분하는 방법이 도움 될 수 있다는 근거.
- [AsynCodeBench](https://arxiv.org/abs/2609.32662) / [ESEM 2026, *Coordinating Agents on a Shared Git Workspace*](https://doi.org/10.4230/LIPIcs.ESEM.2026.18) — 개별 코딩 성공과 협업 의존성 해결의 차이, 작업 상태 관찰의 중요성. 후자는 제한된 실험으로 shared workspace 사용을 일반적으로 권고하는 근거가 아닙니다.
