# Agentic Parallel Development Architecture

**병렬 개발에 유리한 아키텍처는 agent별 폴더가 많은 구조가 아니라, 서로 다른 변경이 다른 영역의 내부 구현을 거의 몰라도 이해·구현·검증할 수 있는 구조입니다.** 한 작업 안에서 여러 agent가 협업하더라도 마찬가지입니다. *독립적으로 바뀔 수 있는 것*과 *의도적으로 함께 결정해야 하는 것*을 구별해야 합니다.

이 패턴은 [GPPC Guidance Stack](../context-engineering/gppc-guidance-stack.md)의 Goal·Principles·Patterns(GPP) 관점으로 구성합니다. 특정 레이어나 저장소 레이아웃을 강제하기보다, **새로운 시스템의 구조를 선택하거나 기존 시스템을 옮길 때 적용할 수 있는 해결 형태**를 다룹니다.

## Goal

한 기능을 변경할 때 필요한 코드·데이터·판단·검증을 가능한 한 좁은 책임 경계 안에 모으고, 다른 작업과의 접점을 예측 가능하게 만듭니다. 이렇게 **맥락 재탐색, 공동 수정, 조정, 병합 뒤 재작업**을 줄이면서 정확성과 후속 변경의 용이성을 유지하는 것을 지향합니다.

에이전트 수와 모듈 수를 늘리는 것은 목표가 아닙니다. 서로 강하게 결합된 변경을 억지로 병렬화하면 더 많은 조정과 통합 실패가 생길 수 있습니다.

## Principles

- **변경 이유와 불변식을 먼저 봅니다.** 함께 바뀌고 함께 일관성을 유지해야 하는 동작은 가깝게, 독립적으로 진화하는 책임은 분리하는 쪽을 선호합니다. 폴더명이나 계층명은 그 결과의 표현입니다.
- **로컬 맥락과 전체 정합성 사이에 경계를 둡니다.** 일반적인 변경은 담당 모듈의 책임·공개 접점·인접 검증으로 진행할 수 있게 하되, 영역 간 계약과 시스템 검증을 생략하지 않습니다.
- **다른 영역의 내부보다 안정된 접점에 의존합니다.** 작은 공개 표면은 독립 변경에 도움이 되지만, 사소한 호출마다 인터페이스와 래퍼를 추가하면 오히려 맥락이 늘어납니다.
- **병렬성의 이득과 구조 유지비를 함께 비교합니다.** 작업을 쉽게 나누더라도 데이터 중복·배포·운영·테스트 비용이 커지면 더 응집된 단위가 낫습니다.
- **처음 설계와 이후 변경을 모두 봅니다.** 당장의 기능 개발이 편해져도 다음 수정에서 의미·에러 처리·입력 검증이 흩어지면 좋은 경계가 아닙니다.

## Patterns

### 변경의 지도를 먼저 만들고 책임 경계를 찾기

현재 디렉터리 트리보다 **실제로 발생할 변경**을 출발점으로 삼습니다. 신규 설계라면 예상되는 사용 시나리오를, 리팩터링이라면 최근 기능 수정·결함 수정·변경 요청을 봅니다. 각 변경에서 읽는 코드, 바꾸는 규칙, 소유 데이터, 외부 효과와 필요한 검증을 찾아봅니다.

- **함께 바뀌는 이유가 같은가?** 요금 계산과 할인 규칙처럼 하나의 정책과 불변식을 공유한다면 가까이 두는 편이 자연스러울 수 있습니다.
- **같은 이름이지만 의미가 다른가?** '주문'이라도 결제의 청구 금액과 배송의 수령 정보를 동일한 모델로 강제하지 않고 각 문맥에 필요한 표현으로 나눌 수 있습니다.
- **다른 영역의 내부 상태를 알아야 하는가?** 필요한 정보만 공개 계약이나 변환 경계로 제공하면 수정 영향이 줄어드는지 봅니다.
- **어디에서 함께 쓰는가?** 공통 DB 테이블·스키마·설정·생성물이 둘 이상의 변경을 묶는다면, 디렉터리 분할보다 그 쓰기의 소유권을 먼저 다룹니다.

여러 파일이 자주 한 커밋에 등장하는 것은 **추가 조사 신호**일 뿐입니다. 대량 formatting, dependency update, 작업 단위의 구성 탓일 수도 있어 그것만으로 모듈 경계를 정하지 않습니다.

### 변경 단위를 중심으로 모듈을 구성하기

반복적인 작업이 사용자 기능이나 제품 역량 단위라면 **도메인·기능 경계로 큰 단위를 나누고, 각 단위 안에서 필요한 기술 계층을 사용하는 구성**을 우선 비교할 만합니다. 반대로 프레임워크가 제공하는 작은 프로그램이나 독립적인 기술 구성 요소에서는 계층·컴포넌트 중심이 더 자연스러울 수 있습니다.

| 구조 후보 | 비교할 상황 | 실패 신호 |
| --- | --- | --- |
| **Domain / capability** | 서로 다른 정책·데이터·변경 이유를 가짐 | 도메인마다 타 영역의 데이터·내부 모델을 직접 변경 |
| **Feature / vertical slice** | 하나의 기능을 끝까지 구현·검증 | 기능마다 동일한 불변식과 핵심 정책이 분산 |
| **Layer / technical concern** | 간단한 프로그램, 강한 ecosystem 관행, 독립적인 기술 책임 | 기능 하나마다 `controllers/`·`services/`·`repositories/`를 모두 횡단 |
| **Component / package** | 실제로 안정된 재사용·릴리스·운영 경계 | 작은 수정에도 여러 패키지의 interface/version을 조정 |

기존의 `controllers/`, `services/`, `repositories/` 구조에서 요금 정책과 배송사 변경이 늘 같은 세 디렉터리를 횡단한다고 가정합니다. 대안은 (A) 현재 계층을 유지하되 문제가 되는 공유 함수만 정리, (B) `billing/`·`shipping/`의 기능 경계를 갖는 modular monolith, (C) 각 기능을 별도 서비스로 분리하는 것입니다. **데이터 소유권과 배포 요구가 바뀌지 않는다면 B를 A·C와 먼저 비교할 근거가 있지만**, 실제로 A만으로 수정 비용이 충분히 낮아지면 대규모 재배치가 필요하지 않습니다. C는 독립 배포나 격리 요구가 명확할 때 비교합니다.

중요한 것은 계층의 제거가 아닙니다. 예컨대 `billing/` 안에 API, 정책, 저장소 접근이 모두 존재할 수 있습니다. 경계를 가로지르는 의존은 각 모듈이 노출한 **좁은 공개 동작·데이터·이벤트**를 통해 연결하고, 내부 클래스나 테이블 구조를 소비자의 가정으로 만들지 않는 편이 좋습니다.

공통 기능은 **진짜 동일한 불변식이나 안정된 플랫폼 역량**인 경우 공유할 수 있습니다. 단지 중복 줄 수를 없애기 위해 모든 모듈의 사소한 helper를 `common/`으로 올리면 변경 병목이 생깁니다. 반대로 하나의 핵심 비즈니스 규칙을 복사해서 여러 모듈이 따로 수정하게 만드는 것도 피합니다. 공통 모델을 통일할지 문맥별 모델을 번역할지는 **함께 진화해야 하는 의미인지**로 판단합니다.

### 공개 접점과 데이터 소유권으로 병렬 변경 가능하게 만들기

**작업 간 병렬 개발**에는 다른 모듈의 구현이 변경되어도 소비자의 일반적인 수정이 지속될 수 있는 접점이 유리합니다. 한 모듈이 타 모듈의 private 함수나 DB를 직접 변경한다면 파일을 분리해도 독립적이지 않습니다.

| 관찰한 결합 | 유력한 구조적 선택 |
| --- | --- |
| 두 기능이 하나의 정책·강한 일관성 경계를 함께 변경 | 그 불변식의 소유 단위를 묶거나 변경 결정을 공동으로 취급 |
| 서로 다른 모델이 한 실체의 일부 정보만 필요 | 각 문맥 모델을 유지하고 필요한 데이터를 공개 API·번역 접점으로 전달 |
| 여러 소비자가 안정된 역량을 반복 사용 | 의미와 호환성이 분명한 공유 모듈·서비스를 검토 |
| 공통 파일이 잦은 충돌 지점이나 변경 파급의 원인 | 코드가 공통 규칙인지 우연한 공통 구현인지 먼저 구별하고 소유 책임 재배치 |

읽기 모델의 복제, 이벤트, 비동기 통신은 **분산 일관성·장애·관측 비용이 정당화될 때** 선택합니다. 단일 프로세스의 모듈 호출이나 하나의 DB에서도 논리적 책임 경계를 유지할 수 있습니다. 분리된 배포는 병렬 개발의 필수 조건이 아닙니다.

**한 작업 안에서의 다중 agent 협업**은 더 작은 단위로 볼 수 있습니다. 예를 들어 checkout의 요금 정책 구현과 배송사 adapter 구현은 공개 입력·출력과 오류 의미가 안정적이라면 따로 진행하고, 이를 사용하는 통합 테스트나 read-only 검토도 독립적으로 준비하기 쉽습니다. 반대로 한 agent가 결제 결과 schema를 바꾸는 동안 다른 agent가 그 schema로 소비자를 작성한다면, 파일이 달라도 먼저 호환 가능한 접점이나 변경 순서를 정할 필요가 있습니다. 구현·테스트·리뷰라는 역할 이름만으로 독립성은 생기지 않습니다. 실제 작업 공간 격리와 orchestration은 이 아키텍처 패턴의 범위를 벗어납니다.

### 기존 구조를 안전하게 옮길 수 있는 접점 만들기

레거시 리팩터링에서는 이상적인 목표 트리부터 확정하기보다, **현재 동작을 유지한 채 한 변경 경계를 떼어낼 수 있는 seam**을 찾는 편이 유용합니다.

예를 들어 요금 정책 변경마다 `controllers/`, `services/`, `repositories/` 및 공유 주문 모델을 수정한다면 다음 변화를 비교할 수 있습니다.

```text
Before                         After (one possible shape)
src/                           src/
  controllers/                    billing/
  services/                         pricing.py
  repositories/                   shipping/
  models/                           carrier.py
  utils/                          ordering/
                                    checkout.py
                                    order_state.py
                                tests/
                                  billing/
                                  shipping/
                                  ordering/
```

여기서는 `ordering`이 주문 상태 변경의 최종 책임을 갖고, checkout이 `billing`의 요금 계산과 `shipping`의 배송 요청을 **공개 동작으로 조합**한다고 가정합니다. `billing`·`shipping`이 주문 테이블에 직접 쓰지 않도록 경계를 정하는 것이 핵심입니다. 필요한 결과는 호출 결과나 메시지로 전달할 수 있지만, 비동기 이벤트로 분산시키는 것이 필수는 아닙니다. 주문 상태와 결제의 원자성이 중요한 경우에는 그 일관성 경계를 먼저 확인해야 합니다.

`ordering/`을 별도로 두는 것이 항상 최선도 아닙니다. 실제 시스템에서 주문 규칙이 `billing`과 함께 유지되어야 하는 경우 두 책임을 더 크게 묶는 대안도 가능합니다. **경계의 의미와 의존성 방향이 정해지지 않으면 파일만 이동한 뒤에도 shared DB 쓰기와 순환 의존성이 남습니다.**

위험을 낮춘 전환 형태는 다음과 같습니다.

1. **현재 동작과 결합을 파악합니다.** 요금·배송·주문 상태의 대표 입력/출력, 입력 검증, 오류·권한·트랜잭션·데이터 갱신, 소비자와 검증 경로를 확인합니다. 이동 과정에서 이런 동작을 우발적으로 바꾸지 않을 비교 기준을 확보합니다.
2. **작게 우회할 seam을 선택합니다.** 우선 기존 checkout 호출을 유지한 채 요금 계산 함수와 그 테스트를 `billing`으로 추출할 수 있는지 봅니다. 기존 접점으로 충분하면 새 interface를 만들지 않습니다.
3. **한 책임을 이동합니다.** checkout은 `billing`의 공개 동작을 호출하도록 바꾸되, 이 시점에는 주문 상태와 저장소의 소유권을 그대로 유지할 수 있습니다. 작은 단위의 동작·회귀 검증 뒤 다음 변경으로 넘어갑니다.
4. **다른 소비자를 점진적으로 전환합니다.** 배송 연동이나 공유 API가 바뀌는 경우 새 형태를 먼저 제공하고 소비자를 옮긴 뒤 구 경로를 제거하는 *expand–migrate–contract*를 비교합니다. 깊이 박힌 라이브러리를 교체할 때만 임시 *branch by abstraction*을 고려합니다.
5. **임시 구조를 정리합니다.** 전환이 끝나면 불필요한 adapter와 구형 경로를 제거합니다. 처음의 요금·배송 변경을 다시 가정해 수정 범위와 통합 위험이 실제로 낮아졌는지 확인합니다.

이것은 필수 5단계 프로세스가 아니라 **레거시 교체에서 선택 가능한 진화 경로**입니다. 처음부터 충분히 모듈화되어 있고 소비자가 적다면 단순한 이동이나 함수 추출이 더 저렴합니다. 데이터 소유권을 바꾸는 작업은 API만 교체하는 것보다 별도의 이행·정합성 검토가 필요할 수 있습니다. **도메인 지식이 불확실하다면 큰 경계를 먼저 유지하고, 변경 경험이 쌓일 때 더 작게 나누는** 대안도 비교합니다.

### 도메인 중심이 아닌 프로젝트에도 적용하기

모든 시스템의 변경 단위가 사용자 기능이나 비즈니스 도메인은 아닙니다. 데이터 파이프라인이라면 `ingestion/`, `normalization/`, `quality/`가 각각 **독립적인 데이터 계약·오류 의미·변경 사유**를 가질 수 있습니다. 반대로 모든 입력마다 세 단계를 항상 함께 변경한다면 소스별 vertical slice가 더 자연스러울 수 있습니다.

예를 들어 새 데이터 연동마다 수집·변환·검증 코드가 함께 추가된다면 `connectors/vendor_a/` 같은 **입력원별 수직 단위**가 독립 변경에 유리할 수 있습니다. 반대로 여러 입력원이 정확히 동일한 표준화 규칙을 공유한다면 `normalization/`에서 그 의미를 소유하고 입력원별 adapter가 이를 사용하도록 하는 편이 낫습니다. 이 선택은 'layer-first'와 'feature-first'라는 이름보다 **실제로 무엇이 함께 바뀌고 어떤 불변식이 공유되는지**에 달려 있습니다.

따라서 `src/`·`tests/`·`docs/`는 자산 유형을 나타내는 한 가지 방식이고, 그 아래의 도메인·기능·파이프라인 영역은 변경 책임을 나타내는 선택지입니다. 언어·프레임워크의 기존 테스트 배치를 우선하며 파일 구조 자체를 아키텍처의 증거로 보지 않습니다. 탐색성은 [Filesystem-Legible Structure](filesystem-legible-structure.md), source/test 대응은 [Source-Mirrored Test Structure](source-mirrored-test-structure.md)를 함께 참고할 수 있습니다.

### 설계 계획을 실제 변경 시나리오로 비교하기

에이전트가 리팩터링 또는 신규 설계안을 제안한다면, **서로 다른 변경 두세 가지를 그 구조에서 실행한다고 가정**해 봅니다. 이상적인 계층도보다 이 시뮬레이션이 구조의 차이를 더 잘 드러낼 수 있습니다.

- **수정 위치와 맥락:** 요금 정책 하나를 바꿀 때 무엇을 읽고, 어느 책임 영역을 수정하는가?
- **독립성과 공유 상태:** 배송 정책 변경과 병행할 때 직접 겹치는 구현·데이터·schema는 무엇인가? 필요한 조정이 실제보다 숨겨져 있지 않은가?
- **피드백과 통합:** 어떤 인접 검증으로 빠르게 확인하고, 어떤 경계·통합 검증으로 합쳐진 동작을 확인하는가?
- **다음 변경과 비용:** 추후 정책·오류 처리·검증 규칙을 바꿀 때도 같은 경계가 유지되는가? 새 인터페이스·adapter·운영 부담이 이득보다 크지 않은가?

수정 폭과 공동 조정이 줄어도 테스트가 불가능하거나 하나의 불변식이 여러 곳에 복제된다면 개선이라고 보기 어렵습니다. 대표 변경에서 이득이 불분명하다면 **모듈이나 계층을 추가하지 않는 선택**도 결과입니다.

## Boundary

이 패턴은 아키텍처를 설계하고 비교하는 방법입니다. agent마다 파일을 할당하거나 branch·worktree·승인·실행 순서·검증 의무를 정의하는 workflow contract는 아닙니다. 소프트웨어의 의미상 경계와 실제 동시 쓰기의 격리도 서로 다릅니다.

원칙을 적용하기 위해 새 모듈·인터페이스·architecture linter·microservice를 의무적으로 추가하지 않습니다. 기존에 유효한 ecosystem convention, 데이터 정합성, 성능·운영·보안 요구를 해치는 분할은 적합하지 않습니다.

## Grounding

이 문서는 특정 디렉터리 구조가 agent 생산성을 항상 개선한다는 실증적 주장보다, 기존 소프트웨어 모듈화·점진적 전환 원칙을 **에이전트의 맥락·협업·후속 변경 비용에 적용하는 설계 휴리스틱**입니다.

- [Parnas, *On the Criteria to Be Used in Decomposing Systems into Modules*](https://doi.org/10.1145/361598.361623) / [Microsoft, *Domain analysis*](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis) — 변경 이유, 문맥별 모델과 명확한 상호작용 경계.
- [Martin Fowler, *Legacy Seam*](https://martinfowler.com/bliki/LegacySeam.html) / [*Branch by Abstraction*](https://martinfowler.com/bliki/BranchByAbstraction.html) / [*Parallel Change*](https://martinfowler.com/bliki/ParallelChange.html) — 기존 기능을 유지하며 경계를 전환하는 방법.
- [OpenAI, *Harness Engineering*](https://openai.com/index/harness-engineering/) — agent가 이해·검증할 수 있는 저장소 구조의 사례. 해당 팀의 엄격한 계층 모델을 보편 규칙으로 복제하지 않습니다.
- [Anthropic, *Multi-agent Research*](https://www.anthropic.com/research/multi-agent-research-system) / [AsynCodeBench](https://arxiv.org/abs/2609.32662) — 병렬 코딩의 조정 비용과 개별 작업 성공·협업 성공의 차이.
- [*Is Agent Code Less Maintainable Than Human Code?*](https://aclanthology.org/2026.emnlp-main.2528/) — 미래 agent 변경 용이성까지 평가할 필요가 있다는 근거. 모든 agent 코드에 대한 일반화는 아닙니다.
