# Software Architecture for Multi-Agent Development

**여러 에이전트가 개발하기 좋은 아키텍처는 작업자별 폴더가 많은 구조가 아니라, 독립 변경은 독립적으로 끝낼 수 있고 함께 결정해야 하는 의미는 한 곳에서 유지되며 통합 결과를 검증할 수 있는 구조입니다.** 파일이 겹치지 않는 것과 기능이 서로 호환되는 것은 다릅니다. 한 에이전트의 API·데이터·정책 변경이 다른 에이전트의 구현을 무효화한다면 서로 다른 파일을 수정해도 독립 작업이 아닙니다.

이 문서는 [GPPC Guidance Stack](../context-engineering/gppc-guidance-stack.md)의 Goal·Principles·Patterns(GPP)를 사용합니다. 특정 디렉터리 레이아웃이나 agent 운영 절차를 강제하지 않고, **여러 변경의 완결성과 결합 비용을 기준으로 소프트웨어 구조를 고르는 방법**을 다룹니다.

## Goal

여러 에이전트가 서로 다른 기능 또는 하나의 기능의 일부를 개발할 때 **올바른 책임 영역에서 변경을 완결하고, 불필요한 공동 수정·재탐색·조정을 줄이며, 합친 뒤에도 계약과 불변식이 유지되도록** 설계합니다.

최적화 대상은 agent 수·모듈 수·개별 PR 성공률이 아니라 **통합 후의 올바른 동작과 총 변경 비용**입니다. 복잡한 서비스 분리나 동시 실행보다 단일 변경·순차 처리가 나은 상황도 허용합니다.

## Principles

- **작업 경계가 아닌 변경 책임에서 출발합니다.** agent에게 임시로 할당한 파일 목록은 아키텍처가 아닙니다. 반복해서 함께 바뀌는 정책·데이터·동작과 서로 독립적으로 진화하는 부분을 구별합니다.
- **공유 의미에는 권위 있는 소유 경계를 둡니다.** 여러 구현이 의존하는 schema, 오류 의미, 상태 전이, 트랜잭션 불변식을 모두가 따로 정의·변경하지 않게 합니다. 소유 경계는 반드시 별도 package나 서비스일 필요가 없습니다.
- **국소 구현 가능성과 전체 결합 가능성을 같이 봅니다.** 한 영역을 내부 구현만으로 수정·검증할 수 있어도 다른 영역과 조합한 동작을 확인할 수 없으면 병렬 개발 성공이 아닙니다.
- **의존성을 숨겨 병렬성으로 계산하지 않습니다.** 생산자–소비자나 공유 불변식의 결정이 필요한 작업은 호환 경계를 먼저 갖추거나 순차·통합 작업으로 남깁니다.
- **편익보다 비싼 구조를 만들지 않습니다.** 불필요한 interface, 공통 package, 서비스 분리, 데이터 복제와 계약 테스트를 늘리지 않습니다. 현 구조 유지나 작은 접점 개선도 유효한 결과입니다.

## Patterns

### 독립적으로 완결되는 변경 단위 만들기

**문제:** 한 에이전트의 작은 기능 변경이 여러 기술 계층·공유 helper·설정을 횡단하고, 다른 에이전트의 변경과 같은 정책·모델을 계속 수정합니다.

**해결 형태:** 자주 독립적으로 발생하는 변경에는 **구현 책임, 그 변경에 필요한 공개 접점, 가까운 검증 경로**가 있는 단위를 비교합니다.

- 결제 수단별 adapter, 외부 데이터 입력원별 변환, 독립적인 정책 등은 실제 변경 이유가 다르고 공유 의미가 안정돼 있다면 각각 구현하고 확인하기 쉬운 경계가 될 수 있습니다.
- 각 단위는 다른 영역의 private 함수나 DB 내부 구조를 수정하지 않고, 공개 동작과 필요한 입력·출력으로 협력하도록 합니다. 기능별 모듈, 도메인별 모듈, 작은 컴포넌트는 모두 후보입니다.
- 독립 단위 내부에는 필요한 API·정책·테스트가 함께 있거나 쉽게 추적되어야 합니다. 반대로 하나의 불변식이 모든 단위에 복제된다면 분할을 줄이거나 의미 소유자를 재검토합니다.

**판단 신호:** 대표 변경을 두 개 동시에 가정했을 때 각자의 수정 지점·동작 검증이 독립적이고, 공유 코드의 변경 없이 공개 계약으로 연결되는가? 단지 파일 이동만으로 dependency cycle과 공동 데이터 쓰기가 남으면 개선이 아닙니다.

### 공유 계약과 불변식의 소유권 고정하기

**문제:** 에이전트 A가 결제 결과의 상태 의미를 바꾸는 사이 B는 이전 의미로 주문 상태를 구현합니다. 텍스트 충돌이 없어도 통합 오류가 발생합니다.

**해결 형태:** 공유 의미를 가진 요소마다 **누가 무엇을 결정하고 누가 소비하는지**가 구조에서 드러나게 합니다.

- 입력·출력의 의미, 오류·재시도 규약, 공통 데이터 형태에 권위 있는 정의가 있으면 소비자는 그 정의나 공개 기능에 의존합니다. 단일 코드·스키마가 적절하면 중복된 문서를 또 만들 필요가 없습니다.
- 각 기능의 문맥에서 의미가 다르다면 하나의 전역 모델을 강제하기보다 소비자 경계에서 변환할 수 있습니다. `shared/`에 모든 타입·helper를 넣는 것이 소유권을 명확히 하는 방법은 아닙니다.
- 계약을 변경할 때는 기존 소비자가 유지되는 호환 확장, 소비자 이전, 기존 형태 제거를 비교할 수 있습니다. 호환이 어렵거나 비용이 크면 그 변경은 하나의 결합 작업으로 다룹니다.
- 강한 정합성이 필요한 DB 상태 변경과 비즈니스 규칙은 **권위 있는 쓰기 주체**를 유지합니다. 병렬성을 위해 복수의 모듈이 같은 상태를 직접 갱신하도록 만들지 않습니다.

**판단 신호:** 두 에이전트가 각자의 코드만 보고 동일한 상태·오류·입출력 의미를 재구성할 수 있는가? 안 된다면 스키마와 타입을 더 쪼개기 전에 **정본 소유와 소비 방향**부터 정합니다.

### 조합 책임과 통합 검증 경계를 드러내기

**문제:** 독립 adapter와 정책 구현의 단위 테스트가 모두 통과해도, 이를 합친 checkout 흐름에서는 주문 상태가 잘못 바뀌거나 오류 처리 규칙이 어긋날 수 있습니다.

**해결 형태:** 여러 기능을 실제로 결합하는 **application/use-case 진입점**과, 거기서 지켜야 하는 불변식의 소유권을 분명하게 합니다.

- 상위 사용 사례가 하위의 공개 동작을 호출·조합하고, 하위 모듈은 상위 사용 사례의 내부 상태를 직접 수정하지 않는 방향을 비교합니다. 상위 조합자가 꼭 새로운 계층이나 별도 서비스일 필요는 없습니다.
- 독립 단위의 테스트와 별도로, 공개 계약을 연결한 동작·실패·상태 전이를 검증하는 지점을 선택합니다. 테스트를 많이 만드는 것보다 **어떤 경계가 무엇을 검증하는지**가 중요합니다.
- 외부 API 호출과 DB 쓰기는 일반적으로 하나의 로컬 트랜잭션으로 원자화되지 않습니다. 결제처럼 재시도·중복 실행·부분 실패가 중요한 곳에서는 그 의미를 소유한 영역이 복구·중복 방지 정책을 다루도록 하고, 이를 단순 통합 테스트 하나로 해결했다고 간주하지 않습니다.

**판단 신호:** 각각의 구현만 성공한 상태와 전체 기능이 올바르게 결합된 상태를 구분할 수 있는가? 조합 로직이 여러 adapter에 중복되거나 서로 순환 호출한다면 조합 책임이 분산된 것일 수 있습니다.

### 병렬화할 수 없는 의존성을 드러내기

세 가지 변경 관계를 구분합니다. 이는 agent 배분 절차가 아니라 **구조 후보를 선택하기 위한 의미적 관계**입니다.

| 변경 관계 | 아키텍처 선택 | 병렬화 판단 |
| --- | --- | --- |
| **독립**: 별도 정책·구현이 안정된 접점을 소비 | 변경별 내부 책임과 인접 검증을 분리 | 서로의 결정 없이 완결 가능할 때 병렬 후보 |
| **생산자–소비자**: API·schema·오류 의미가 한쪽의 입력 | 정본 계약과 소비 방향을 드러내고 필요 시 호환 경계 마련 | 계약이 안정되거나 호환 이전이 가능할 때만 독립 |
| **결합**: 같은 상태 전이·트랜잭션·정책을 함께 결정 | 하나의 불변식 소유 경계 안에 유지하고 주변부만 분리 | 공동 결정이 필요하면 결합 또는 순차 변경 |

구조적으로 **서로 다른 모듈을 갖는 것과 여러 agent가 동시에 안전하게 수정할 수 있는 것은 별개**입니다. 실행 시 작업 순서·branch·worktree·메시지 교환은 orchestrator가 다루지만, 의존성이 어디서 생기는지는 소프트웨어의 구조와 의미에서 결정됩니다.

### 다음 변경에서도 경계를 찾고 검증할 수 있게 하기

에이전트가 매번 저장소 전체를 다시 읽지 않도록 **공개 진입점 → 책임·계약의 원본 → 관련 검증**을 찾기 쉬운 형태를 선호합니다. 이는 독립 변경 경계의 실효성을 높이는 보조 패턴입니다.

이미 package export, 선언된 타입, 테스트 위치, 코드 검색·symbol navigation이 충분하면 새 인덱스와 설명 문서를 만들지 않습니다. 코드 구조 자체가 흐릿하거나 생성 코드·동적 등록 때문에 진짜 소유자가 감춰질 때만 기존 구조·설명을 개선합니다. 파일명·배치의 탐색성은 [Filesystem-Legible Structure](filesystem-legible-structure.md)가 담당합니다.

빠른 테스트 실행, 로그 수집, 세션 인계, 컨텍스트 주입 도구는 유용해도 모두 이 패턴의 아키텍처 요구는 아닙니다. 여기서 중요한 것은 **모듈이 의미 있는 동작과 검증 가능한 접점을 제공하는가**입니다.

## Example: 여러 에이전트가 하나의 checkout 기능 개발하기

가정: 카드·계좌이체 결제를 추가하면서 할인 규칙을 변경하고, 최종 결제 결과에 따라 주문 상태를 전이시켜야 합니다. 서로 다른 구현을 동시에 개발할 수 있지만 **결제 결과의 의미, 중복 요청 처리, 주문 상태 전이**는 공유 결정입니다.

### 후보 A — 하나의 변경이 여러 작업과 충돌하기 쉬운 구조

```text
src/
  checkout.py     # provider 분기 + 할인 + 주문 상태 변경
  payments.py     # 카드/이체 구현과 공통 반환 의미
  models.py       # 공유 주문·결제 상태
tests/
  test_checkout.py
```

카드 구현, 계좌이체 구현, 할인 정책을 각각 수정하면서 여러 에이전트가 `checkout.py`의 분기와 `payments.py`의 반환 의미를 함께 바꿔야 한다면, 기능별 코드가 다른 위치에 있어도 실제로는 결합돼 있습니다. 파일 충돌이 없더라도 각자의 오류 의미가 다르면 통합 실패가 납니다.

### 후보 B — 책임과 통합 경계를 분리한 구조

```text
src/
  ordering/
    checkout.py            # 가격·결제 동작을 조합
    state.py               # 주문 상태 쓰기·전이의 권위
  pricing/
    discounts.py           # 할인 정책
  payments/
    outcome.py             # 결과·오류의 공개 의미
    charge.py              # 외부 소비자를 위한 결제 동작
    providers/
      card.py
      bank_transfer.py
tests/
  pricing/
  payments/
    providers/
  ordering/
    test_checkout.py       # 계약 연결·상태 전이 검증
```

이 배치는 가능한 설계 **예시**입니다. 파일 경계와 runtime 호출 경계가 반드시 1:1일 필요는 없습니다.

- 카드와 계좌이체 구현은 동일한 `payments`의 결과·오류 의미를 소비하며 각자의 연동 동작을 검증할 수 있습니다. 할인 정책은 `pricing`에서 별도로 변경할 수 있습니다.
- `ordering.checkout`이 가격 계산과 결제 동작을 조합하고, 주문 상태 변경은 `ordering.state`에 모읍니다. 결제 provider가 주문 테이블에 직접 쓰는 형태는 피합니다.
- 외부 결제와 주문 DB는 원자적이지 않을 수 있습니다. 주문 상태·재시도·멱등성의 실제 정책 소유는 해당 시스템의 결제 흐름을 분석해 정해야 하며, 그림만으로 분산 정합성을 보장하지 않습니다.
- `payments.outcome`의 의미가 아직 변하고 있다면 provider 구현과 checkout 소비자는 독립이 아닙니다. 이때는 **공개 계약을 먼저 안정화하거나, 호환 전환을 택하거나, 하나의 결합 변경으로 다루는 것**이 정확한 선택입니다.

**구조적 차이:** 후보 B에서는 일부 구현이 공유 계약을 *읽기만* 하며 자체 검증으로 완료될 수 있습니다. 반면 결제 결과 해석과 주문 상태 전이의 통합 책임은 그대로 남아 있습니다. 병렬 작업이 가능해진 것은 agent별 디렉터리 때문이 아니라 **독립 변경과 공유 의미의 경계가 달라졌기 때문**입니다.

### 후보 C — 구조 개편보다 작은 개선이 나은 경우

현재 코드에서 각 provider가 이미 별도 함수로 나뉘어 있고 공통 결과 의미도 안정적이라면, `checkout.py`에서 실제로 함께 바뀌는 분기만 작게 정리하거나 관련 테스트를 보강하는 것으로 충분할 수 있습니다. provider가 둘뿐이고 변화가 드물다면 후보 B의 새 모듈과 파일은 과도합니다.

**추가 반례:** 할인과 결제가 반드시 하나의 일관성 경계에서 결정돼야 한다면, 여러 정책을 물리적으로 분리하는 것이 좋다는 결론을 먼저 내리지 않습니다. 시스템이 요구하는 원자성·실패 복구 규칙을 보존하는 더 큰 책임 단위를 선택할 수 있습니다.

## 설계안을 어떻게 비교할까

신규 설계나 리팩터링 전에 대표 변경 두세 가지를 두고 **현 구조 유지(A), 최소 seam 개선(C), 책임 경계 재설계(B)**를 비교합니다. 꼭 이 순서나 세 후보를 의무화할 필요는 없습니다.

- **독립 완료:** 변경마다 무엇을 읽고 어디를 수정하며 어떤 검증만으로 해당 부분의 성공을 확인할 수 있는가?
- **공유 의미:** 함께 변경하는 계약·데이터·정책·쓰기 소유자는 누구인가? 다른 agent가 그 의미를 별도로 추측해야 하는가?
- **통합:** 연결된 기능의 상태·오류·재시도·후속 효과를 검증할 진입점은 어디인가?
- **비용과 반례:** 새 추상화·패키지·테스트의 유지비가 공동 수정·재탐색·통합 재작업 감소보다 적은가? 순차 변경이 더 안전한가?

독립 작업만 성공하고 통합이 깨지는 구조는 좋은 병렬 개발 아키텍처가 아닙니다. 다만 경계가 명확하다는 이유만으로 실제 성능 향상을 입증했다고 주장하지 않습니다. 실제 비교에는 동일 조건의 agent 실행과 **통합 후 정확성, cross-agent 의존성 충족, 재작업·실행 비용**을 함께 봐야 합니다.

## Boundary

이 패턴은 **소프트웨어의 구조 선택**을 소유합니다. agent 역할 배분, 실행 순서, 통신, 컨텍스트 전달, branch·worktree, CI gate, 테스트 runner 및 기억 시스템의 운영은 별도 workflow·harness의 책임입니다. 아키텍처는 그들이 사용할 수 있는 책임·계약·검증 경계를 제공할 뿐입니다.

기존의 도메인 응집도, 보안, 트랜잭션 정합성, 성능과 운영 요구를 훼손하지 않습니다. agent 수에 맞는 모듈 수, 고정 레이어, 서비스 분리, 이벤트 버스, 새 문서·index, 맞춤 lint, 의무적인 계약 테스트를 요구하지 않습니다.

## Grounding

**실증과 설계 휴리스틱을 구별합니다.** 아래 연구는 다중 agent 코딩의 통합·조정 문제가 있음을 보여주지만, 특정 모듈 구조가 모든 프로젝트에서 더 빠르다고 증명하지는 않습니다.

- [CooperBench](https://arxiv.org/abs/2601.13295) — 두 agent가 각각 구현할 수 있는 작업도 협업 과정에서 실패할 수 있다는 근거. 그 결과를 아키텍처 변경의 인과적 효과로 읽지 않습니다.
- [AsynCodeBench](https://arxiv.org/abs/2609.32662) — 개별 task 성공과 agent 간 의존성 충족을 분리해 평가할 근거.
- [OpenAI, Harness Engineering](https://openai.com/index/harness-engineering/) — agent가 이해할 수 있는 경계, 접근 가능한 정본과 검증 가능한 구조의 실무 사례. 사례의 고정 레이어·맞춤 lint를 보편 규칙으로 복제하지 않습니다.
- [Parnas, Modular Decomposition](https://doi.org/10.1145/361598.361623) / [Microsoft, Domain Analysis](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis) — 변경 이유에 따른 책임 분리와 의미적 소유권의 기본 원리. 이는 인간 개발에도 통용됩니다.
- [Fowler, Parallel Change](https://martinfowler.com/bliki/ParallelChange.html) / [Microservice Trade-Offs](https://martinfowler.com/articles/microservice-trade-offs.html) — 계약의 점진적 전환과 물리적 서비스 분리의 유지비.
