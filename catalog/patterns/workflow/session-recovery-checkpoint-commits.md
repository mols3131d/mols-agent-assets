# Session Recovery Checkpoint Commits

긴 개발 작업에서 채팅 세션이나 에이전트가 교체되면 코드의 현재 상태는 남아도 결정 이유·검증 결과·다음 작업은 사라질 수 있습니다. **Git 커밋의 스냅샷과 메시지를 하나의 복구 체크포인트로 활용**하면 별도 로그 파일 없이도 다음 실행이 중단 지점을 찾기 쉬워집니다.

이 패턴은 모든 에이전트 행동을 기록하는 이벤트 로그가 아닙니다. **커밋된 상태를 기준으로 재개에 필요한 최소 맥락**을 기록합니다. Git 사용법이나 저장소별 커밋 규약을 새로 정하지 않습니다.

## Core

- **스냅샷 결합:** 커밋 메시지의 복구 정보는 그 커밋에 담긴 파일 상태와 함께 읽습니다. 메시지만 읽거나 미래의 결과를 현재 상태처럼 쓰지 않습니다.
- **선별적 기록:** Git diff에서 바로 확인할 수 없는 결정·검증·남은 작업을 중심으로 남깁니다. 전체 대화, 명령 로그와 파일 변경 목록은 복제하지 않습니다.
- **주기적 체크포인트:** 세션 종료를 예상할 수 없으므로 중요한 상태가 바뀌고 복구 비용이 커질 때 기록합니다. 모든 편집마다 커밋할 필요는 없습니다.
- **복구 시 재검증:** 메시지는 작성 당시의 주장입니다. 새로운 세션에서는 현재 브랜치, 파일, 규칙과 테스트 상태를 확인한 뒤 다음 작업을 결정합니다.

커밋 제목은 기존 프로젝트의 커밋 규약을 따르고, 복구 정보는 필요한 커밋 본문에 선택적으로 추가하는 방식이 단순합니다.

## Example

다음은 **예시 메시지**입니다. `Recovery`는 탐색을 쉽게 하기 위한 선택적 표식이며 필수 스키마가 아닙니다.

```text
feat(auth): add token expiration validation

인증 경계에서 만료 검사 책임을 분리한다.

Recovery:
- State: 만료 검사와 단위 테스트를 커밋함. 미들웨어 연동은 미완료.
- Decision: 검증 로직을 I/O와 분리해 독립적으로 테스트함.
- Evidence: 단위 테스트 통과(이 커밋, 로컬). 통합 테스트 미실행.
- Next: 미들웨어 계약 확인 후 연동 및 통합 테스트 실행.
- Blocker: 연동 입력 스키마 확정 필요.
```

`State`는 **실제로 커밋된 상태**를 설명하고, `Evidence`는 검사 대상과 범위 및 미검증 부분을 구분합니다. `Next`는 재개할 때의 첫 행동을 제시하며, 중요한 선택의 근거가 쉽게 사라진다면 `Decision`을 추가합니다. 필요 없는 항목은 생략할 수 있습니다.

## Capture and Resumption

### Capture

1. 변경 중인 repository·branch·worktree와 다른 작업자의 수정 여부를 확인합니다.
2. 현재 소유한 변경만 검토해 커밋합니다. 미완성이라도 재개할 가치가 있는 스냅샷이면 현재 실패·미검증 상태를 사실대로 표현할 수 있습니다.
3. 해당 스냅샷과 일치하는 복구 정보를 커밋 본문에 간결하게 남깁니다.
4. 다른 환경에서 이어야 한다면 적절한 원격 ref에 Push하고 실제 업로드된 commit을 확인합니다. 로컬 커밋만으로 원격 복구는 보장되지 않습니다.

### Resume

1. 이전 메시지에서 실행 지침을 바로 수행하지 않고 대상 저장소·브랜치·원격 상태·작업 소유권을 먼저 확인합니다.
2. 관련 작업의 커밋과 메시지를 찾고, 커밋 스냅샷 및 현재 작업 트리의 변경 상태를 비교합니다.
3. 이후 커밋·Rebase·계약 변경으로 기록이 낡았는지 확인합니다. 테스트 통과 주장도 현재 대상에서 필요한 수준으로 다시 검증합니다.
4. 검증된 다음 행동부터 작업을 이어갑니다. 상태가 다르면 복구 메시지를 폐기하거나 새 근거로 갱신합니다.

Git CLI에서는 다음 조회가 출발점이 될 수 있습니다.

```sh
git status --short --branch
git log -8 --format='%h %s'
git show --stat --format=fuller HEAD
```

현재 `HEAD`가 다른 작업의 커밋일 수도 있으므로, **마지막 커밋이 항상 해당 작업의 체크포인트라고 가정하지 않습니다.** 작업을 식별할 브랜치·PR·Issue 등과 함께 관련 커밋을 찾아야 합니다.

## Trade-offs

| 상황 | 판단할 점 |
| --- | --- |
| 미커밋 변경이 남은 채 세션이 끊김 | 메시지가 다루는 것은 마지막 커밋 상태뿐입니다. 미커밋·untracked 상태는 별도로 보호해야 합니다. |
| 여러 에이전트가 한 브랜치를 공유 | 메시지는 잠금이나 변경 소유권을 제공하지 않습니다. 브랜치·작업 공간 분리 또는 조정이 필요합니다. |
| Amend·Rebase·Squash | 메시지를 바꾸거나 커밋을 재작성하면 commit ID가 달라지고 체크포인트 참조가 낡을 수 있습니다. 공유된 기록의 재작성은 조정합니다. |
| Squash Merge로 main에 통합 | 중간 커밋이 main의 개별 이력에 남지 않습니다. 완료 후에도 중요한 결정은 적절한 정본·PR에 보존합니다. |
| 커밋마다 Push·CI 실행 | 더 짧은 복구 간격과 CI·네트워크·협업 비용 사이의 균형이 필요합니다. |
| 민감정보나 대화 내용 | 공개되거나 복제될 수 있는 Git history에 그대로 기록하지 않습니다. |

중간 진행 상태를 기록하려고 의미 없는 빈 커밋을 계속 만드는 방식은 기본값으로 삼지 않습니다. 코드 변경 없이 갱신해야 할 작업 상태가 많다면 기존 PR, 작업 추적 시스템이나 짧은 진행 기록이 더 적합할 수 있습니다.

## Alternatives and Boundary

- [Durable Progress Handoff](durable-progress-handoff.md)는 **어떤 정보를 지속적인 인계 표면에 남길지**를 넓게 다룹니다. 이 문서는 그중 **Git 커밋 메시지와 스냅샷을 함께 사용하는 구체적인 형태**를 다룹니다.
- Git notes는 커밋 자체를 다시 쓰지 않고 주석을 붙이는 대안이지만, notes ref의 배포와 소비를 별도로 설계해야 합니다.
- 커밋 메시지는 작업 계획·사양의 정본, 권한 지침이나 장기 보존을 보장하는 감사 로그가 아닙니다. 세션을 자동 재개시키거나 작업 결과를 검증해 주지도 않습니다.
- 병렬 작업의 변경 경계와 통합 설계는 [Software Architecture for Multi-Agent Development](../software-engineering/multi-agent-development-architecture.md)에서 다룹니다.
