# Session Recovery Checkpoint Commits

Git diff만으로는 변경 이유·검증 한계·다음 확인 지점을 알기 어려울 수 있습니다. **의미 있는 변경 단위로 커밋하고, 메시지에 필요한 재개 단서를 남기면** 세션 단절·작업자 교체 후 재탐색 비용을 줄일 수 있습니다.

이 패턴은 커밋에 기록된 상태로 작업을 재개하는 방식이며, 미커밋 변경이나 장기 작업의 전체 진행 상황까지 복원하지는 못합니다.

## When to Use

- **적합:** 의미 있는 변경을 체크포인트로 남기고, 다음 작업자가 diff 밖의 판단·검증 범위·후속 조건을 알아야 할 때.
- **다른 수단이 적합:** 코드 변경 없이 작업 상태만 남기거나 여러 커밋에 걸친 목표·의존성·진행 상황을 관리할 때. PR·작업 기록 또는 [Durable Progress Handoff](durable-progress-handoff.md)를 고려합니다.

## Core

- **의미 있는 스냅샷:** 하나의 변경 목적을 중심으로 커밋을 구성해 이해·검토·검증·되돌리기 쉽게 합니다.
- **새로운 재개 단서:** 변경 이유와 더불어 diff·PR·명세에 없는 중요한 결정·검증 한계·후속 조건만 메시지에 보완합니다. 다시 알아내기 비싼 정보에 집중하고 중복은 줄입니다.
- **현재 상태와 대조:** 메시지는 해당 커밋 당시의 기록입니다. 재개 시 현재 ref·코드·작업 공간과 검증 근거를 확인합니다.

## Commit Granularity

커밋 단위는 줄 수·파일 수·세션 길이보다 **함께 이해하고 검토할 수 있는 변경 목적**을 기준으로 선택하는 편이 유용합니다. 하나의 작업이나 PR이 여러 커밋으로 구성될 수도 있습니다.

- **묶기:** 하나의 목적을 완성하는 구현·테스트·설정·문서를 함께 포함할 수 있습니다. 기계적 분할로 맥락을 흩뜨리지 않습니다.
- **나누기:** 독립적인 목적의 수정은 분리하고, 큰 변경은 검토·검증 가능한 하위 단위로 구성합니다. 고정된 변경 줄 수를 강제하지 않습니다.
- **체크포인트 시점:** 의미 있는 진척이나 인계 필요에 따라 커밋합니다. 세션 종료만을 이유로 커밋을 늘리지는 않습니다. 미완료 상태를 보존할 때는 작업 브랜치에서 미검증 범위를 명확히 하고 통합 가능한 결과로 오인하지 않습니다.
- **재구성:** 필요하면 커밋을 분할·통합·재배열할 수 있습니다. 게시·공유된 이력을 재작성할 때는 다른 작업자의 의존성과 프로젝트 권한을 먼저 확인합니다.

예를 들어 인증 만료 정책과 회귀 테스트는 함께 묶고, 무관한 로깅 정리는 별도 커밋으로 분리할 수 있습니다. 작업 브랜치의 체크포인트 구성과 최종 통합 이력은 같을 필요가 없습니다.

## Sample Commit Message

메시지에는 변경 이유와, 필요하다면 재개 시 알아야 할 검증 한계·후속 조건을 자연스럽게 적습니다. 별도의 재개 전용 필드는 필요하지 않습니다. 다음 예시의 제목은 [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) 표현을 빌렸을 뿐, 규약 채택을 요구하지 않습니다.

간단한 변경에는 제목만으로 충분합니다.

```text
fix(auth): reject expired access tokens
```

검증 한계와 후속 확인이 중요하다면 본문에 남깁니다.

```text
refactor(auth): separate token expiry policy

Keep expiry rules independent of HTTP middleware so policy
tests do not require HTTP request setup.

Token policy unit tests passed locally; middleware integration
remains unverified. Confirm the request schema before adding
integration tests.
```

## Typical Use

1. **구성:** 현재 diff를 살펴보고 위 기준으로 체크포인트 단위를 정하며 미완료·미검증 범위를 확인합니다.
2. **기록:** 커밋할 변경과 실제 검증을 확인한 후, 다음 작업자가 다시 알아내기 어려운 정보만 메시지에 보완합니다. 실행하지 않은 검사를 통과로 적거나 커밋 자체의 SHA를 메시지에 미리 넣지 않습니다.
3. **재개:** 올바른 작업·저장소·브랜치/PR 및 현재 working tree를 확인한 다음, 관련 커밋의 메시지와 스냅샷을 읽습니다. 반드시 HEAD일 필요는 없으며 이후 변경과 계약을 대조하고 필요한 검증을 수행합니다.

다른 실행 환경에서 재개하려면 해당 커밋이 **조회 가능한 원격 ref에 게시**되어 있어야 합니다.

## Limits

- **미커밋 상태:** 커밋 이후 변경과 폐기된 로컬 상태는 복구할 수 없습니다. 남은 변경은 다른 작업자의 소유 여부를 확인하고 보존합니다.
- **이력의 지속성:** amend·rebase·branch 삭제·[Squash Merge](https://docs.github.com/en/pull-requests/reference/pull-request-merges)로 중간 커밋을 찾기 어려워질 수 있습니다. 오래 보존할 결정은 PR·명세 등 지속적인 소유 위치에 옮깁니다.
- **기록의 신뢰성:** 과거 검증·후속 제안은 현재의 사실·지침·실행 권한이 아닙니다. 변경된 환경을 확인하고 다른 작업자의 변경을 덮어쓰지 않습니다.
- **정보 노출:** 커밋 메시지는 공유·영구 보존될 수 있으므로 비밀정보·개인정보·공개할 수 없는 대화는 포함하지 않습니다.

## Boundary

이 패턴은 **커밋의 변경 단위와 메시지·스냅샷을 통해 세션 복구 단서를 남기는 선택지**입니다. 긴 작업의 전체 상태·에이전트 간 동시 작업 조정·프로젝트별 Git 규약과 이력 재작성 권한은 별도의 작업 기록과 적용 프로젝트의 정책이 소유합니다.
