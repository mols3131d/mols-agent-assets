# Chatbot-Driven Development

사람이 개발의 목표와 제약을 제시하면 챗봇이 **필요한 판단을 함께 구체화하거나 위임받아 수행**하고, 실제 근거로 결과를 검토하며 다음 행동을 이어 가는 협업 패턴입니다.

초기 요청은 완성된 스펙일 필요가 없습니다. 반대로 모호하다는 이유만으로 긴 인터뷰를 의무화하지도 않습니다. 핵심은 **사람의 개입 비용을 줄이면서도 목적의 정합성, 판단 품질과 검증 수준을 유지하는 것**입니다.

## Core

```text
목표·제약·원하는 결과
         ↓
현재 맥락과 미정 사항 파악
         ↓
필요한 만큼 구체화 ── 질문 / 조사 / 토론 / 위임 판단
         ↓
달성할 범위·완료 조건과 확인 방법
         ↓
적합한 개발 Work ── 스펙 / 계획 / 구현 / 테스트 / 리뷰
         ↓
실제 근거로 결과 검토 ── 실패·불확실성에 따라 필요한 부분 재진행
         ↓
요청 범위의 완료 / 사람의 결정 / 인계·차단
```

이 흐름은 반드시 거쳐야 하는 직선형 pipeline이 아닙니다. 이미 충분히 명확한 요청은 바로 Work로 이어질 수 있고, 조사나 설계가 요청한 최종 결과라면 **구현 없이 그 결과에서 끝날 수 있습니다**. 구현 뒤 새 증거가 초기 가정을 뒤집으면 구체화나 계획을 다시 검토할 수도 있습니다.

이 패턴은 별도의 오케스트레이터나 필수 Prompt·Command·Skill을 정의하지 않습니다. 현재 환경의 기존 개발 방법, 프로젝트 정책과 도구를 조합하는 **협업 방식**에 가깝습니다.

## 목표를 어떻게 구체화할까?

모호함은 모두 같은 성질이 아닙니다. 현재 구현에서 **조사로 확인할 사실**, 사용자에게 **선호를 물어야 할 선택**, 에이전트가 **위임받아 판단할 수 있는 기술적 결정**을 구분하면 질문과 시행착오를 함께 줄일 수 있습니다.

| 참여 방식 | 유용한 상황 | 대표적인 상호작용 |
| --- | --- | --- |
| **함께 구체화** | 제품 방향이나 우선순위를 사람이 직접 결정하려는 경우 | 중요한 선택지를 설명하고 질문·토론으로 목표와 완료 조건을 정함 |
| **질문 최소화** | 목표는 대체로 명확하지만 세부사항이 비어 있는 경우 | 저장소·근거를 먼저 조사하고, 결과를 바꾸는 질문만 추려서 제시 |
| **판단 위임** | 사용자가 기술적·실무적 결정을 에이전트에게 맡기려는 경우 | 가정과 대안을 검토하고 적절한 기본값을 채택하며, 필요한 경계에서만 사람에게 돌려줌 |

이들은 고정된 모드나 단계가 아니라 상황에 따라 달라지는 **참여 정도**입니다. 사용자는 같은 작업에서도 초기 목표는 함께 정하고, 구현 대안 선택과 검증은 위임할 수 있습니다.

### 무엇을 질문하고 무엇을 위임할까?

- **조사 가능한 사실** — 소스 코드, 기존 스펙, 계약, 이슈와 실제 환경에서 확인할 수 있다면 먼저 조사하는 편이 유용합니다.
- **작고 가역적인 선택** — 이미 정해진 범위 안에서 합리적인 기본값을 선택하고 그 이유를 간결하게 남길 수 있습니다.
- **사용자의 가치·선호가 필요한 선택** — 상충하는 목표, 제품 우선순위, 기대 경험처럼 근거만으로 답이 정해지지 않으면 대안과 권고를 제시하고 묻는 편이 낫습니다.
- **권한이나 영향 범위가 달라지는 선택** — 범위 확대, 비가역적인 조작, 중요한 외부 계약 변경은 단순한 판단 위임만으로 허가됐다고 볼 수 없습니다. 실제 프로젝트와 도구의 승인 경계를 따릅니다.

위임의 품질은 **질문을 얼마나 생략했는가**보다, 질문할 필요 없는 사실을 해결하고 중요한 미정 사항과 반례를 발견했는가에 달려 있습니다. 에이전트가 도출한 가정은 사용자가 명시적으로 정한 요구사항과 구별해 둘 가치가 있습니다.

## 구체화에 쓸 수 있는 방법

| 방법 | 특히 유용한 경우 | 기대하는 기여 |
| --- | --- | --- |
| **Grill Me식 질문** | 선행 결정이 확정되지 않아 후속 질문에 답하기 어려움 | 결정 의존관계를 따라 질문을 묶고, 필요한 선택을 드러냄 |
| **조사** | 동작·제약·대안에 대한 사실이 불명확함 | 기존 상태와 근거를 확인하고 추측과 사실을 분리 |
| **토론·반증** | 중요한 설계 대안이 경합하거나 가정이 취약함 | 반대 입장과 실패 사례를 검토해 방향을 개선하거나 미해결로 남김 |
| **스펙** | 목표를 구현·검증 과정에서 일관되게 참조해야 함 | 기대 동작, 비목표, 경계 조건과 완료 기준을 명료하게 표현 |
| **테스트 설계** | 완료 조건을 관측 가능한 동작으로 연결할 수 있음 | 정상·실패·회귀 사례와 검증 가능한 주장을 식별 |

모든 방법을 호출할 이유는 없습니다. 불필요한 질문·의례적 토론·형식만 갖춘 스펙은 오히려 비용을 늘립니다. 반대로 복잡하고 되돌리기 어려운 변경에서는 짧은 구현보다 충분한 조사와 반증이 저렴할 수 있습니다.

## 완료는 어떤 근거로 판단할까?

목표를 구체화했다면 **요구한 결과와 그것을 확인할 근거**가 서로 연결되어 있는지 살펴볼 수 있습니다.

```text
사용자 목적 · 기존 계약
      ↓
완료 조건 · 예상 동작
      ↓
테스트 / 관찰 / 리뷰 등 확인 방법
      ↓
현재 revision에서 얻은 실제 결과
      ↓
충족 · 미검증 · 불충족을 구분
```

스펙은 기대하는 동작을 서술하고, 테스트는 일부 동작을 관찰하며, CI는 특정 변경 상태에서 해당 검증이 실행된 결과를 제공합니다. **CI 통과가 모든 요구사항이나 사용자 의도를 입증하지는 않습니다.** 에이전트가 스스로 작성한 스펙과 테스트가 서로 일치하더라도 최초 의도와 기존 계약이 틀리게 해석됐을 가능성은 남습니다.

검증은 목적에 맞는 가장 작은 근거부터 선택할 수 있습니다. 단순한 문서 수정에 종합적인 런타임 평가가 필요한 것은 아니며, 사용자 경험이나 외부 시스템 동작은 정적 테스트만으로 충분하지 않을 수 있습니다. 리뷰와 재작업은 **새 근거가 드러낸 공백**을 중심으로 진행하는 편이 효율적입니다.

## Typical Forms

### 모호한 기능 요청

> “이 기능을 더 쓰기 쉽게 만들어 줘. 세부 판단은 맡길게.”

챗봇은 먼저 현재 동작과 사용 맥락을 조사하고 개선 방향과 반례를 비교할 수 있습니다. 시제품 없이는 결정하기 어려운 경험적 선택은 소규모 실험으로 확인하고, 사용자 취향이 결정적인 문제라면 압축된 선택지를 물을 수 있습니다. 요청이 조사·기획까지라면 그 결과를 종료점으로 삼고, 구현이 허용된 경우에만 변경과 검증으로 이어집니다.

### 기존 PR의 준비 상태 개선

> “이 PR을 리뷰하고 필요한 수정을 진행해. CI까지 확인해 줘.”

챗봇은 PR의 의도, 변경 상태와 검증 근거를 확인한 뒤 결함을 수정하고 해당 revision에 대응하는 결과를 다시 살펴볼 수 있습니다. 완료된 작업, 미검증 조건, 최종 승인 판단은 구분합니다. **PR의 검증 준비와 실제 병합 승인은 동일하지 않습니다.**

### 로컬 실행 환경이 없는 챗봇

코드를 직접 실행할 수 없어도 저장소 연동으로 수정하거나 원격 CI의 결과를 검토하는 형태가 가능합니다. 다만 read/write, 검사 로그 조회, 작업 재실행과 권한은 각 연결의 실제 기능에 달려 있습니다.

CI 실패가 생성기 실행이나 환경 문제를 드러냈지만 해당 조작을 할 수 없다면, 근거 없는 수동 수정이나 성공 선언보다 정확한 장애 원인과 가능한 복구 경로를 남기는 것이 더 유용합니다. **연결된 도구가 있다고 해서 비동기 작업 지속이나 세션 종료 후 자동 재개까지 가능한 것은 아닙니다.**

## Considerations

- **목적보다 절차가 앞서는 문제** — 질문·스펙·테스트의 개수나 고정 순서가 성과 지표가 되면 작은 작업도 불필요하게 무거워집니다. 중요한 미정 사항과 위험에 비례해 깊이를 선택할 수 있습니다.
- **위임이 무제한 권한처럼 해석되는 문제** — 에이전트에게 판단을 맡기는 것과 변경·배포·병합 권한을 부여하는 것은 별개입니다. 사용자 의도, 프로젝트 규칙과 실제 실행 권한의 경계를 유지할 필요가 있습니다.
- **자체 검증의 순환 논리** — 스펙, 구현, 테스트와 셀프 리뷰를 한 모델이 모두 만들었다면 서로의 일치성은 독립적인 정확성 근거가 아닙니다. 기존 계약, 관측된 결과, 별도 검토와 비교할 수 있습니다.
- **길어진 작업의 맥락 손실** — 세션을 넘어가야 한다면 전체 대화보다 목표·유효한 결정·검증 상태·남은 작업을 재개 가능한 곳에 남기는 편이 효율적입니다. 재개 시에는 현재 소스와 상태를 다시 확인합니다.
- **작동하는 자동화를 문서만으로 기대하는 문제** — 패턴을 참고하거나 로드했다고 해서 챗봇이 자동 발견·호출하거나 CI 완료 후 다시 실행되지는 않습니다. 실제 연계는 대상 런타임과 프로젝트가 선택합니다.

## Related Patterns and Methods

- [Durable Progress Handoff](durable-progress-handoff.md) — 인계·재개에 필요한 최소 상태와 freshness 확인을 다룹니다.
- [Artifact Inbox](artifact-inbox.md) — 조사·스펙·리뷰 등 임시 작업 결과를 놓을 수 있는 surface를 소개합니다.
- [Progressive Context Routing](../context-engineering/progressive-context-routing.md) — 필요한 지침과 근거만 단계적으로 불러오는 방법을 다룹니다.

- [mols-loops](../../../src/rulesync/.rulesync/skills/mols-loops/SKILL.md) — Research·Plan·Work·Review를 반복적으로 조합하는 **선택 가능한** 기존 오케스트레이터 예시입니다.

질문 방식은 [Grill Me](https://github.com/mattpocock/skills/blob/main/docs/productivity/grill-me.md), 스펙과 작업의 정합성은 [Spec Kit](https://github.com/github/spec-kit/blob/main/docs/quickstart.md)와 [OpenSpec](https://openspec.dev/docs/quickstart)를 참고할 수 있습니다. 이들을 설치하거나 동일한 단계·파일 구조를 채택해야 하는 것은 아닙니다.

## Boundary

이 패턴이 다루는 것은 **목표 구체화, 판단 위임, 개발 수행과 증거 기반 완료를 연결하는 협업의 형태**입니다. 특정 오케스트레이터의 상태 기계, 스펙 스키마, 테스트·CI 계약, GitHub 권한, Agent Asset의 호출 방식이나 repository 정책은 각각의 소유자가 정합니다.

패턴을 채택하는 프로젝트는 자기 환경에 맞게 좁히거나 변형할 수 있으며, **이 문서가 있다는 사실만으로 어느 챗봇이나 에이전트에 적용되는 지침이 되지는 않습니다.**
